Part I — Foundations

Why Version Control — Chapter 1

Before the commands, the problem. Version control exists to solve real pain that anyone who's ever lost work, juggled "final_v3_FINAL.docx" files, or tried to collaborate on code has felt. Understanding *why* makes the *how* make sense.

The pain without it

You've lived the problems version control solves, even if you've never used Git:

  • "final_v3_REALfinal_v2.docx" — manually copying files to save versions, then losing track of which is which.
  • "It worked yesterday" — you changed something, it broke, and you can't remember what you changed or get back to the working version.
  • Collaboration chaos — two people edit the same file and one overwrites the other's work; emailing zip files back and forth.
  • No history — no record of what changed, when, why, or who did it.
  • Fear of changing things — afraid to experiment because you might break what works and can't undo it.

What version control gives you

A version control system (VCS) tracks changes to files over time, so you can:

  • Travel through time — every saved version (commit) is recoverable; go back to any point.
  • See the full history — what changed, when, by whom, and (via commit messages) why.
  • Experiment safely — branch off, try something, and either keep it or throw it away without touching the working version.
  • Collaborate without chaos — many people work in parallel and merge their changes intelligently.
  • Back up & sync — your whole project and its history live in multiple places.

Git won — and here's the lineage

There have been many version control systems (CVS, Subversion/SVN, Mercurial), but Git has become the overwhelming standard — it's what essentially the entire software world uses. It was created in 2005 by Linus Torvalds (yes, the Linux creator — Linux Field Guide) to manage Linux kernel development, after the team lost access to their previous tool. He built it to be fast, distributed, and impossible to corrupt silently — and those design choices are why it won.

Git vs GitHub — the distinction everyone blurs

This trips up every beginner, so let's nail it now:

Analogy: Git is the tool; GitHub is a place to store and share what the tool produces — like the difference between a word processor (Git) and a document-sharing service (GitHub). You can use Git entirely on your own machine forever; GitHub adds hosting, collaboration, pull requests, and the social/project layer (Part III).

From the field — Git is non-negotiable, and worth understanding deeply Git isn't optional in modern tech. Every software job, most sysadmin and security and data roles, every open-source project, and increasingly every kind of "files that change over time" work assumes you know it. The good news and bad news: most people learn just enough Git to get by — add, commit, push — and then panic the first time something unexpected happens, because they never learned the model. This book's bet is that an hour spent understanding how Git actually thinks (Chapter 2) saves you years of cargo-culting commands you don't understand. The difference between someone who's "okay at Git" and someone who's genuinely comfortable isn't more memorized commands — it's the mental model that lets them reason about any situation. That's what we build next.

How Git Thinks — Chapter 2

This is the most important chapter in the book. Almost every Git frustration comes from not having the mental model — and once you have it, the commands stop being magic spells and become obvious. Read this slowly; everything else depends on it.

Git stores snapshots, not differences

The first key idea: when you commit, Git saves a complete snapshot of all your files at that moment — not a list of changes, but a picture of the whole project (it's clever about not duplicating unchanged files, but think "snapshot"). Your history is a series of these snapshots, each one a commit. This is why you can jump to any past state instantly: Git just shows you that snapshot. Think of commits as save points in a video game — each is a complete, restorable state of your world.

The three areas — the heart of the model

Your files move through three areas, and understanding this flow is 80% of understanding Git:

AreaWhat it isYou get here with
Working DirectoryYour actual files, as you edit them right now(just editing)
Staging Area (index)A "loading dock" — the changes you've chosen to include in the next commitgit add
Repository (.git)The permanent history of committed snapshotsgit commit

The staging area is what confuses people but it's powerful: it lets you craft a commit deliberately — include these changes but not those, so each commit is a clean, logical unit. You edit freely, add the changes you want to group, then commit them as a snapshot with a message.

Commits form a chain (the DAG)

Each commit points back to its parent (the commit before it), forming a chain — technically a directed acyclic graph (DAG) once branches enter the picture. Each commit has a unique ID (a SHA hash like a3f5c9d). You don't need the graph theory; just hold this picture: commits are snapshots linked in a chain, newest pointing back to oldest. Branches (Part II) are just movable pointers to a commit in this chain — which is why branching in Git is so cheap and fast.

HEAD — "you are here"

One more piece: HEAD is a pointer to "where you currently are" — normally the latest commit on your current branch. When you commit, HEAD (and your branch) move forward to the new commit. When you switch branches or check out an old commit, HEAD moves. Think of HEAD as the "you are here" marker on the map of your history. Many commands make sense once you picture what HEAD points to and where it moves.

From the field — this model is the whole game Internalize four things and Git stops being scary forever: (1) commits are snapshots (complete save points); (2) files flow through three areas — working dir → add → staging → commit → repository; (3) commits form a chain, each pointing to its parent; (4) branches and HEAD are just pointers that move along that chain. Every command in this book is some manipulation of these ideas: add moves changes to staging, commit snapshots staging, branch makes a new pointer, merge joins chains, reset moves a pointer, checkout moves HEAD. People who memorize commands without this model are forever lost when something unexpected happens; people who hold the model can reason out any situation by asking "what are the areas, what do the pointers point to, where will this move them?" Spend the time here. Re-read it if you need to. It pays off on every page after this one.

Setup & Your First Repo — Chapter 3

Time to get hands-on. Install Git, tell it who you are, and create your first repository — a few minutes of setup, then you have a place to practice everything in this book. Keep a throwaway repo around for the rest of the chapters.

Install & identify yourself

Install Git: on Linux it's in your package manager (sudo apt install git — Linux Field Guide); on macOS it comes with the Xcode command-line tools (xcode-select --install) or Homebrew; on Windows, download from git-scm.com (includes "Git Bash"). Verify with git --version. Then do the one-time global setup — Git stamps every commit with your name and email, so set them:

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main    # name the first branch "main"
git config --global core.editor "nano"         # or "vim", "code --wait", etc.
git config --list                               # check your settings

These live in ~/.gitconfig (Linux Field Guide). The name/email aren't verified — they're just labels on your commits — but use real ones, especially the email, so platforms like GitHub link commits to your account (Part III).

Creating a repository — two ways

A repository ("repo") is a project folder that Git is tracking — it has a hidden .git subfolder holding all the history (Chapter 2). You get one two ways:

# 1. Start fresh in a new or existing folder:
mkdir myproject && cd myproject
git init                       # turns this folder into a repo (creates .git/)

# 2. Or copy an existing repo from elsewhere (e.g. GitHub):
git clone https://github.com/user/repo.git   # covered in Ch 10

git init creates the .git directory — that hidden folder is the repository (the history, config, everything); delete it and you have plain files again. git clone downloads a full copy of a remote repo, history and all (Chapter 10). For learning now, use git init in a throwaway folder.

Checking status — your most-used command

git status tells you the current state — what's changed, what's staged, what branch you're on. You'll run it constantly; it's how you orient yourself (Chapter 2's three areas, made visible):

git status            # the command you'll run more than any other
git status -s         # short/compact format
Try it — create your practice repo 
git --version                          # confirm Git is installed
git config --global user.name "Test User"
git config --global user.email "test@example.com"
mkdir ~/git-practice && cd ~/git-practice
git init                               # initialize the repo
git status                             # "On branch main / No commits yet"
echo "# My Project" > README.md        # create a file
git status                             # README.md shows as "untracked"
ls -a                                  # notice the hidden .git folder
Keep this ~/git-practice repo — you'll use it for the next chapters.
"main" vs "master" Older Git defaulted the first branch to master; modern Git and GitHub use main. They're just names for the default branch (Chapter 5) — functionally identical. Setting init.defaultBranch main (above) keeps you consistent with today's convention and with GitHub, avoiding a small mismatch later. If you see master in older projects or tutorials, it's the same thing.
From the field — git status is your compass; run it constantly The single habit that makes Git feel calm instead of confusing is running git status all the time — before and after almost every other command. It answers the questions that cause all the anxiety: What branch am I on? What's changed? What's staged for the next commit? What's Git suggesting I do next? (Status even prints helpful hints like "use git add to stage" or "your branch is ahead by 2 commits.") Beginners get lost because they lose track of state; git status shows you the state, mapped directly onto the three areas from Chapter 2. Make it reflexive — it costs nothing, it's always safe (it changes nothing), and it keeps you grounded. When in doubt at any point in this book: git status.

The Core Loop — Chapter 4

Edit, stage, commit, repeat. This handful of commands is what you'll do thousands of times — the daily rhythm of working with Git. Master this loop and you can use Git productively; everything else builds on it.

The loop

The everyday Git cycle, mapped to the three areas (Chapter 2):

  1. Edit your files (working directory).
  2. git status — see what changed.
  3. git add — stage the changes you want in the next commit.
  4. git commit — snapshot the staged changes with a message.
  5. Repeat.
git status                     # what changed?
git add file.txt               # stage one file
git add .                      # stage everything changed
git commit -m "Add the thing"  # snapshot staged changes with a message
git log                        # see the history

Staging: add

git add moves changes from the working directory into the staging area (Chapter 2). You control exactly what goes in:

CommandStages
git add file.txtOne specific file
git add .Everything changed in the current directory & below
git add -AAll changes in the whole repo (incl. deletions)
git add -pInteractively pick parts of files (powerful for clean commits)

Committing

git commit takes everything staged and saves it as a snapshot with a message:

git commit -m "Short summary of what changed"
git commit                     # opens your editor for a longer message
git commit -am "msg"           # stage all TRACKED changes AND commit (skips add)

The commit message matters — it's the "why" your future self and teammates will read. Good convention: a concise imperative summary line (under ~50 chars), like "Fix login timeout bug" or "Add user export feature" — phrased as if completing "This commit will...". For bigger changes, a blank line then a paragraph explaining the why. (commit -am is a handy shortcut, but it only stages already-tracked files — brand-new files still need an explicit add.)

Seeing history & changes

CommandShows
git logCommit history (newest first): hash, author, date, message
git log --onelineCompact one-line-per-commit view
git log --oneline --graph --allVisual graph of all branches (Chapter 5)
git diffUnstaged changes (working dir vs staging)
git diff --stagedStaged changes (what the next commit will include)
git show HEADWhat the most recent commit changed
Try it — make your first commits 
cd ~/git-practice              # the repo from Chapter 3
git add README.md              # stage the README
git status                     # now shows it as "staged"
git commit -m "Add README"     # your first commit!
git log                        # see it in the history
echo "Some notes" > notes.txt  # make a new file
echo "More content" >> README.md   # change an existing one
git status                     # one new, one modified
git diff                       # see exactly what changed in README
git add .                      # stage both
git commit -m "Add notes and expand README"
git log --oneline              # two commits now
From the field — commit small, commit often, write real messages Three habits make Git history a help instead of a mess. Commit small, logical units — one change, one commit (the staging area, Chapter 2, exists exactly so you can group related changes and leave unrelated ones for a separate commit). A commit that says "fixed stuff" and touches 40 unrelated files is useless to future-you; ten focused commits are a readable story. Commit often — small frequent commits give you fine-grained save points to return to (Chapter 9) and make mistakes cheap to undo. Write messages for humans — explain why, not just what (the diff already shows what); "Fix race condition in payment handler" beats "update code." You're writing to your future self and your teammates, who will read these when hunting a bug six months from now. This loop — edit, status, add, commit — is 90% of daily Git; get it smooth and the rest is additions to it.

Part II — Branching & Merging

Branches — Chapter 5

Branching is Git's superpower — and once you understand it's just a movable pointer (Chapter 2), it stops being scary. Branches let you work on something in isolation without disturbing the main line, which is the foundation of all real Git workflows.

What a branch really is

Here's the demystifying truth: a branch is just a lightweight, movable pointer to a commit (Chapter 2). That's it. The default branch (main) is a pointer to the latest commit on the main line. Creating a branch creates another pointer to the same commit; as you commit on that branch, its pointer moves forward independently. Because a branch is just a 40-character pointer, creating one is instant and free — unlike older systems where branching copied everything. This cheapness is why Git workflows branch constantly.

Why branch?

  • Isolate work — build a feature or fix a bug without destabilizing the working main.
  • Experiment freely — try an idea on a branch; if it's bad, delete the branch and it's gone, with main untouched.
  • Collaborate — everyone works on their own branch and merges via pull requests (Part III).
  • Keep main deployable — main stays clean and releasable while work happens on branches.

The branch commands

CommandDoes
git branchList branches (* marks current)
git branch featureCreate a branch (doesn't switch to it)
git switch featureSwitch to a branch (modern command)
git switch -c featureCreate and switch in one step
git checkout featureOlder way to switch (still works)
git branch -d featureDelete a merged branch (-D force-delete)
git branch -m newnameRename the current branch

(git switch/git restore are the newer, clearer commands that split what the overloaded git checkout used to do; older docs and habits use checkout for both — both work.)

Try it — branch, work, switch back 
cd ~/git-practice
git branch                       # see you're on main
git switch -c feature-test       # create and switch to a new branch
echo "experimental" > experiment.txt
git add . && git commit -m "Add experiment on feature branch"
git log --oneline                # the new commit is here
git switch main                  # back to main
ls                               # experiment.txt is GONE -- it's only on the branch!
git log --oneline                # main doesn't have that commit
git switch feature-test          # switch back; experiment.txt returns
Watch how switching branches changes the files in your working directory — that "time travel" feeling is branches in action.
From the field — branch for everything, it's free Once branches click as "just a cheap pointer," you'll branch constantly — and you should. The professional norm is: never commit directly to main; make a branch for every feature, fix, or experiment, however small (Chapter 12, 16). It keeps main always clean and deployable, isolates your work so a half-finished feature never breaks the main line, and makes collaboration via pull requests (Part III) natural. The thing beginners fear — "what if I mess up the branch?" — is exactly why branches are great: a bad branch is deleted with one command and main never knew it existed. Watching experiment.txt appear and disappear as you switch branches (the Try-it box) is the moment branches stop being abstract. Branch early, branch often; it costs nothing and saves everything.

Merging — Chapter 6

Branching splits work apart; merging brings it back together. Once your feature branch is done, you merge it into main. Understanding the two kinds of merge — fast-forward and three-way — makes the history make sense and conflicts (Chapter 7) less mysterious.

The basic merge

To merge, you switch to the branch you want to merge into (usually main), then merge the other branch in:

git switch main                # go to the destination branch
git merge feature              # bring feature's commits into main
git branch -d feature          # delete the merged branch (optional cleanup)

The direction matters and trips people up: you merge from the feature branch into the branch you're currently on. So to get your feature into main: be on main, run git merge feature.

Two kinds of merge

TypeWhenResult
Fast-forwardmain hasn't changed since you branchedGit just slides main's pointer forward to the feature's tip — no merge commit, a straight line
Three-way mergeBoth main and the feature got new commits (they diverged)Git combines both lines and creates a new merge commit with two parents

Fast-forward vs merge commit — and why people care

A fast-forward keeps history as a clean straight line (no extra commit), which looks tidy but loses the information that a branch ever existed. A merge commit preserves that a feature was developed separately and merged as a unit. Teams have preferences: some like the explicit merge commits (git merge --no-ff forces one even when fast-forward is possible), others prefer linear history via rebasing (Chapter 8). There's no universally right answer; it's a project convention (Chapter 16).

Checking what's merged

git merge feature              # do the merge
git log --oneline --graph --all   # SEE the merge in the history graph
git branch --merged            # which branches are fully merged (safe to delete)
git branch --no-merged         # branches with unmerged work
Try it — make and merge a branch 
cd ~/git-practice
git switch -c add-feature         # new branch
echo "a new feature" > feature.txt
git add . && git commit -m "Add feature.txt"
git switch main                   # back to main
git merge add-feature             # merge it in (likely a fast-forward)
ls                                # feature.txt is now on main
git log --oneline --graph --all   # see the history
git branch -d add-feature         # clean up the merged branch
From the field — merge direction and "graph" are the keys Two things make merging painless. First, get the direction right: switch to the destination (main), then git merge <source> — you pull the feature into where you are. Reversing it (merging main into your feature) is sometimes intentional but usually not what beginners mean. Second, live in git log --oneline --graph --all — it draws the actual branch/merge structure as ASCII art, and seeing the graph is what makes branching and merging finally click; you watch the lines diverge and rejoin. Don't fear merges — most are clean fast-forwards or automatic three-way merges where Git figures everything out. The only time merging gets interesting is when both sides changed the same lines, which is a conflict — and conflicts are normal, not errors, and entirely manageable once you know the routine (Chapter 7).

Merge Conflicts — Chapter 7

A merge conflict sounds alarming but it's routine — it just means two branches changed the same lines, and Git needs you to decide which version wins. It is not an error or a disaster. Learn the simple routine to resolve one and conflicts stop being scary forever.

Why conflicts happen

When you merge (Chapter 6), Git combines changes automatically — unless both branches edited the same lines of the same file in different ways. Then Git can't know which version you want, so it stops and asks you. That's a conflict. It's a normal, expected part of collaboration, not a sign you did something wrong. Git pauses the merge, marks the conflicting spots in the file, and waits for you to resolve them.

What a conflict looks like

Git inserts conflict markers into the affected file, showing both versions:

Here is some shared text.
<<<<<<< HEAD
This is the version from your current branch (e.g. main).
=======
This is the version from the branch you're merging in.
>>>>>>> feature
More shared text.

Read it as three parts: between <<<<<<< HEAD and ======= is your side (the current branch); between ======= and >>>>>>> feature is their side (the branch being merged). Your job: edit this into the final version you want, and delete the marker lines.

The resolution routine

  1. See what conflicted: git status lists files "both modified."
  2. Open each conflicted file and find the markers (search for <<<<<<<).
  3. Edit to the final result — keep your side, their side, both, or a blend — and delete all three marker lines (<<<, ===, >>>).
  4. Stage the resolved file: git add file (this tells Git "I've resolved this one").
  5. Complete the merge: git commit (Git pre-fills a merge message).
git merge feature              # CONFLICT! Git pauses
git status                     # see which files conflict
# ...edit each file: pick the right content, remove the <<< === >>> markers...
git add conflicted-file.txt    # mark it resolved
git commit                     # finish the merge
# changed your mind mid-merge? bail out completely:
git merge --abort              # undo the whole merge, back to before it started

Tools that help

You don't have to edit markers by hand. VS Code and most editors show conflicts with clickable "Accept Current / Accept Incoming / Accept Both" buttons. git mergetool launches a configured visual merge tool. And the safety valve worth memorizing: git merge --abort throws away the in-progress merge and returns you to exactly where you were before — so you can always back out and try again calmly.

Try it — create and resolve a conflict on purpose 
cd ~/git-practice
echo "line one" > conflict.txt
git add . && git commit -m "Add conflict.txt"
git switch -c branch-a
echo "version from A" > conflict.txt   # change the line on branch A
git commit -am "A's version"
git switch main
echo "version from main" > conflict.txt # change the SAME line on main
git commit -am "main's version"
git merge branch-a               # CONFLICT!
git status                       # see "both modified"
cat conflict.txt                 # see the <<< === >>> markers
nano conflict.txt                # edit to the final version, delete the markers
git add conflict.txt
git commit                       # finish -- conflict resolved!
Doing this once, deliberately, removes the fear entirely.
From the field — conflicts are normal; the routine is always the same New users panic at their first conflict like something broke. Nothing broke — Git is doing exactly the right thing: when it can't safely guess, it asks you, the human who knows which version is correct. The routine never changes: git status to see the conflicts, open each file and edit the marked sections into what you actually want (removing the <<</===/>>> lines), git add each resolved file, then git commit. And remember the escape hatch — git merge --abort — so you always know you can back out and nothing is permanent until you commit. Two habits reduce how often you hit conflicts: pull/merge frequently (small, frequent integrations conflict less than giant ones — Chapter 10), and keep branches short-lived (Chapter 16). Resolve a conflict deliberately once in your practice repo and you'll never fear them again.

Rebasing — Chapter 8

Rebasing is the other way to combine branches — instead of joining histories with a merge commit, it *replays* your commits on top of another branch, producing a clean, linear history. It's powerful and a little dangerous, and it comes with one golden rule you must never break.

Rebase vs merge — the same goal, different shape

Both merge (Chapter 6) and rebase integrate one branch's work with another's. The difference is the result:

MergeRebase
HowJoins the two histories with a merge commitRe-applies your commits one-by-one on top of the target
History shapePreserves the branching (a graph with merge commits)Linear, as if you'd worked on top of the latest all along
Rewrites commits?No (keeps original commits)Yes — creates new commits with new IDs
Best forPreserving exactly what happened; shared branchesClean history; tidying your own work before sharing

The basic rebase

git switch feature
git rebase main                # replay feature's commits on top of latest main
# now feature looks like it was built on current main, linearly
# then a fast-forward merge into main gives a clean straight history:
git switch main && git merge feature

The mental picture: rebase lifts your branch's commits off where they were, updates the base to the tip of main, and re-plays your commits there — giving new commits (new IDs) sitting in a clean line on top of main. If a replayed commit conflicts, you resolve it (Chapter 7) and run git rebase --continue; git rebase --abort bails out.

Interactive rebase — cleaning up your commits

The genuinely loved feature: git rebase -i lets you rewrite a series of your own, unpushed commits before sharing them — squash several messy "wip" commits into one clean commit, reword messages, reorder, or drop commits:

git rebase -i HEAD~4            # interactively edit the last 4 commits
# an editor opens listing them; change "pick" to:
#   squash (s) -- fold into the previous commit
#   reword (r) -- change the message
#   drop   (d) -- remove the commit
#   edit   (e) -- pause to amend it
# save, and Git replays them with your changes

This turns a messy work-in-progress branch ("wip", "fix typo", "actually fix it", "ok now it works") into one or two clean, meaningful commits before anyone else sees them — great hygiene for pull requests (Chapter 13).

The golden rule: never rebase shared history Because rebase rewrites commits (new IDs replace old ones), it must only be used on commits that are still private to you — commits you haven't pushed, or a branch nobody else has based work on. Never rebase commits that others have already pulled (especially never rebase main or any shared branch). If you do, everyone else's history diverges from yours, you'll be tempted to push --force over their work, and you create a painful mess for the whole team. The rule, memorized: rebase your own un-shared work to tidy it; merge everything else. When in doubt, merge — merge is always safe; rebase is only safe on private commits.
Try it — rebase and squash (in your practice repo) 
cd ~/git-practice
git switch -c tidy-me
echo "1" > a.txt; git add . && git commit -m "wip"
echo "2" >> a.txt; git commit -am "more wip"
echo "3" >> a.txt; git commit -am "fix typo"
git log --oneline                # three messy commits
git rebase -i HEAD~3             # change the 2nd and 3rd "pick" to "squash", save
# (an editor opens for the combined message; save it)
git log --oneline                # now ONE clean commit -- but only do this BEFORE pushing!
From the field — rebase to polish your own work, merge to integrate Here's the practical way to think about it: rebase is for tidying your own private commits; merge is for combining shared work. The two everyday uses of rebase are (1) git rebase main on your feature branch to get the latest changes and keep history linear, and (2) git rebase -i to squash your messy work-in-progress commits into clean ones before opening a pull request (Chapter 13) — reviewers see a tidy story instead of "wip, wip, oops, fix." Both operate on your unshared commits, which is safe. The moment commits are shared, switch to merge. If rebasing ever feels confusing or risky, just merge instead — you'll get a slightly messier graph but never a disaster. Many teams happily never use anything fancier than merge. Rebase is a sharp, useful tool; the golden rule (above) is what keeps it from cutting you.

Undoing Things — Chapter 9

The chapter that removes the fear. Git's reputation for being scary comes entirely from "what if I did the wrong thing?" — so here's how to undo basically anything. Once you know you can always recover, you'll use Git boldly instead of timidly.

Match the undo to the situation

The confusing part is that there are several "undo" commands for different situations. The key question is always: which of the three areas (Chapter 2) is the thing I want to undo in?

I want to…Command
Discard un-staged changes to a file (revert it to last commit)git restore file
Unstage a file (keep the edits, just remove from staging)git restore --staged file
Fix the last commit's message or add a forgotten file to itgit commit --amend
Undo recent commits but keep the changes (to redo/re-commit)git reset --soft HEAD~1
Undo recent commits and discard the changes entirelygit reset --hard HEAD~1 (careful!)
Undo a commit by making a new commit that reverses it (safe on shared history)git revert <commit>
Recover something you think you lostgit reflog (below)

restore — for working-directory and staging

git restore file.txt           # throw away unstaged edits to file (back to last commit)
git restore .                  # discard ALL unstaged changes (careful)
git restore --staged file.txt  # unstage (move from staging back to working dir; edits kept)

restore handles the everyday "I messed up this file, put it back" and "oops, I staged the wrong thing." Note git restore file (without --staged) discards your edits — that part isn't recoverable via reflog since it was never committed, so be sure.

reset — moving the branch pointer

reset moves your branch pointer (and HEAD) to an earlier commit (Chapter 2). The three modes differ in what they do to your changes:

ModeMoves pointer?Your changes?
--softYesKept, and left staged (ready to re-commit)
--mixed (default)YesKept, but unstaged
--hardYesDiscarded — gone from working dir too

Common use: git reset --soft HEAD~1 "uncommits" the last commit while keeping all its changes staged — perfect for "I committed too early / want to redo that commit." --hard is the one to respect: it throws away changes.

revert — the safe undo for shared history

git revert <commit> doesn't rewrite history — it creates a new commit that undoes the changes of an old one. Because it adds rather than rewrites, it's safe to use on commits you've already pushed/shared (unlike reset/rebase — Chapter 8). This is how you undo a bad commit that's already on a shared branch like main.

reflog — the ultimate safety net

Here's the reassuring secret: git reflog records (almost) every move HEAD makes — every commit, switch, reset, rebase — for weeks. So even after a "disastrous" reset --hard, the old commit is still findable in the reflog, and you can return to it:

git reflog                     # a timeline of everywhere HEAD has been
# find the commit you want (e.g. abc1234), then:
git reset --hard abc1234       # jump back to it -- recovered!
# or make a branch from it:
git branch recovered abc1234

This is why committed work is almost never truly lost in Git. If you commit regularly (Chapter 4), the reflog is your time machine.

Try it — break and recover (fearlessly) 
cd ~/git-practice
echo "important work" > valuable.txt
git add . && git commit -m "Add valuable work"
git log --oneline                # note the commit
git reset --hard HEAD~1          # "oops" -- uncommit and discard
ls                               # valuable.txt is gone!
git reflog                       # find the "Add valuable work" commit's hash
git reset --hard <that-hash>     # bring it ALL back
ls                               # valuable.txt returns -- nothing was truly lost
Doing this once proves to yourself that Git has your back.
From the field — committed work is safe, so be bold The biggest unlock in this whole book: once something is committed, it's extremely hard to actually lose. The reflog remembers nearly everything for weeks, so almost every "I destroyed my work" panic is recoverable with git reflog + git reset --hard <hash>. This changes how you should use Git: commit often (each commit is a recovery point), then experiment, rebase, reset, and rearrange boldly, knowing you can get back. The two things that genuinely aren't protected: changes you never committed (a restore or reset --hard over uncommitted edits is unrecoverable), and rewriting shared history (Chapter 8's golden rule). So: commit your work before doing anything risky, prefer revert for undoing shared commits, and keep reflog in your back pocket as the universal "get me out of this" tool. Knowing recovery is almost always possible is exactly what turns Git from terrifying into trustworthy.

Part III — Remotes & GitHub

Remotes — Chapter 10

So far everything has been local. Remotes connect your repository to a copy elsewhere — usually GitHub — so you can back up your work, access it anywhere, and collaborate. Four commands (clone, push, pull, fetch) cover almost everything.

What a remote is

A remote is a version of your repository hosted somewhere else (GitHub, GitLab, a server). Because Git is distributed (Chapter 1), each copy is a full repository with complete history — the remote isn't "the real one" and yours a mere checkout; they're peers that you keep in sync. The conventional name for your main remote is origin. The flow:

The four commands

CommandDoes
git clone URLDownload a full copy of a remote repo (history and all) — how you start from an existing repo
git pushUpload your local commits to the remote
git pullDownload and merge remote commits into your branch (= fetch + merge)
git fetchDownload remote commits but don't merge yet (look before you leap)

Connecting a local repo to a remote

If you started locally with git init (Chapter 3), you link it to a remote you created on GitHub (Chapter 11):

git remote add origin https://github.com/you/repo.git   # link the remote
git remote -v                                            # verify it
git push -u origin main          # first push (-u sets the default upstream)
# after that, just:
git push                         # subsequent pushes
git pull                         # get others' changes

The -u on the first push sets up tracking so future git push/git pull know where to go without arguments. (If you cloned, the remote and tracking are already set up for you.)

pull vs fetch — the useful distinction

git pull is convenient (fetch + merge in one) but it merges immediately, which can surprise you with conflicts (Chapter 7) or unexpected merges. git fetch downloads the remote's new commits without changing your working branch, so you can inspect them (git log origin/main) before deciding to merge or rebase. Beginners use pull; as you mature you may prefer fetch then a deliberate merge/rebase, especially on shared branches.

Try it — push to GitHub (after Chapter 11 setup) or simulate locally 
# If you have a GitHub repo ready (Ch 11) and auth set up (Ch 15):
cd ~/git-practice
git remote add origin https://github.com/YOU/git-practice.git
git push -u origin main          # upload your history
# later, the everyday rhythm:
git pull                         # get any remote changes first
# ...do work, commit...
git push                         # share your work
The daily habit: pull before you start, push when you're done.
From the field — pull before you push, and push often Two rhythms make remote work smooth. Pull before you start working (and before you push) — get everyone else's latest changes first, so you're building on current work and resolving any small conflicts early rather than discovering a giant one later. Push often — pushing is also your off-machine backup; commits sitting only on your laptop are one spilled coffee from gone. The classic beginner failure is working in isolation for days, then trying to push a mountain of changes onto a main that moved on without them — a conflict nightmare. Small, frequent pull/push cycles keep you in sync and keep integrations tiny. And when a push is rejected with "updates were rejected" / "fetch first," it just means the remote has commits you don't — git pull to integrate them, then push again. That's normal collaboration, not an error.

GitHub takes Git's repositories and wraps them in a platform: hosting, a web interface, collaboration tools, automation, and a social layer that hosts most of the world's open-source software. This chapter is the tour — what GitHub adds on top of Git, and how to create and navigate a repo there.

Anatomy of a GitHub repository

Open any repo on github.com and you'll find a consistent layout worth knowing: the code tab (files + the rendered README.md as the landing page), commit history, branches dropdown, Issues and Pull Requests tabs, Actions (CI runs), Insights (stats), and Settings. The green "Code" button gives you the clone URL (HTTPS or SSH — Chapter 15). A good README.md is the front door — it's the first thing visitors (and future-you) read.

Creating a repo & the gh CLI

Two ways to make a GitHub repo:

# 1. On the website: click "New repository", name it, choose public/private,
#    optionally add a README/.gitignore/license, then clone or link it (Ch 10).

# 2. From the terminal with the GitHub CLI (gh) -- fast once set up (Ch 15):

The gh CLI is GitHub's official command-line tool — it lets you create repos, open and review pull requests, manage issues, and more without leaving the terminal. It's a big productivity win once you're comfortable (and how this very book's repos were created).

README, license, and the basics of a good repo

  • README.md — written in Markdown; explains what the project is, how to install/use it, and how to contribute. The single most important file for humans.
  • LICENSE — tells others what they're legally allowed to do with your code (MIT and Apache-2.0 are common permissive choices). No license = "all rights reserved", so add one if you want others to use it.
  • .gitignore — keeps junk (build files, secrets, dependencies) out of the repo (Chapter 17).
From the field — GitHub is where your work becomes visible For most people GitHub is two things: a backup-and-access service (your work is safe in the cloud and reachable from any machine) and a collaboration hub (pull requests, issues, review — Part III). But there's a third, career-relevant angle worth knowing early: GitHub is also a portfolio. Your public repos and contribution history are visible to anyone, and they're increasingly part of how technical people are evaluated — a tidy repo with a clear README and clean commit history (Chapter 4) says a lot about how you work. So treat even small personal projects with a little care: write a real README, add a license if it's public, keep commits meaningful. You don't need to be an open-source star; just having clean, public work demonstrates competence. Start by pushing your practice projects there — and learn the gh CLI, which makes the whole GitHub workflow as fast as the local one.

The Collaboration Workflow — Chapter 12

Everything so far comes together here: the standard workflow that teams and open-source projects use to work on the same codebase without chaos. Branch, push, pull request, review, merge — this loop is how modern software actually gets built.

The two collaboration models

There are two common setups, depending on whether you have write access to the repo:

ModelWhenHow
Shared repositoryYou're on the team (have write access)Branch directly in the repo, push your branch, open a PR
Fork & pullContributing to a project you don't own (open source)Fork the repo to your account, work there, open a PR back to the original

A fork is your own server-side copy of someone else's repo — it lets you make changes freely (you have full control of your fork) and then propose them back to the original via a pull request. The original maintainer reviews and decides whether to merge. This is how open source works: thousands of strangers contribute to projects they don't control, safely.

The standard feature workflow (shared repo)

The loop you'll run constantly on a team:

git switch main && git pull        # 1. start from the latest main
git switch -c feature-x            # 2. branch for your work (Ch 5)
# ...edit, git add, git commit... (Ch 4) -- as many commits as you like
git push -u origin feature-x       # 3. push your branch to GitHub
# 4. open a Pull Request on GitHub (feature-x → main)  (Ch 13)
# 5. teammates review; you address feedback with more commits + push
# 6. PR approved → merge it on GitHub
git switch main && git pull        # 7. update local main with the merged work
git branch -d feature-x            # 8. delete the finished branch

That eight-step cycle — pull, branch, work, push, PR, review, merge, clean up — is the heartbeat of professional Git. Notice you never commit directly to main; all changes arrive via reviewed pull requests (Chapter 16).

The fork & pull workflow (open source)

git clone https://github.com/YOU/their-repo.git   # clone YOUR fork (after forking on GitHub)
cd their-repo
git remote add upstream https://github.com/ORIGINAL/their-repo.git  # link the original
git switch -c fix-typo             # branch
# ...make your change, commit...
git push origin fix-typo           # push to YOUR fork
# open a PR from your fork's branch to the original repo (Ch 13)
# keep your fork current later:
git fetch upstream && git merge upstream/main

The extra piece here is upstream — a second remote pointing at the original repo, so you can pull in its updates (origin is your fork, upstream is the source). This is contributing to open source in a nutshell (Chapter 19).

Try it — the workflow on your own repo 
cd ~/git-practice                  # (with a GitHub remote set up, Ch 10/15)
git switch main && git pull
git switch -c add-greeting          # branch
echo "Hello, collaborators" > greeting.txt
git add . && git commit -m "Add greeting"
git push -u origin add-greeting     # push the branch
# now open github.com, you'll see a prompt to open a Pull Request (Ch 13)
# merge it on the site, then:
git switch main && git pull         # bring the merge down
git branch -d add-greeting          # clean up
From the field — the workflow is the actual job Beginners think learning Git means learning commands; on a team, it really means learning this workflow — and it's remarkably consistent across nearly every company and project. Internalize the cycle (pull latest, branch, commit, push, open PR, get reviewed, merge, clean up) and you can drop into almost any team and be productive immediately, because they all work roughly this way (Chapter 16). Two rules underpin it: never work directly on main (always branch — Chapter 5), and changes get reviewed before merging (via PRs — Chapter 13). For open source, the fork-and-pull variant lets you contribute to projects you don't own — which is both how the software commons gets built and a great way to build a public track record (Chapter 19). The commands you already know; this chapter is how they assemble into how real software gets made.

Pull Requests & Code Review — Chapter 13

The pull request is GitHub's central feature and the heart of team collaboration: a proposal to merge your branch, opened up for discussion and review before it lands. Learning to open good PRs and give good reviews is as much a professional skill as writing the code.

What a pull request is

A pull request (PR) says: "here are the commits on my branch; please review them and, if they're good, merge them into the target branch." It's not a Git feature — it's a GitHub (platform) feature built on top of branches. A PR bundles: the diff (all changes), a description (what and why), a conversation (review comments, discussion), checks (automated tests via CI — Chapter 18), and the merge button. It turns "merging code" from a silent act into a reviewable, discussable, documented event. (GitLab calls them "merge requests" — same thing.)

Opening a good PR

After you push a branch (Chapter 12), GitHub prompts you to open a PR. A good one:

  • Has a clear title and description — what changed and why; link related issues (Chapter 14) with "Closes #42" so they auto-close on merge.
  • Is small and focused — one logical change. Reviewers do a careful job on a 50-line PR and a rubber-stamp on a 2,000-line one.
  • Has clean commits — tidy your branch first if needed (rebase -i — Chapter 8).
  • Passes its checks — green CI before asking for review.
# open a PR from the terminal with the gh CLI (Ch 15):
gh pr create --title "Add login timeout" --body "Fixes the hang described in #42"
gh pr status            # PRs involving you
gh pr view --web        # open it in the browser
gh pr checkout 123      # check out someone else's PR locally to test it

The review

Reviewers read the diff and leave feedback: line comments (on specific lines), an overall review with a verdict — Approve, Request changes, or Comment — and suggestions you can sometimes apply with one click. You respond by pushing more commits to the same branch (they appear in the PR automatically) and replying to comments. Once approved (and checks pass), someone clicks Merge. GitHub offers merge styles: a regular merge commit, squash and merge (combine all PR commits into one — popular for clean history), or rebase and merge (Chapter 16).

Giving good reviews

Reviewing is a skill: be kind and specific (comment on the code, not the person; explain why), distinguish must-fix from nitpick (prefix optional comments with "nit:"), ask questions rather than demand ("could this be null here?"), and approve generously when it's good enough — perfect is the enemy of shipped. A review is a conversation to improve the code together, not a gate to prove superiority.

From the field — small PRs and kind reviews make teams fast Two truths about PRs that take people years to learn. First, small PRs get better reviews and merge faster. A focused 50-line change gets genuine scrutiny and a quick approval; a sprawling 2,000-line PR gets a glance and a reluctant "LGTM" because no human can review it well — so bugs slip through and it sits for days. Keep PRs small and single-purpose, even if it means splitting your work into several (Chapter 12). Second, code review is about the code, never the person. The best teams review warmly — specific, curious, generous — and it makes everyone better and the codebase stronger; toxic nitpicky review just makes people defensive and slow. Whether you're opening PRs or reviewing them, you're participating in the core ritual of professional software, and doing it well (small, clear, kind) marks you as someone good to work with — which matters as much as the code itself.

Issues & Project Management — Chapter 14

GitHub isn't just code — it's where the work *around* the code gets organized. Issues track bugs and tasks, labels and milestones organize them, and Projects turn them into boards. This is how teams (and solo developers) plan and coordinate.

Issues — the unit of work

An issue is a tracked item: a bug report, a feature request, a task, or a discussion. Each has a title, a description (Markdown), a number (#42), a status (open/closed), and a conversation thread. Issues are how a project says "here's what needs doing and what's wrong." Good practice: one issue per discrete problem or task, with a clear title and enough detail to act on (for bugs: steps to reproduce, expected vs actual).

Issues + commits + PRs: the magic links

The pieces connect, which is what makes GitHub a project tool and not just a tracker. Reference an issue from a commit or PR with #number, and use closing keywords to auto-close it on merge:

git commit -m "Fix null check in parser (refs #42)"   # links to issue 42
# in a PR description or commit:  "Closes #42"  /  "Fixes #42"  /  "Resolves #42"
# → when that PR merges, issue #42 closes automatically and links the PR to it

So the lifecycle ties together: file an issue → create a branch to fix it → open a PR that says "Closes #42" → review and merge → the issue closes itself, with a permanent trail linking the bug, the discussion, the code change, and the merge. That traceability is gold months later when someone asks "why was this changed?"

Projects, Discussions, Wikis

  • Projects — Kanban-style boards (Todo / In Progress / Done) and tables built from your issues and PRs, for planning and tracking work visually. The lightweight project-management layer.
  • Discussions — forum-style threads for Q&A and open-ended conversation that aren't actionable "issues."
  • Wiki — longer-form documentation living alongside the repo.
  • Milestones — bundle issues/PRs toward a version or date and track progress.

gh issue view 42

From the field — issues turn "stuff in my head" into shared, trackable work Even solo, issues are worth using: they're where you offload "things to do / things that are broken" so they're not rattling around your head or lost in a notes file — and your future self gets a clear, prioritized list. On a team they're essential: issues are the shared source of truth for what the work is, while PRs (Chapter 13) are how it gets done, and the #number links weave them into a traceable history. The habit that pays off most: connect everything — reference the issue in your branch name and PR, use "Closes #N" so merging a fix closes the bug automatically. Six months later when someone asks "why does this code do X?", the trail — issue → discussion → PR → merge — answers it instantly. And for getting into open source (Chapter 19), the good first issue label is your on-ramp: maintainers tag beginner-friendly tasks there specifically to welcome new contributors.

Authentication — Chapter 15

"Why does GitHub keep rejecting my password?" is the first wall almost everyone hits. GitHub stopped accepting passwords for Git operations years ago — you authenticate with SSH keys, a personal access token, or the gh CLI. Here's how to set it up once and never think about it again.

Why your password doesn't work

Since 2021, GitHub no longer accepts your account password for Git operations over HTTPS (it was insecure and phishable). Instead you use one of three modern methods. Pick one, set it up once, done:

MethodBest for
SSH keysThe classic developer choice — set up once, no tokens to manage
Personal Access Token (PAT)HTTPS users; also for scripts/CI — a token used instead of a password
gh CLI / Git Credential ManagerEasiest — handles auth for you

Option 1: SSH keys (recommended)

The same key-pair system from the Linux Field Guide: a private key stays on your machine, the public key goes on GitHub, and they prove your identity with no password typed:

ssh-keygen -t ed25519 -C "you@example.com"   # generate a key pair (Enter for defaults)
cat ~/.ssh/id_ed25519.pub                    # copy this PUBLIC key
# paste it on GitHub: Settings → SSH and GPG keys → New SSH key
ssh -T git@github.com                        # test it ("Hi USER! ...")
# then use SSH clone URLs:
git clone git@github.com:user/repo.git       # note: git@github.com, not https://

Use the SSH URL (git@github.com:...) for repos, not the HTTPS one, and your private key authenticates automatically. The one gotcha from the Linux guide applies: SSH needs tight permissions — ~/.ssh at 700, the private key at 600 — or it silently ignores the key.

Option 2: Personal Access Token (PAT)

If you prefer HTTPS, generate a token on GitHub (Settings → Developer settings → Personal access tokens) and use it as your password when Git prompts:

git clone https://github.com/user/repo.git
# Username: your-username
# Password: PASTE THE TOKEN (not your account password)

Use fine-grained tokens scoped to only the repos and permissions needed, and set an expiry. Tokens are also how scripts and CI authenticate (Chapter 18). Treat a token like a password — it's a secret (Chapter 20).

Option 3: gh CLI / credential helper (easiest)

gh auth login            # walks you through it; sets up Git auth automatically
# or let Git remember an HTTPS token via the OS credential store:
git config --global credential.helper store     # (or "manager" on Windows/Mac)

The gh CLI (Chapter 11) is the simplest path: gh auth login handles everything, including configuring Git to use its credentials, so git push/pull just work. The Git Credential Manager (bundled with Git for Windows/macOS) caches your token securely so you enter it once.

Never commit secrets — tokens, keys, passwords A token or SSH private key is a credential to your account — guard it like a password. The classic, costly mistake: accidentally committing a secret (a token, an API key, a password in a config file) and pushing it to a public repo, where bots scrape it within minutes. If it happens: revoke the secret immediately (it's compromised the instant it's pushed — removing it from history isn't enough), then rotate it. Prevent it with .gitignore for secret files (Chapter 17), never hard-coding secrets, and GitHub's secret-scanning/push-protection (Chapter 20). Your private SSH key (id_ed25519) must never leave your machine — only ever share the .pub.
From the field — set up SSH once, then forget about auth The authentication wall frustrates every beginner ("my password doesn't work!"), but it's a one-time setup. The advice: set up SSH keys (or run gh auth login) once, and you'll never type a credential for Git again — pushes and pulls just work. If a key "isn't working," check permissions first (Linux Field Guide's gotcha: ~/.ssh = 700, key = 600). The same SSH key works across GitHub, GitLab, and most cloud platforms, so the setup pays off everywhere. For automation and CI (Chapter 18), use scoped, expiring tokens rather than your personal credentials. And burn this in: secrets never go in commits — the single most common way people get compromised on GitHub is pushing a key or token to a public repo, where it's harvested almost instantly. Set auth up properly once, keep secrets out of Git, and authentication becomes invisible.

Part IV — Collaboration at Scale

Branching Strategies — Chapter 16

Once a team shares a repo, you need agreed rules for how branches are used — a "branching strategy." It's less about Git mechanics and more about team convention. Knowing the common models lets you fit into any team's workflow quickly.

Why a strategy matters

Git lets you branch however you like, but a team needs everyone branching the same way, or chaos ensues — people stepping on each other, unclear what's deployable, messy history. A branching strategy answers: What's main for? Where does new work go? How does it get released? Teams pick a convention and stick to it. Here are the common ones, simplest first.

GitHub Flow — simple and the most common

The dominant model for most teams and continuous deployment. The rules are minimal:

  • main is always deployable — it always works and can ship at any time.
  • Branch off main for every change (feature/fix), with a descriptive name.
  • Open a PR, get it reviewed, ensure CI passes (Chapter 13, 18).
  • Merge to main and deploy. Delete the branch.

That's it — short-lived branches, frequent merges, main always green. If you learn one model, learn this; it's what this whole book's workflow (Chapter 12) has been teaching.

The other models you'll meet

ModelShapeWhen
GitHub Flowmain + short feature branchesMost teams; web apps; continuous deployment
Git Flowmain + develop + feature/release/hotfix branchesScheduled releases, versioned software; heavier — falling out of favor
Trunk-basedEveryone commits to main very frequently (tiny branches or direct, behind feature flags)High-velocity teams with strong CI
Environment branchesmain + staging + production branchesDeploy-by-branch setups

Git Flow (a more elaborate model with long-lived develop and release branches) was popular for versioned/desktop software but is heavy for modern web development; you'll still encounter it. Trunk-based goes the other way — minimal branching, integrate constantly, hide unfinished work behind feature flags — favored by teams with excellent automated testing.

Naming & protection conventions

  • Branch names: descriptive, often prefixed — feature/login-timeout, fix/null-parser, chore/update-deps. Some teams include the issue number (feature/42-login).
  • Protected branches: GitHub can enforce the strategy — require PRs and reviews before merging to main, require CI to pass, block force-pushes. This turns convention into a guarantee (Chapter 20).
  • Merge style: teams pick one — squash-merge (clean, one commit per PR), merge commit (preserves branch structure), or rebase-merge (linear) (Chapter 6, 8).
From the field — learn GitHub Flow, then adapt to the team Don't overthink branching strategies. For the vast majority of work — personal projects, startups, web apps, open source — GitHub Flow is the answer: main always works, branch for each change, PR + review, merge, deploy, repeat. It's simple, it scales surprisingly far, and it's what this book has been teaching all along (Chapter 12). The reason to know the others is that when you join a team, they'll have their convention — maybe Git Flow at an enterprise with quarterly releases, maybe trunk-based at a high-velocity shop — and you'll want to recognize it and fit in fast rather than impose your own. The mechanics are identical (it's all branches, PRs, and merges from earlier chapters); the strategy is just the team's agreement about how to use them. Ask "what's our branching model and merge style?" on day one of any new team, follow it, and you'll slot in smoothly. And on your own repos, keep it simple: GitHub Flow, protected main, done.

.gitignore & Git LFS — Chapter 17

Not everything belongs in version control. .gitignore keeps junk and secrets out of your repo, and Git LFS handles the large binary files Git was never designed for. Getting these right keeps repos clean, small, and safe.

.gitignore — what to leave out

A repo should contain your source — the things you write — not generated, downloaded, or secret files. .gitignore is a file listing patterns Git should ignore (never track). What to ignore:

The "already tracked" gotcha

.gitignore only ignores files Git isn't already tracking. If you committed node_modules/ before adding it to .gitignore, it stays tracked. To fix, stop tracking it (while keeping it on disk) then commit:

git rm -r --cached node_modules/    # untrack but keep the files locally
echo "node_modules/" >> .gitignore
git commit -m "Stop tracking node_modules"

Git LFS — for large binary files

Git was built for text — it diffs and stores text changes brilliantly, but it handles large binary files (videos, datasets, big images, design files, game assets) badly: every version of a 100 MB file bloats the repo permanently, and binaries don't diff. Git Large File Storage (LFS) solves this by storing big files outside the normal repo and keeping just a small pointer in Git:

git lfs install                # one-time setup
git lfs track "*.psd"          # tell LFS to handle these (writes to .gitattributes)
git lfs track "*.mp4"
git add .gitattributes
git add design.psd && git commit -m "Add design file via LFS"

Now the big file is stored in LFS; the repo stays lean. (GitHub provides LFS storage with quotas.) Use it whenever a project must version large binaries. The related .gitattributes file also controls things like line-ending normalization — useful on cross-platform teams.

From the field — set up .gitignore first, and keep binaries out (or in LFS) Two habits keep repos healthy. Add a .gitignore before your first commit — start from GitHub's language template — so you never accidentally track node_modules, build output, or a .env full of secrets. The "I committed it before ignoring it" cleanup (above) is annoying and, for secrets, dangerous (Chapter 20) — far better to ignore from the start. And keep big binaries out of plain Git. A repo that's slow to clone is almost always one where someone committed large files (or a node_modules), bloating the history permanently — even deleting the file later doesn't shrink the repo, because every past version is still stored. If a project genuinely needs to version large assets, use LFS from the start. Lean repos clone fast, stay cheap, and don't leak secrets — and it all starts with a good .gitignore on day one.

GitHub Actions (CI/CD) — Chapter 18

GitHub Actions automates work that happens around your code: run tests on every push, check formatting, build, and deploy — automatically. It's GitHub's built-in CI/CD, and a basic understanding turns "I hope it works" into "the robots checked it."

What CI/CD means

CI (Continuous Integration) = automatically build and test your code every time it changes, so problems are caught immediately rather than days later. CD (Continuous Delivery/Deployment) = automatically ship the tested code to staging or production. GitHub Actions is the engine that runs these workflows for you, triggered by events in your repo (a push, a PR, a schedule). The payoff: every change is automatically verified, and the green/red check on a PR (Chapter 13) tells reviewers at a glance whether it's safe.

How Actions is structured

A simple workflow

Drop a YAML file in .github/workflows/ and GitHub runs it automatically. This one runs tests on every push and PR:

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]          # triggers
jobs:
  test:
    runs-on: ubuntu-latest         # a fresh Linux VM (Linux Field Guide!)
    steps:
      - uses: actions/checkout@v4         # get your code
      - uses: actions/setup-node@v4       # install Node (or setup-python, etc.)
        with:
          node-version: '20'
      - run: npm install                  # your commands...
      - run: npm test                     # ...run the tests

Commit that, push, and the Actions tab shows it running; the result becomes a check on your commits and PRs. The marketplace has thousands of prebuilt Actions (uses:) so you rarely script from scratch — checkout, language setup, linting, deploys, releases.

What teams automate

  • Run the test suite on every push/PR — the most common use; catches breakage instantly.
  • Lint & format checks — enforce code style automatically.
  • Build the app/artifacts and store them.
  • Deploy to staging/production on merge to main (CD).
  • Security scans — dependency and secret scanning (Chapter 20).
  • Scheduled jobs — nightly tasks, dependency updates.
Secrets in Actions, and runner safety Workflows often need credentials (to deploy, to push to a registry). Never hard-code these in the YAML — the file is in your repo. Use GitHub's encrypted repository secrets (Settings → Secrets) and reference them as ${{ secrets.MY_TOKEN }} (Chapter 20). Two more cautions: be careful enabling Actions on untrusted PRs (a fork's workflow could try to steal secrets — GitHub has protections, but know the risk), and pin third-party Actions to a specific version/SHA rather than a moving tag, since you're running someone else's code in your pipeline.
From the field — even one CI workflow changes everything You don't need to be a DevOps expert to benefit from Actions — a single "run the tests on every push" workflow is transformative. Suddenly every change is automatically checked, broken code can't quietly slip into main, and the green check on a PR (Chapter 13) gives everyone confidence to merge. It also catches the eternal "works on my machine" problem, because the tests run on a clean VM, not your customized setup. Start tiny: add a workflow that just runs your test command, watch it go green on the Actions tab, then grow it (linting, build, eventually deploy) as you need. The barrier is low — copy a starter workflow for your language, commit it, done — and the payoff is huge: automated verification is one of the biggest quality multipliers in software, and it's built right into GitHub. Combine it with protected branches (require checks to pass before merge — Chapter 16, 20) and you've got a real safety net.

Open Source — Chapter 19

GitHub is where open source lives, and contributing to it is one of the best ways to learn, build a public reputation, and give back. It's also less intimidating than it looks — your first contribution can be fixing a typo. This chapter is how to participate, as a contributor and eventually a maintainer.

What open source is (and the license point)

Open source software has source code anyone can read, use, modify, and share, under a license that grants those rights (Chapter 11). Common licenses: MIT / Apache-2.0 / BSD (permissive — do almost anything, just keep the notice) and GPL (copyleft — derivatives must also be open). The license matters: no license means "all rights reserved" — you can look but legally can't reuse it. Add a license to your own projects if you want others to use them, and check a project's license before depending on it.

Contributing — the fork & pull workflow

You contribute to a project you don't own via fork-and-pull (Chapter 12):

  1. Find something to do — look for the good first issue or help wanted labels (Chapter 14); maintainers tag beginner-friendly tasks there on purpose.
  2. Read CONTRIBUTING.md — many projects document how they want contributions (style, tests, PR format). Follow it.
  3. Fork the repo, clone your fork, branch for the change.
  4. Make the change, commit with a clear message (Chapter 4), push to your fork.
  5. Open a PR to the original repo, describing what and why (Chapter 13); link the issue with "Closes #N".
  6. Respond to review graciously — maintainers may ask for changes; push more commits to update the PR.
# after forking on GitHub:
git clone git@github.com:YOU/project.git && cd project
git remote add upstream git@github.com:ORIGINAL/project.git   # track the source
git switch -c fix-readme-typo
# ...make the change, commit...
git push origin fix-readme-typo
# open the PR on GitHub; later keep your fork fresh:
git fetch upstream && git switch main && git merge upstream/main

Your first contribution can be tiny

Open source has a reputation for being intimidating — but the on-ramp is gentle. Documentation fixes count: a typo, a broken link, a clearer sentence in the README, a missing setup step. These are real, welcomed contributions and a perfect first PR — you learn the whole workflow (fork → branch → PR → review → merge) on something low-stakes. From there, work up to small bug fixes, then features. Every prolific open-source contributor started with a first nervous PR.

Becoming a maintainer

The other side: running a project others contribute to. A welcoming, well-run repo has a clear README (what/why/how), CONTRIBUTING.md (how to help), a LICENSE, a CODE_OF_CONDUCT, issue/PR templates (Chapter 14), and CI that checks PRs automatically (Chapter 18). As a maintainer you review PRs kindly (Chapter 13), tag good first issues to invite newcomers, and remember contributors are volunteers giving you their time — gratitude and responsiveness keep a community alive.

From the field — contributing is the best way to learn, and a real portfolio Open source gives you three things at once that are hard to get otherwise. You learn from real codebases — reading and modifying production code written by experienced people teaches more than any tutorial. You build a public track record — merged PRs on real projects are visible proof of skill that employers genuinely value (Chapter 11), far more than a private repo of toy projects. And you give back to the software commons everyone depends on. The barrier is mostly psychological: people imagine they need to be experts, when maintainers are often desperate for help with docs, small bugs, and triage. Start with one tiny PR — fix a typo in a project's README, properly, via the full workflow — and you'll have done the scariest part (the first one). The rest is just repetition with growing confidence. The skills from this entire book exist precisely so you can do this; go put them to use on something real.

Security — Chapter 20

Version control and code hosting come with real security responsibilities — the most common and most painful being leaked secrets. This chapter is the practical security hygiene every Git/GitHub user needs, plus the platform features that protect your code and your account.

The #1 risk: leaked secrets

The single most common Git security disaster is committing a secret — an API key, password, token (Chapter 15), or private key — and pushing it, especially to a public repo where automated bots find and abuse it within minutes. The critical thing to understand: once a secret is committed, it's in the history forever, even if you delete the file in a later commit (Chapter 9 — the old commit still contains it). Removing it from history is painful and incomplete. So:

If you leak a secret: rotate first, scrub second Assume any secret that was ever pushed is compromised the instant it landed — bots scrape public GitHub continuously. So the order is: (1) immediately revoke/rotate the secret at its source (regenerate the API key, change the password, revoke the token) — this makes the leaked copy useless and is the only step that truly protects you. (2) Then remove it from history if you must (tools like git filter-repo or BFG rewrite history — disruptive, and pointless if you skipped step 1). Don't waste time scrubbing history while the live secret is still valid. Prevent it entirely: .gitignore your secret files (Chapter 17), never hard-code credentials, and use environment variables or a secrets manager.

Most projects pull in many third-party packages, and a vulnerability (or malicious package) in any of them affects you — the "supply chain" risk. Practical hygiene: keep dependencies updated (Dependabot automates the PRs), review what you add (don't install random packages casually), pin versions for reproducibility, and watch the security alerts GitHub surfaces. This is the same patch-and-vet discipline from the Server Admin & Security Guide and Red Team Guide, applied to your code's dependencies.

From the field — keep secrets out, turn on the free protections The overwhelming majority of Git/GitHub security incidents for individuals come down to one thing: a secret got committed. So internalize the prevention — secrets never go in Git (use .gitignore and environment variables, Chapter 17) — and the response — if one leaks, rotate it immediately, because it's compromised the moment it's pushed. Everything else is turning on protections GitHub gives you for free: enable 2FA on your account today (non-negotiable), turn on secret-scanning push protection (it'll literally stop you from pushing a detected key), enable Dependabot for vulnerable-dependency alerts, and protect main so changes can't bypass review (Chapter 16). None of this requires expertise — it's a few toggles in repo/account settings — and it prevents the great majority of real-world incidents. Good Git security is mostly good hygiene done consistently.

Part V — Power & Recovery

Advanced Git — Chapter 21

A grab-bag of powerful commands that solve specific real problems: stashing work-in-progress, grabbing a single commit, tagging releases, finding the commit that broke something, and more. You won't need these daily, but when you do, they're exactly the right tool.

stash — set work aside temporarily

You're mid-change and need to switch branches (Chapter 5) or pull, but you're not ready to commit. git stash shelves your uncommitted changes (working dir + staging) and gives you a clean slate; you reapply them later:

git stash                  # shelve current changes, clean working dir
git stash list             # see stashes
git stash pop              # reapply the latest stash AND remove it
git stash apply            # reapply but keep it in the list
git stash -u               # include untracked files
git stash drop             # delete a stash

Perfect for "I need to quickly switch to fix something else, then come back to what I was doing."

cherry-pick — grab one specific commit

git cherry-pick <commit> copies a single commit from one branch onto your current branch — useful for pulling one bug fix into a release branch without merging everything, or moving a commit you made on the wrong branch:

git switch main
git cherry-pick a1b2c3d    # apply just that one commit here

tags & releases — marking versions

Tags are permanent named pointers to a commit, used to mark releases (v1.0.0). Unlike branches, they don't move:

git tag v1.0.0                       # lightweight tag on current commit
git tag -a v1.0.0 -m "First release" # annotated tag (recommended: has message/date/author)
git push origin v1.0.0               # tags aren't pushed by default!
git push origin --tags               # push all tags

On GitHub, tags become Releases — downloadable versioned snapshots with release notes and attached binaries. Most projects use semantic versioning: MAJOR.MINOR.PATCH (breaking.feature.fix).

bisect — find the commit that broke it

git bisect is a hidden gem: it binary-searches your history to pinpoint exactly which commit introduced a bug. You mark a known-good and known-bad commit; Git checks out the midpoint; you test and say good/bad; it narrows down — finding the culprit among thousands of commits in a handful of steps:

git bisect start
git bisect bad                  # current version is broken
git bisect good v1.0.0          # this old version worked
# Git checks out a midpoint commit; test it, then:
git bisect good   (or)   git bisect bad     # repeat until it names the culprit
git bisect reset                # done -- return to where you were

Git Internals: Objects & the DAG — Chapter 22

Everything Git does — branches, merges, the reflog, recovery — makes far more sense once you see the simple data model underneath. Git is, at heart, a content-addressed database of four object types linked into a graph. Learn that, and Git stops being magic.

The four objects

Git stores everything as objects, each named by the SHA hash of its contents (content-addressing — identical content always gets the same name). There are four kinds:

  • Blob — the contents of a file (just the bytes, no name).
  • Tree — a directory listing: names plus the blob/tree each points to. A tree is a snapshot of a folder.
  • Commit — a pointer to one tree (the whole project snapshot), plus author, message, and the hash(es) of its parent commit(s).
  • Tag — (annotated tags) a named, described pointer to an object.

Because a commit names its parents, the commits form a directed acyclic graph (DAG) — history is literally a graph of snapshots, each pointing back to where it came from.

Refs are just pointers

A branch is not a thing — it's just a tiny movable ref: a file containing one commit hash. main is a pointer to a commit; committing moves that pointer forward. HEAD is a pointer to the current branch (usually). This is why branching is so cheap (Chapter 5): making a branch just writes one 40-character hash to a file. Tags, remotes' tracking branches — all just refs pointing into the object graph.

git cat-file -t <hash>     # what type is this object?
git cat-file -p <hash>     # pretty-print its contents
git rev-parse HEAD         # the hash HEAD points to
ls .git/refs/heads         # your branches are just files here

Why this explains everything

The model demystifies the rest of Git: a merge is a commit with two parents; a rebase (Chapter 8) rewrites commits as new objects with new hashes (which is why hashes change and why rewriting shared history is disruptive); "detached HEAD" (Chapter 25) just means HEAD points straight at a commit instead of a branch; and the reflog (Chapter 9) can recover "lost" work because the objects still exist in the database even when no ref points to them — nothing is deleted until garbage collection, long after.

From the field — "snapshots, not diffs" The single most clarifying idea: Git stores snapshots, not differences. Each commit records the complete state of the project (via its tree), not a patch against the last one. Git computes diffs on demand for display, but it stores whole snapshots (deduplicated by content hash, so unchanged files cost nothing). Once "every commit is a full snapshot, and a branch is just a pointer to one," clicks into place, Git's behavior becomes predictable instead of mysterious — and you can reason your way out of almost any situation.

Submodules, Subtrees & Monorepos — Chapter 23

Real projects often outgrow a single repository — you depend on another repo, or you pull many projects into one. Git offers several ways to handle this, each with real trade-offs, and choosing badly causes lasting pain.

Submodules: a repo inside a repo

A submodule embeds one Git repository inside another, pinned to a specific commit of the inner repo. The outer repo records "use this dependency at exactly this commit," giving precise, reproducible control over a dependency you also develop. The cost: submodules are notoriously fiddly — clones need --recurse-submodules, updates are a two-step dance, and teammates forget to init them.

git submodule add <url> path/    # add a submodule
git clone --recurse-submodules <url>   # clone everything
git submodule update --remote     # pull submodule updates

Subtrees: merge a repo in

A subtree takes a different approach: it actually merges another repo's contents into yours as a subdirectory, so clones "just work" with no special commands — everyone gets everything normally. The trade-off is that pushing changes back upstream is more involved. Subtrees favor the consumer (simple clone); submodules favor precise dependency control.

Monorepos vs. many repos

The bigger architectural choice: a monorepo (many projects in one big repository) or polyrepo (one repo per project). Monorepos simplify cross-project changes and shared tooling and are used at huge scale by some companies; they also strain Git at very large sizes (mitigated by tools like sparse-checkout, partial clone, and Chapter 22's object model). Polyrepos keep each project small and independent but make coordinated changes harder. There's no universal right answer — it's a deliberate trade-off about how your teams work.

From the field — reach for these only when you must Most projects need none of this — and that's the point. Submodules and subtrees solve a specific problem (sharing code between repos you control) and add real friction, so adopt them only when a genuine need appears, and pick one approach and document it. For dependencies you merely consume, a normal package manager is almost always better than a submodule. And monorepo-vs-polyrepo is a team-scale decision, not a default to agonize over solo. When in doubt, stay with one ordinary repo as long as you can.

Hooks & Automating Git — Chapter 24

Git can run your own scripts automatically at key moments — before a commit, after a merge, when someone pushes. These hooks are how teams enforce quality and automate the boring parts, and they're the bridge from Git to CI/CD.

What hooks are

A hook is just a script Git runs automatically at a defined point in its workflow. They live in .git/hooks/ (client-side) or on the server. Common client-side hooks:

  • pre-commit — runs before a commit is created; the classic place to lint code, run quick tests, or block secrets and giant files. If it exits non-zero, the commit is aborted.
  • commit-msg — checks or formats the commit message (e.g., enforce a convention).
  • pre-push — runs before pushing; a last chance to run the test suite.

The catch, and the fix

A crucial gotcha: hooks in .git/hooks/ are local and not shared by cloning (the .git folder isn't part of the project history). So a hook you set up doesn't reach your teammates. The standard solution is a hook manager — tools like the popular pre-commit framework or Husky — that store hook configuration in the repo and install it for everyone, making quality checks consistent across the team.

From hooks to CI/CD

Hooks enforce things on developers' machines, but they can be bypassed and aren't guaranteed. That's why the real enforcement lives on the server, in CI/CD (Chapter 18): GitHub Actions and similar run your tests and checks on every push and pull request, where they can't be skipped. The healthy pattern is layered: fast checks via local hooks for quick feedback, authoritative checks in CI as the gate that actually protects the shared branch.

From the field — automate the rules, don't nag about them The best teams encode their standards in automation rather than relying on people to remember: a pre-commit hook that auto-formats code ends the formatting debates; a secret-scanning hook catches the credential before it's ever committed (cheaper than the cleanup in Chapter 20); CI that blocks merges on failing tests keeps the main branch healthy. Start small — one formatter and one test run — and let the machine enforce what would otherwise be tedious review comments. Automation turns "please remember to…" into "it just happens."

Getting Out of Trouble — Chapter 22

Everyone gets into Git messes — wrong branch, bad commit, scary error message, "I think I deleted everything." This chapter is the rescue manual: the calm, reassuring truth that almost everything is recoverable, plus the specific fixes for the situations that actually happen.

First, the calming truth

Before any fix, internalize this (from Chapter 9): committed work is almost never truly lost. The reflog remembers nearly every state HEAD has been in for weeks. So when something looks catastrophic, take a breath — it's almost certainly recoverable. The two genuine exceptions: changes you never committed (uncommitted work discarded by reset --hard, restore, or clean), and rewriting shared history (Chapter 8). Everything else, you can get back.

"Detached HEAD" — the scary-sounding non-disaster

This warning panics beginners but is harmless. It means HEAD points directly at a commit instead of a branch (Chapter 2) — usually because you checked out an old commit or a tag to look around. You can look freely; you just shouldn't commit there without making a branch (commits on a detached HEAD can be lost when you leave, since no branch points to them). If you made changes you want to keep: git switch -c new-branch-name turns them into a real branch. If you just want out: git switch main. Not a disaster — just Git telling you "you're not on a branch right now."

When you're truly stuck

If you can't figure out a fix and it's a real mess, the nuclear-but-safe option exists: clone a fresh copy. Because the remote (and reflog) have your history, you can often git clone the repo again into a new folder, salvage what you need, and start clean — without losing committed work. And searching the exact Git error message almost always finds someone who hit it before. You are rarely the first.

From the field — stay calm, check the reflog, and remember --abort The difference between a Git novice and a veteran isn't that veterans don't get into messes — they absolutely do, constantly — it's that they don't panic, because they know the escape routes. Three things to carry: (1) committed work is almost always recoverable via git reflog + reset --hard <hash> (Chapter 9) — so a "disaster" is usually a five-minute fix; (2) when you're stuck in the middle of a merge/rebase/anything, --abort usually exists and puts you back where you started; (3) "detached HEAD" and "push rejected" sound scary but are routine, non-destructive states with simple fixes (above). Read the error message carefully — Git's messages, once you're past the initial intimidation, are genuinely helpful and often tell you the fix. And keep a clean practice repo (Chapter 3) to test a risky recovery before doing it on real work. Calm + reflog + --abort gets you out of nearly anything. That confidence is the final piece of Git fluency.

Part VI — Practice & Reference

Lab Exercises — Chapter 23

Git only sticks when you do it. These labs walk you through the real workflows using everything from the book — safe to do in a throwaway practice repo. Type them, make the mistakes on purpose, and recover. That's how the fear turns into fluency.

Ground rules Use a throwaway repo (mkdir ~/git-lab; cd ~/git-lab; git init) so nothing matters. For the GitHub labs you'll need a (free) account and auth set up (Chapter 15) — or skip those and do the local ones. Type the commands; the typing is the learning. Run git status and git log --oneline --graph --all liberally to see what each command did.

Lab 1 — The core loop (Ch 3, 4)

  1. git init a repo; configure your name/email if you haven't.
  2. Create a file, git status, git add, git commit; repeat with edits.
  3. git log --oneline to see your history; git diff before staging.
  4. Goal: the edit→status→add→commit rhythm is automatic.

Lab 2 — Branch & merge (Ch 5, 6)

  1. Branch with git switch -c feature; commit something; switch back to main and watch the file vanish.
  2. Merge feature into main; view it with git log --graph --all.
  3. Delete the merged branch.
  4. Goal: branching/merging feels routine.

Lab 3 — Create & resolve a conflict (Ch 7)

  1. Make two branches that edit the same line of a file differently.
  2. Merge one into the other; hit the conflict.
  3. Edit the file to resolve it (remove the markers), git add, git commit.
  4. Bonus: trigger another conflict and git merge --abort out of it.
  5. Goal: conflicts don't scare you.

Lab 4 — Undo everything (Ch 9)

  1. Make a commit, then git reset --hard HEAD~1 to "lose" it.
  2. Recover it via git reflog + git reset --hard <hash>.
  3. Practice git restore (discard edits) and git restore --staged (unstage).
  4. Make a bad commit and fix it with git commit --amend.
  5. Goal: you believe, from experience, that Git has your back.

Lab 5 — Tidy with interactive rebase (Ch 8)

  1. Make 3-4 messy commits ("wip", "more", "fix").
  2. git rebase -i HEAD~4; squash them into one and reword the message.
  3. Confirm with git log --oneline.
  4. Goal: clean up your own history before sharing.

Lab 6 — Push to GitHub (Ch 10, 11, 15)

  1. Set up auth (SSH keys via gh auth login or manually).
  2. Create a repo (gh repo create or on the website), link it, git push -u origin main.
  3. Edit a file on the GitHub website, then git pull the change down.
  4. Goal: the local↔remote sync loop.

Lab 7 — The full PR workflow (Ch 12, 13)

  1. Branch, commit, push the branch (git push -u origin feature).
  2. Open a PR on GitHub (or gh pr create); read the diff view.
  3. Merge it (try "squash and merge"); pull main; delete the branch.
  4. Goal: the professional everyday cycle, end to end.

Lab 8 — Add a .gitignore & a CI workflow (Ch 17, 18)

  1. Add a .gitignore (use a language template); confirm ignored files don't show in git status.
  2. Add a tiny .github/workflows/ci.yml that runs echo "tests pass" on push.
  3. Push; watch it run on the Actions tab.
  4. Goal: clean repos + automation basics.

Lab 9 — Contribute to open source (Ch 19) (the capstone)

  1. Find a project with a good first issue or a docs typo (your own other repos count for practice).
  2. Fork, clone, branch, fix, commit, push to your fork.
  3. Open a PR to the original; write a clear description.
  4. Goal: you've done a real contribution, the full fork-and-pull flow.

Lab 10 — Get out of trouble (Ch 22)

  1. Create a "detached HEAD" by checking out an old commit; rescue work into a branch.
  2. Commit to the wrong branch on purpose; move it to the right one.
  3. Use git bisect on a repo with several commits to "find" a planted change (Ch 21).
  4. Goal: calm under pressure — you know the escape routes.
From the field — make the mistakes here, on purpose The single best way to become genuinely confident with Git is to deliberately create the scary situations in a throwaway repo and practice recovering — lose a commit and reflog it back, cause a conflict and resolve it, get a detached HEAD and escape, reset --hard and undo it. Do these labs and the abstract fear ("what if I break something?") gets replaced by concrete experience ("oh, I've recovered from this exact thing before"). That's the whole difference. Then take the real step: use Git for an actual project you care about — a website, a script collection, your dotfiles (Linux Field Guide), school work, anything — and push it to GitHub. Nothing cements the workflow like living in it daily on something real, and you'll build a public portfolio (Chapter 11) in the process. Reading taught you the model; the keyboard makes it yours.

"How Do I Undo X?" — Appendix C

The panic-button reference. Find your situation, get the fix. This is the page to open when something went wrong and you need the answer now — then read the linked chapter later to understand why it works.

First: don't panic Committed work is almost never truly lost (Ch 9, 22). The reflog remembers nearly everything for weeks. The only genuinely unrecoverable things are uncommitted changes you discard, and rewriting shared history. So breathe, find your row below, and fix it.

Undoing changes & commits

I want to…Do this
Discard edits to a file (not committed)git restore file (gone for good — be sure)
Unstage a file (keep the edits)git restore --staged file
Discard ALL uncommitted changesgit restore . (and git clean -fd for untracked) — careful
Fix the last commit's messagegit commit --amend (only if not pushed)

The few things that ARE dangerous Most of the above is safe and reversible, but respect these: reset --hard and git clean and restore permanently discard uncommitted work (no reflog for what was never committed) — commit or stash first if unsure. Force-pushing (push --force) after a rebase can overwrite others' work on a shared branch — never do it on shared branches; prefer --force-with-lease even on your own (Ch 8). And rewriting shared history is the one truly disruptive thing. When in doubt, prefer the additive, safe options (revert, a new commit, stash) over the rewriting ones.
From the field — bookmark this page This is the appendix you'll actually use under stress. The pattern to remember: when something goes wrong, (1) stop and breathe — it's almost certainly recoverable; (2) find your row here for the immediate fix; (3) if you're unsure whether a fix is destructive, git stash or commit your current state first so you have a fallback; (4) when calm, read the linked chapter to understand why it worked, so next time it's not a mystery. The single most empowering Git command for getting unstuck is git reflog — it's the time machine that makes "I destroyed everything" almost always false. Keep this page handy, lean on it without shame (everyone does), and over time you'll need it less as the fixes become familiar. Calm + this reference = you can get out of anything Git throws at you.
