The Python Environment Field Guide

Interpreters, Virtual Environments & Packages
Almost every "it works on my machine" story in Python is really an environment story — the wrong interpreter, a package installed somewhere the interpreter never looks, a version that quietly upgraded underneath a project. This book teaches the one mental model that dissolves all of it: a Python environment is just a folder containing an interpreter and its packages, and every command you run picks one. Once you can answer "which Python am I actually running, and where do its packages live?" the errors stop being mysteries and become questions with obvious answers.

How to Read This Book — Front Matter

This is a short book about a topic that wastes an enormous amount of people's time. Read Part I and Part II in order — they are the whole foundation — then treat the rest as reference you come back to when a specific problem finds you.

The journey, part by part Part I (The Interpreter) builds the mental model: what an "environment" actually is on disk, how to install Python without breaking your system, and how to answer the single most important debugging question in Python — which interpreter is running right now? Part II (Isolation) is the core skill: virtual environments, pip, and requirements.txt, which together make a project reproducible on someone else's machine. Part III (The Ecosystem) covers the alternatives you'll meet in the wild — conda, uv, Poetry — plus how environments interact with Jupyter notebooks and with robotics stacks like ROS 2. Part IV is troubleshooting, labs, and the reference pages you'll actually keep open.
How to actually use it Have a terminal open. Every chapter in Part II has commands you should run, and the muscle memory is the point — python3 -m venv .venv should eventually be something your fingers type without consulting anything. If you're short on time and just need to get working today, read Chapter 5 and Appendix A, then come back. If you're here because something is broken right now, jump straight to Chapter 11. This guide assumes basic comfort at a command line; if that's shaky, the Linux Field Guide covers the shell from zero.
The one rule, stated up front Never install project packages into your system Python. Not with sudo pip install, not with a bare pip install that happens to hit the system interpreter. Your operating system uses its Python for its own tools; packages you shove in there can break them, and you will eventually hit a version conflict you cannot untangle. Make a virtual environment per project. It takes eight seconds and it is the entire difference between Python being pleasant and Python being a source of dread. Modern Python (3.11+) actually blocks this by default with an externally-managed-environment error — that error is your friend, not an obstacle to work around.

Part I — The Interpreter

What an Environment Is — Chapter 1

Strip away the tooling and a Python environment is an unglamorous thing: a folder with an interpreter in it and a folder of packages next to it. Almost every confusing error makes sense once you can picture that.

An environment is a folder

When you run python, your shell finds an executable file somewhere on disk and runs it. That executable is the interpreter. Sitting next to it — at a path the interpreter computes from its own location — is a directory called site-packages, which is where every library you install lands. An "environment" is just that pairing:

Why this picture explains everything

Hold that image and the classic errors decode themselves:

The errorWhat it actually means
ModuleNotFoundError: No module named 'numpy'You installed numpy into one site-packages and ran a different interpreter. Classic mismatch.
pip install says "already satisfied" but the import still failsSame thing, seen from the other side: pip and python are pointing at different environments.
Code works in the terminal but not in your editorYour editor selected a different interpreter than your shell. See the VS Code guide.
Two projects need incompatible versions of the same libraryThey're sharing one site-packages. They need one each.
error: externally-managed-environmentYou tried to install into the OS's own Python. Make a venv instead.

Notice that four of those five are the same bug wearing different hats. That's the payoff of the model: instead of five memorized fixes, you have one question — which environment is this command using? — and Chapter 3 teaches you to answer it in two commands.

What "activating" really does

Tools talk about activating an environment as if it were a mode switch. It isn't, and believing it is causes confusion later. Activation does something much dumber: it puts the environment's bin/ directory first on your PATH, so that when you type python, the shell finds that one before the system one. That's essentially the whole trick. It also sets VIRTUAL_ENV and decorates your prompt so you can see what's going on.

The useful consequence: you never have to activate. Running .venv/bin/python script.py directly is exactly equivalent and is what scripts, cron jobs, and CI systems generally do. Activation is a convenience for humans typing interactively, and understanding that it's "just PATH" is what lets you debug it when it misbehaves.

From the field — the question that saves the afternoon Experienced Python developers have an involuntary reflex: the instant an import fails, before reading the traceback closely or reaching for search, they run which python and python -c "import sys; print(sys.executable)". Not because they suspect anything specific, but because environment mismatch is far and away the most common cause and it takes three seconds to rule out. Build that reflex now and you'll skip years of confused debugging. The corollary is a habit worth adopting today: prefer python -m pip install X over bare pip install X. The -m form guarantees the pip you're running belongs to the python you just named, which structurally eliminates the mismatch instead of merely detecting it.

Installing Python — Chapter 2

Getting Python onto a machine is easy. Getting it on in a way that won't fight your operating system a year later takes about two minutes of care, which this chapter spends for you.

You probably already have one — and shouldn't use it

Every Linux distribution and macOS ships with a Python, because system tooling is written in it. That interpreter belongs to the OS. You can run it, and you'll use it to create virtual environments, but you should not install packages into it (Chapter 1). Check what you have:

python3 --version          # Linux / macOS
python --version           # Windows
python3 -c "import sys; print(sys.executable)"

Per-platform install

PlatformRecommendedNotes
Ubuntu / Debiansudo apt install python3 python3-venv python3-pippython3-venv is a separate package on Debian-family systems and is the single most common missing piece.
Fedora / RHELsudo dnf install python3 python3-pipvenv is bundled.
macOSbrew install pythonHomebrew's Python is kept separate from Apple's, which is what you want.
Windowspython.org installer, or winget install Python.Python.3.12Tick "Add python.exe to PATH" in the installer. Ships with the py launcher.

The Windows py launcher

Windows installs a small dispatcher called py that knows about every Python on the machine. It's more reliable than python because it doesn't depend on PATH ordering, and it's how you pick a version explicitly:

py --list            # every Python installed on this machine
py -3.12 --version   # run a specific version
py -m venv .venv     # create a venv with the default Python

Windows also has "App Execution Aliases" — stub python.exe files that open the Microsoft Store instead of running anything. If typing python opens the Store, turn those off in Settings → Apps → Advanced app settings → App execution aliases, or just use py.

Which version should you install?

Unless a project pins you, take the current stable release minus one minor version. The newest release is fine for your own code but some compiled scientific packages lag a few months behind, and robotics stacks in particular pin hard: ROS 2 Jazzy expects the Python that ships with Ubuntu 24.04 (Chapter 10). Python's versioning is 3.MAJOR.MINOR; the number that matters for compatibility is the middle one, because site-packages is version-specific — which is exactly why upgrading Python appears to "delete" all your packages. It didn't; the new interpreter is simply looking in a different folder.

Try it — take inventory 
python3 --version
python3 -c "import sys; print(sys.executable)"
python3 -c "import sys; print(sys.prefix)"
python3 -m venv --help | head -3      # confirms venv is available

# Linux/macOS: find every python the shell can see
type -a python python3 2>/dev/null

# Windows PowerShell:
# py --list
# Get-Command python -All
If python3 -m venv --help errors on Ubuntu, install python3-venv. That one package is behind a remarkable share of "venv doesn't work" reports.

Which Python Am I Running? — Chapter 3

This is the diagnostic chapter, and it's the highest-value five minutes in the book. Two commands answer nearly every environment question you will ever have.

The two commands

# 1. Which executable will the shell run?
which python          # Linux / macOS  (use 'where python' or 'Get-Command python' on Windows)

# 2. Which interpreter is actually running, and where does it look for packages?
python -c "import sys; print(sys.executable); print(sys.prefix)"

sys.executable is the full path of the running interpreter and sys.prefix is the root of its environment. If sys.prefix points inside your project's .venv, you're in the venv. If it points at /usr, you are not, whatever your prompt claims.

Where does it search for imports?

When you import numpy, Python walks a list of directories in order and takes the first hit. That list is sys.path:

python -c "import sys; print('\n'.join(sys.path))"

# Where did a specific package actually come from?
python -c "import numpy; print(numpy.__file__)"

# What does pip think it's managing?
python -m pip --version        # prints pip's path AND its python — both, in one line

That last one is quietly the best diagnostic in Python. Its output looks like pip 24.0 from /home/you/proj/.venv/lib/python3.12/site-packages/pip (python 3.12) — naming the environment pip will install into. If that path isn't the one you expected, you've found your bug before you started looking.

The first entry on sys.path is not what you think

Python puts the directory of the script you ran (or the current directory, for an interactive session) at the front of sys.path. So a file named random.py or email.py in your project directory will shadow the standard-library module of the same name, and the resulting errors are deeply confusing — something inside a library you didn't write suddenly fails to import. If a stdlib import breaks for no reason, look for a file in your folder with that name (and delete the matching __pycache__ entry).

Try it — see a mismatch on purpose 
cd /tmp && mkdir -p envdemo && cd envdemo
python3 -m venv .venv

# Before activating:
which python3
python3 -c "import sys; print(sys.prefix)"

# After activating:
source .venv/bin/activate           # Windows: .venv\Scripts\activate
which python
python -c "import sys; print(sys.prefix)"
python -m pip --version

deactivate                          # and back out again
Watch sys.prefix change from /usr to your .venv and back. That flip is the entire mechanism, and seeing it once beats reading about it three times.
From the field — trust the interpreter, not the prompt A decorated shell prompt showing (.venv) is a string that activation set, not a live readout of reality. It can be stale — you deleted the venv folder but the prompt still says it's there; you activated in one terminal tab and are typing in another; a tool re-execs Python with a different interpreter under the hood. The prompt is a hint. sys.executable is the truth, because it is the running process reporting on itself. When a colleague says "but it's activated, look" and points at their prompt, the productive next move is always the same: ask them to run python -m pip --version. Roughly half the time that single line ends the discussion, because it shows pip cheerfully managing a completely different environment from the one the prompt advertises.

Part II — Isolation

Why Virtual Environments — Chapter 4

The case for venvs in one sentence: two projects will eventually need two different versions of the same library, and without isolation only one of them can win.

The conflict, made concrete

You have a robotics project pinned to an older numpy because a vendor SDK compiled against it, and a data-analysis project that wants the newest one for a feature you need. Both install into the same site-packages. Installing for one silently breaks the other, and you discover it days later in an unrelated traceback. There is no clever fix at this level — one directory can only hold one version of a package. The only real answer is more directories, which is what a virtual environment is.

What you get

  • Independence — each project pins whatever versions it needs, and upgrading one can't touch another.
  • A safe system Python — your OS keeps working because you never wrote into its package directory.
  • Reproducibility — the environment can be described in a file (Chapter 7) and rebuilt identically by a teammate, a grader, or a CI runner.
  • A trivial undo — when an environment gets into a state you can't explain, delete the folder and rebuild it in thirty seconds. This is genuinely liberating and worth doing sooner than you'd think.
  • Honesty about dependencies — a fresh venv tells you immediately when your project depends on something you forgot to declare, because the import fails.

The cost

Being fair about the downsides: a venv is a real folder using real disk space (tens of MB, more with something like PyTorch), you have to remember to activate it, and editors need to be told which one to use. In exchange you never again debug a version conflict. It is not a close trade, and the friction disappears within a week of habit.

The convention worth adopting Name it .venv, put it in the project root, and add it to .gitignore. The leading dot hides it from casual listings, .venv is what VS Code and PyCharm auto-detect (VS Code guide), and it's the near-universal convention so teammates know what it is on sight. Never commit it to Git — it contains platform-specific compiled binaries that are useless on anyone else's machine, and it will bloat your repository enormously. You commit the recipe (requirements.txt), not the cake. See the Git guide on .gitignore.

venv, Start to Finish — Chapter 5

The whole workflow, which is four commands. Learn these and you have the skill this book exists to teach.

Create, activate, install, leave

# 1. Create — makes a .venv folder in the current directory
python3 -m venv .venv

# 2. Activate — puts .venv/bin at the front of PATH
source .venv/bin/activate          # Linux / macOS (bash, zsh)
# .venv\Scripts\activate           # Windows PowerShell / cmd

# 3. Work — python and pip now mean the venv's copies
python -m pip install requests
python myscript.py

# 4. Leave
deactivate

Note python3 -m venv, not a venv command — venv is a stdlib module, and the -m form means "the venv module belonging to this interpreter", which is how you control which Python version the new environment gets.

Activation by shell

ShellCommand
bash / zsh (Linux, macOS)source .venv/bin/activate
fishsource .venv/bin/activate.fish
Windows PowerShell.venv\Scripts\Activate.ps1
Windows cmd.exe.venv\Scripts\activate.bat
Git Bash on Windowssource .venv/Scripts/activate

If PowerShell refuses with an execution-policy error, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once. It's a per-user setting and doesn't require admin rights.

Choosing the Python version

The venv is built from whichever interpreter you invoke, and its version is fixed at creation — there is no upgrading a venv in place. To change versions, delete it and make a new one:

python3.11 -m venv .venv        # Linux/macOS: use a specific version
py -3.11 -m venv .venv          # Windows

rm -rf .venv && python3.12 -m venv .venv   # "upgrading" = recreating

Useful flags

python3 -m venv --upgrade-deps .venv   # start with current pip/setuptools
python3 -m venv --system-site-packages .venv   # also see the system's packages
python3 -m venv --prompt robotics .venv        # custom name in the prompt

--system-site-packages deserves a warning: it makes the venv fall back to the system's packages for anything not installed locally. That defeats most of the isolation you came for, and it makes pip freeze misleading. There is one legitimate common use — robotics, where you need the system-installed ROS 2 Python packages visible inside your venv (Chapter 10) — but reach for it only when you have that specific problem.

Try it — the full loop 
mkdir -p ~/py-practice && cd ~/py-practice
python3 -m venv .venv
source .venv/bin/activate                 # Windows: .venv\Scripts\activate

python -m pip --version                   # confirm it's the venv's pip
python -m pip install requests
python -c "import requests; print(requests.__file__)"   # inside .venv — good

python -m pip freeze > requirements.txt
cat requirements.txt

deactivate
python -c "import requests"               # ModuleNotFoundError — correct!
That final error is the proof that isolation works: outside the venv, the package genuinely isn't there. Keep this folder for Chapter 12.
From the field — make it reflex, and make it disposable Two habits separate people who find Python pleasant from people who find it maddening. The first: the venv is the second thing you do in a new project, right after git init — not something you retrofit after a conflict forces you to. It costs eight seconds up front and saves hours later. The second, and less obvious: treat environments as disposable. Beginners nurse a sick environment for hours, uninstalling and reinstalling packages, trying to reason about how it got into its current state. Professionals delete it. rm -rf .venv && python3 -m venv .venv && pip install -r requirements.txt takes under a minute and gives you a state you can actually reason about. The willingness to throw an environment away is what makes environments cheap, and the whole workflow in Chapter 7 exists to make that rebuild reliable.

Installing Packages with pip — Chapter 6

pip is Python's package installer. It talks to PyPI, the public index of several hundred thousand packages, and drops what it finds into the active environment's site-packages.

The commands you'll use

python -m pip install requests           # latest version
python -m pip install "requests==2.31.0" # exactly this version
python -m pip install "requests>=2.28"   # at least this version
python -m pip install "requests~=2.31.0" # 2.31.x, but not 2.32 (compatible release)

python -m pip uninstall requests
python -m pip list                       # everything installed here
python -m pip show requests              # version, location, dependencies
python -m pip install --upgrade requests

Quote your version specifiers. > and < are redirection operators in every shell, so an unquoted pip install requests>=2.28 creates a file called =2.28 and installs the wrong thing.

Where packages come from

By default pip downloads from PyPI (pypi.org). Most packages arrive as wheels — pre-built .whl archives, often compiled for your exact platform and Python version. When no matching wheel exists, pip falls back to building from source, which needs a compiler and is where installs get slow and error-prone. A wall of C compiler errors during pip install almost always means "no wheel for your platform/version"; the usual fixes are upgrading pip (wheel support improves), using a slightly older Python (packages lag new releases by months), or installing the system build dependencies.

Other install sources

python -m pip install -r requirements.txt        # from a requirements file
python -m pip install -e .                       # editable: your own project, live
python -m pip install git+https://github.com/user/repo.git
python -m pip install ./some/local/package
python -m pip install --index-url https://my.mirror/simple pkg    # private index

pip install -e . ("editable install") is worth knowing early: it installs your own project so it's importable from anywhere, but as a link back to your source, so edits take effect without reinstalling. It's the standard way to work on a package you're also using.

Two real hazards Never sudo pip install. It writes into the OS's package directory as root, and on Linux it can break system tools written in Python. If a tutorial tells you to, the tutorial is old. And check names before you install. Anyone can publish to PyPI, and typosquatting is an active problem: python-nmap vs nmap, beautifulsoup4 (correct) vs beautifulsoup (not). Packages run arbitrary code at install time, so a typo can mean running someone else's script as you. Copy names from official docs rather than typing from memory, and glance at the download count and last-release date on pypi.org for anything unfamiliar.

The dependency resolver, and why it sometimes stalls

Packages depend on other packages, which have their own version constraints, and pip has to find a set that satisfies everything at once. Usually this is instant. Occasionally — especially with large scientific or ML stacks — you'll watch it download the same package a dozen times while it backtracks through the solution space. It's working, not hung. You can help it enormously by pinning the packages you actually care about (numpy==1.26.4 rather than leaving it open), which collapses the search. If it truly won't converge, uv (Chapter 8) solves the same problem dramatically faster.

requirements.txt — Chapter 7

An environment nobody else can rebuild isn't reproducible, it's a liability. A requirements file is the recipe that turns your working setup into something a teammate, a grader, or a server can recreate exactly.

Producing and consuming one

python -m pip freeze > requirements.txt      # capture the current environment
python -m pip install -r requirements.txt    # rebuild it somewhere else

pip freeze writes every installed package at its exact version, one per line. Commit that file to Git; never commit the .venv itself (Chapter 4).

Pinned vs. loose — the real tradeoff

There are two philosophies and they suit different files:

Pinned ==Loose >= / ~=
Examplenumpy==1.26.4numpy>=1.26
Reproducible?Exactly — same bytes every timeNo — you get whatever's current today
Gets security fixes?Only when you bump it deliberatelyAutomatically on reinstall
Best forApplications, deployments, coursework, anything reproducibleLibraries other people install alongside their own deps

The mature pattern separates the two concerns: keep a short hand-written file of your direct dependencies with loose bounds, and generate a fully-pinned lock file from it for actual installs. That way you know which four packages you chose and which sixty came along for the ride:

# requirements.in — what you actually chose, hand-written
numpy>=1.26
requests
pyserial

# then generate the pinned lock file (pip-tools, or uv):
pip-compile requirements.in -o requirements.txt
# uv equivalent:  uv pip compile requirements.in -o requirements.txt

The portability trap in pip freeze

pip freeze records what's installed, including things that don't travel. Two things to strip before committing:

  • Local paths — editable installs appear as -e git+ssh://... or a bare filesystem path that exists only on your machine.
  • Platform-specific packages — pywin32 in a file a Linux teammate installs will fail outright. Guard them with environment markers: pywin32==306; sys_platform == "win32".

Also note that pip freeze captures everything, including transitive dependencies you never chose. That's correct for a lock file and noisy for a human-maintained one — hence the two-file pattern above.

Try it — prove reproducibility 
cd ~/py-practice && source .venv/bin/activate
python -m pip install requests rich
python -m pip freeze > requirements.txt
deactivate

# Now rebuild it from scratch, as a teammate would:
rm -rf .venv
python3 -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip list                # same packages, same versions
You just deleted your entire environment and got it back in under a minute. That is what "reproducible" buys you, and it's why deleting a broken venv should feel routine rather than drastic.
From the field — the README test Here's the standard your projects should meet, and it's the one graders and hiring managers apply without announcing it: a stranger with your repo and no other context should be able to run your code from three commands in the README — create a venv, install requirements, run the thing. If they need to ask you what to install, the project isn't finished. The way to verify this isn't to think hard about it, it's to test it: clone your own repo into a fresh directory, build the environment from your own instructions, and run it. You will find something missing — almost everyone does the first time, usually a package you installed months ago and forgot was doing work. Doing this once before you submit or share anything is the cheapest quality improvement available to you, and it's the same instinct that makes the installation guides in this series worth writing carefully.

Part III — The Ecosystem

conda, uv, Poetry & Friends — Chapter 8

venv and pip are the standard library's answer and they're enough for most work. But you will meet the alternatives in real projects, and each exists because it solves something the standard pair genuinely doesn't.

The landscape

ToolWhat it addsReach for it when
venv + pipNothing extra — built in, always availableDefault. Start here, stay here unless something pushes you off.
uvThe same workflow, 10–100× faster, with real lock filesYou want a drop-in speedup, or pip's resolver is crawling.
conda / mambaManages non-Python deps too (CUDA, compilers, C libraries) and Python itselfGPU/ML work, or a package that needs system libraries you can't install.
PoetryDependency management + packaging + publishing, one fileYou're building a library to publish on PyPI.
pipxInstalls command-line apps, each in its own hidden venvInstalling tools (black, ruff) you want on PATH globally.
pyenvInstalls and switches between multiple Python versionsYou need 3.9 and 3.13 on one machine.

uv, briefly

uv is a fast reimplementation of the pip/venv workflow whose commands are deliberately familiar. If pip's resolver is making you wait, it's a nearly free swap:

uv venv                          # create .venv
uv pip install requests          # same syntax as pip, much faster
uv pip compile requirements.in -o requirements.txt
uv pip sync requirements.txt     # make the env match the file *exactly*

uv pip sync has no direct pip equivalent and is genuinely useful: it removes anything not in the file, so the environment matches the lock rather than merely containing it.

conda, and why it's a separate world

conda solves a problem pip structurally can't: some scientific packages need compiled C/C++/CUDA libraries that aren't Python at all. conda ships those as part of the package, which is why GPU-accelerated ML setups so often use it. The tradeoff is that it's a parallel universe — its own package repositories, its own environment format, and its own install of Python.

conda create -n myenv python=3.11
conda activate myenv
conda install numpy pandas
conda env export > environment.yml
conda env create -f environment.yml
conda deactivate

The standard advice for mixing them: install what you can with conda first, then use pip inside the conda environment for anything conda doesn't have. Going back and forth — conda, then pip, then conda again — is what produces environments that break in ways nobody can explain, because the two tools don't share a view of what's installed.

Don't tool-shop, especially not while learning Python's packaging ecosystem is genuinely fragmented, and every few years a new tool is confidently declared the future. This generates a lot of anxious blog posts and very little actual value for someone trying to finish a project. venv + pip + requirements.txt is a complete, permanent, always-available answer that ships with Python and will work on every machine you ever touch. Learn it thoroughly. Adopt another tool when you hit the specific problem it solves — conda when a package needs CUDA, uv when the resolver is too slow to bear, pipx when you want a CLI tool globally — and not because a comparison article was persuasive. The mental model in Chapter 1 transfers to all of them anyway, which is the real reason to learn the basics properly first.

Environments & Notebooks — Chapter 9

Jupyter adds a layer of indirection between "the environment" and "the code that runs", and that layer is responsible for a specific, very common flavour of confusion.

Where the confusion comes from

A notebook doesn't run in the environment you launched it from. It runs in a kernel, which is a separate process with its own interpreter. Launch Jupyter from environment A, select a kernel registered by environment B, and your pip install in A's terminal has no effect on the code in the cell. Hence the eternal beginner experience: install a package, restart everything, still get ModuleNotFoundError.

The fix: register the venv as a kernel

source .venv/bin/activate
python -m pip install ipykernel
python -m ipykernel install --user --name=myproject --display-name "Python (myproject)"

jupyter kernelspec list      # see every registered kernel and its path
jupyter kernelspec uninstall myproject   # remove a stale one

Then pick "Python (myproject)" from the kernel menu. Kernel specs accumulate — it's worth running kernelspec list occasionally and deleting ones whose environments you long since deleted, since selecting a kernel whose venv no longer exists produces an unhelpful startup failure.

The diagnostic that works every time

Run this in a notebook cell, not in a terminal:

import sys
print(sys.executable)
print(sys.prefix)

That's the interpreter the kernel is actually using. And if you need to install from inside a notebook, use the %pip magic rather than !pip — %pip targets the running kernel's environment, while !pip shells out and hits whatever pip is on PATH, which is exactly the mismatch you're trying to avoid:

%pip install requests      # correct — installs into the kernel's environment
!pip install requests      # unreliable — may install somewhere else entirely

The Jupyter Field Guide covers kernels, magics, and the notebook workflow in much more depth.

Environments in Robotics — Chapter 10

Robotics is where Python environments get genuinely hard, because the robot's software stack was installed by the system package manager and expects the system Python — while your project wants isolation. Here's how the two coexist.

Why ROS 2 fights your venv

ROS 2 installs its Python packages (rclpy and friends) system-wide via apt, built against the exact Python that ships with that Ubuntu release — ROS 2 Jazzy against Ubuntu 24.04's Python 3.12. When you create a normal isolated venv and activate it, import rclpy fails, because your clean venv correctly can't see the system's packages. The isolation you wanted is precisely the problem.

The standard resolution is the one exception to the rule in Chapter 5:

# Source the ROS 2 environment FIRST, then build a venv that can see it
source /opt/ros/jazzy/setup.bash
python3 -m venv --system-site-packages .venv
source .venv/bin/activate

python -c "import rclpy; print(rclpy.__file__)"   # from /opt/ros — correct
python -m pip install numpy matplotlib             # yours, into .venv

Order matters: source ROS first so its environment variables are set, then activate the venv so its bin/ wins on PATH. Reverse it and you'll get the system Python back. If a shell is behaving strangely in a ROS project, that ordering is the first thing to check.

Vendor SDKs are pinned, and they mean it

Hardware SDKs — the Unitree SDK among them — are frequently built against a specific Python version and a specific numpy. Upgrading numpy because an unrelated tutorial suggested it is a genuinely common way to break a working robot setup, and the resulting error usually surfaces far from the cause. Two habits protect you:

  • Pin the vendor's versions explicitly in requirements.txt with ==, and add a comment saying why, so future-you doesn't "helpfully" bump it.
  • Keep the robot environment separate from your analysis environment. Plotting and data work has no business sharing a venv with the SDK that drives real actuators.
The robot is not your laptop On a real robot, an environment mistake has physical consequences: a broken dependency mid-session can leave a limb energized or drop a controller that was holding a pose. Two rules that lab courses learn the hard way. Never install packages on a robot you can't rebuild — if there's no requirements.txt capturing its working state, make one before you touch anything. And never run pip install while hardware is powered and unattended. Test the environment change with the robot on a stand or in simulation, confirm imports work, and only then run it live. The Robotics Software Installation Guide walks through building a lab environment from scratch in the right order.
From the field — write down what worked Robotics environments are fragile in a way web or data environments usually aren't, because they sit on top of vendor SDKs, kernel modules, and hardware drivers that nobody can reinstall from PyPI. The single most valuable thing you can do the moment a robot setup works — before you write a line of project code — is capture it: pip freeze > requirements.txt, note the ROS distro and Ubuntu version, note the SDK version and where it came from, and commit all of it. Teams that do this recover from a wiped machine in an hour. Teams that don't lose days reconstructing a configuration nobody fully remembers, usually right before a demo. The working state of a robot is real, hard-won knowledge, and it lives in exactly one place until you write it down.

The nuclear option, and why it's fine

deactivate 2>/dev/null
rm -rf .venv
python3 -m venv .venv && source .venv/bin/activate
python -m pip install -r requirements.txt

Four commands, under a minute, and you have a known-good state. If you have a requirements.txt this is not a defeat — it is very often the correct first move, ahead of investigation, because the time spent diagnosing a corrupted environment rarely teaches you anything worth knowing.

Lab Exercises — Chapter 12

Short, practical, and cumulative. Do them in order in a scratch directory; the point is to make the mechanics automatic and to see isolation actually work.

Lab 1 — Prove isolation exists

  1. Create two directories, projA and projB, each with its own .venv.
  2. In A: python -m pip install "requests==2.28.0". In B: install requests==2.31.0.
  3. In each, run python -c "import requests; print(requests.__version__, requests.__file__)".
  4. Confirm the versions differ and each resolves inside its own .venv. Why can both exist at once?

Lab 2 — Break it deliberately

  1. Activate projA's venv, then run deactivate and try importing requests. Explain the error using sys.path.
  2. Reactivate and compare which python and which pip before and after. Which directory got prepended?
  3. Rename the projA folder and try activating again. It breaks — find out why (hint: head -1 .venv/bin/pip).

Lab 3 — The reproducibility test

  1. In a fresh project, install three packages of your choice and write a script that imports all three.
  2. pip freeze > requirements.txt, then delete .venv entirely.
  3. Rebuild from the requirements file and confirm your script still runs.
  4. Now hand requirements.txt and your script (no venv) to a classmate. Can they run it without asking you anything? That's the README test.

Lab 4 — Shadowing

  1. In an empty directory, create a file called random.py containing print("hijacked").
  2. In the same directory, run python -c "import random; print(random.randint(1,10))".
  3. Explain what happened using the first entry of sys.path (Chapter 3). Then delete the file and __pycache__.

Lab 5 — Notebook kernels

  1. Create a venv, install ipykernel and rich, and register the kernel with a recognizable display name.
  2. Launch Jupyter, select the kernel, and print sys.executable in a cell. Does it match the venv?
  3. Switch to a different kernel and print it again. Explain why !pip install would be unreliable here.

From the field — the short version of this whole book If you retain one page, make it this one. One project, one venv, named .venv, gitignored, described by a requirements.txt you actually commit. Create it before you write code, not after something breaks. Use python -m pip install rather than bare pip, so the installer and the interpreter can never disagree. When something imports wrong, check sys.executable before you check anything else. And when an environment gets weird, delete it — you have the recipe, the rebuild takes a minute, and hours spent nursing a corrupted environment teach you nothing you'll want to remember. That's the entire discipline. It's not sophisticated, and it eliminates the overwhelming majority of the problems that make people describe Python packaging as a nightmare.
A closing word Python's environment story has a bad reputation, and some of it is earned — the ecosystem is fragmented and the error messages are rarely as helpful as they could be. But the underlying model is genuinely simple, and it's the same model under every tool in Chapter 8: an interpreter, a folder of packages, and a PATH that decides which pair you get. Everything else is convenience on top. Once you can picture that — and once checking sys.executable is reflex rather than something you remember to do — the errors stop feeling arbitrary and start reading like plain statements of fact about which folder something is in. That shift, from mystery to mechanism, is what this book was for. Now go make a venv.
