Part I — Meeting Linux

What Linux Is & Why It Matters — Chapter 1

Linux runs the world quietly — most of the internet, nearly all supercomputers, every Android phone, your car, your router, the cloud. Learning it is the highest-leverage skill in computing, because once you know Linux, you know the machine the modern world actually runs on.

Kernel, OS, and the open-source story

Strictly, Linux is a kernel — the core program that talks to the hardware, manages memory, and runs your programs. What you actually install (Ubuntu, Fedora, Debian) is a distribution ("distro"): the Linux kernel plus a whole operating system of tools, mostly from the GNU project and thousands of open-source contributors (which is why purists say "GNU/Linux"). It was started in 1991 by a Finnish student, Linus Torvalds, as a hobby — and grew, through the open-source movement, into the most widely deployed operating system on Earth.

The defining trait is open source: the code is free to read, modify, and share (most of it under the GPL license). That's not just ideology — it's why Linux is everywhere. Anyone can adapt it, so it got adapted to run on everything from watches to supercomputers, with no licensing fees and no vendor lock-in.

Why it's worth your time

  • It's the industry's lingua franca. Servers, cloud, DevOps, security, data science, embedded — all run on Linux. The skill transfers across the entire field and barely ages.
  • It makes you powerful. The command line (Part II) does in one line what takes ten clicks elsewhere, and automates what can't be clicked at all (Chapter 18).
  • It's transparent. Nothing is hidden — configuration is readable text files (Chapter 6), logs explain what happened (Chapter 17), and you can see and change how everything works.
  • It's free, in both senses. No cost, and no one dictating what you may do with your own machine.

How Linux thinks (the philosophy that explains everything)

Linux inherits the Unix philosophy, and internalizing it early makes the whole system make sense:

  • Do one thing well. Tools are small and focused (a tool to list files, a tool to search text), not giant do-everything apps.
  • Combine small tools. You build power by connecting simple tools with pipes (Chapter 10) — the output of one becomes the input of the next.
  • Everything is a file. Documents, devices, even processes are represented as files you can read and write (Chapter 6) — a profoundly simplifying idea.
  • Text is the universal interface. Configuration and data are plain text, so the same tools work on all of it.
From the field — you already use Linux every day People think Linux is a niche thing for hackers and servers, but you almost certainly used it a dozen times today without knowing: every Google search, every Android phone, most websites you visited, the Wi-Fi router in your home, the cloud storing your files — Linux, all of it. That ubiquity is the practical case for learning it: this isn't an obscure hobby OS, it's the substrate of modern computing. The companies hiring for cloud, security, DevOps, and data roles all assume Linux fluency. And here's the encouraging part — it's learnable. It feels alien for a week and then it clicks, because underneath it's a small set of consistent ideas (the philosophy above) applied everywhere. This book's whole job is to get you to that click as fast as possible. The fastest way there starts in Chapter 3: get a Linux you can play with, and never stop typing.

Distros & the Ecosystem — Chapter 2

"Which Linux should I use?" is the first question everyone asks, and the answer matters less than beginners fear. The distros differ mostly in packaging and defaults, not in the fundamentals — learn one and you mostly know them all. Here's the map so you can choose without overthinking.

What a distro actually is

A distribution bundles the Linux kernel (Chapter 1) with a chosen set of components: a package manager (how you install software — Chapter 14), a desktop environment (the GUI, if any — Chapter 4), default tools, a release schedule, and a community or company behind it. The kernel and the core command-line tools are largely the same everywhere — so the skills in this book transfer across all of them. The differences are real but mostly about packaging and philosophy.

The major families

The biggest practical fork is the package manager (Chapter 14): Debian-family uses apt, Red Hat-family uses dnf, Arch uses pacman. Most other commands are identical across all of them.

Stable vs cutting-edge: the release-model choice

  • Fixed/stable releases (Debian, Ubuntu LTS, RHEL/Rocky) — tested package sets, updated on a schedule; some software is older but rock-solid. Best for servers and "it must just work."
  • Rolling releases (Arch, openSUSE Tumbleweed) — continuously updated to the newest versions; cutting-edge but occasionally needs hand-holding. Best for enthusiasts who want the latest.
  • LTS (Long-Term Support) — versions (like Ubuntu's, every 2 years) supported for ~5+ years. The sensible default for stability.

From the field — stop distro-hopping, start using one The classic beginner trap is spending weeks agonizing over and reinstalling distros instead of learning Linux. Don't. For 95% of people the right move is: install Ubuntu LTS (or Mint), and start working. The fundamentals you'll learn — the shell, files, permissions, processes, packages — are the same on every distro, so time spent learning is never wasted, while time spent hopping mostly is. You can always switch later once you actually know what you'd be switching for; until then, the differences are mostly cosmetic to a learner. Pick the popular, well-documented one (so every error you google has an answer), and pour your energy into Part II. The distro is the car; the command line is driving — and driving is the skill that transfers.

Getting Linux Running — Chapter 3

You can't learn Linux by reading — you learn it by typing. So before anything else, get a Linux you can experiment in freely and break without consequence. There are four easy ways, and the best one for learning is whichever gets you to a prompt fastest.

The four ways in

MethodWhat it isBest for
Virtual machineLinux running in a window on your current OS (VirtualBox/VMware/Hyper-V)Learning — safe, snapshot-able, doesn't touch your real system (Field Tech Guide)
WSL (Windows Subsystem for Linux)A real Linux command line inside Windows, no VM overheadWindows users who want the terminal fast (no GUI)
Live USBBoot Linux from a USB stick without installingTrying it on real hardware; rescue work (Field Tech Guide)
Dual-boot / full installInstall alongside or instead of your current OSCommitting to Linux as a daily driver

The two best starting points

For most learners: a virtual machine. Install VirtualBox (free), download an Ubuntu ISO, create a VM, and install Linux inside it. The killer feature is snapshots: save a clean state, then experiment fearlessly — break the system completely, and roll back in seconds. This removes all the fear that makes beginners hesitant, which is exactly what you want while learning.

For Windows users who just want the terminal: WSL. One command gets you a genuine Ubuntu shell inside Windows:

wsl --install                 # installs WSL + Ubuntu (run in admin PowerShell, then reboot)
wsl --install -d kali-linux    # or pick a specific distro
wsl -l -v                      # list installed distros

WSL is brilliant for learning the command line (Part II) without a full VM — though it has no GUI by default and isn't a "real" boot, so for system-level topics (boot/systemd, Chapter 15) a VM is better.

Live USB & dual-boot, briefly

A live USB (made with Rufus, balenaEtcher, or Ventoy) boots Linux straight from the stick — great for trying it on real hardware or for rescue (covered in the Field Tech Guide). Dual-boot installs Linux alongside Windows, letting you choose at boot — the real-hardware daily-driver path, but it touches partitions (Field Tech Guide), so back up first and only do it once you're comfortable.

Try it — get to a prompt today Fastest path by situation. Windows + just want to learn the CLI: open PowerShell as admin, run wsl --install, reboot, and you're at an Ubuntu prompt. Want the full experience safely: install VirtualBox, grab the Ubuntu Desktop ISO, make a VM (give it 2+ CPUs, 4+ GB RAM, 25+ GB disk), install Ubuntu in it, and take a snapshot the moment it's set up. Mac: use VirtualBox/UTM, or just open Terminal — macOS is Unix-like, so most Part II commands work there too. Whichever you pick, the goal is the same: a prompt you can type into without fear.
From the field — the snapshot is your safety net and your teacher The single best thing you can do as a Linux beginner is work in a VM and snapshot a clean state before you experiment. It changes how you learn: instead of timidly avoiding anything that might break, you can run the scary command, watch what happens, and roll back if it goes wrong — which is how you actually understand what commands do. Wipe the wrong thing, mangle a config, fill the disk — revert and try again. The fear of breaking your system is the #1 thing that slows beginners down; a VM snapshot removes it entirely. (This is the same "lab where you're allowed to fail" idea from the Red Team Guide and Server Guide.) Set it up once, and break things on purpose — that's the fast lane to fluency.

Desktop vs Terminal — Chapter 4

Linux gives you two ways to drive: a graphical desktop that feels familiar, and a command line that feels alien — at first. Understanding what each is for, and why this book leans hard into the terminal, sets you up to actually become powerful instead of just comfortable.

The graphical desktop

Linux has full graphical desktop environments (DEs) — and unlike Windows or macOS, you choose yours. The common ones:

DesktopFeel
GNOMEModern, clean, opinionated (Ubuntu's default, Fedora)
KDE PlasmaPowerful, Windows-like, endlessly customizable
CinnamonTraditional desktop, very approachable (Linux Mint)
XFCE / LXQtLightweight — great on old or low-power hardware

The desktop handles the everyday: browser, files, settings, apps — and for normal computer use it's perfectly pleasant. That you can swap the entire desktop is itself a lesson in Linux's modularity (Chapter 1). But the desktop is not where Linux's real power lives.

The terminal — where the power is

The terminal (a window running a shell — Chapter 5) is the text interface, and it's the heart of Linux for reasons that become obvious with use:

  • Speed & precision — one typed command does what takes many clicks, exactly and repeatably.
  • Power — combine small tools with pipes (Chapter 10) to do things no GUI offers.
  • Automation — anything you can type, you can script and schedule (Chapter 18, 16). You can't automate clicking.
  • Remote & servers — most Linux machines (servers, cloud) have no GUI at all; you reach them over SSH (Chapter 21) and the terminal is the only interface.
  • It's universal — the same commands work on every distro, every server, every cloud instance, going back decades.

Opening a terminal & the prompt

On a desktop: it's an app called Terminal / Konsole / GNOME Terminal (often Ctrl+Alt+T). On a server: it's all you get. You'll see a prompt like:

desmond@laptop:~$

Read it: user (desmond) @ host (laptop), then the current directory (~ means your home), then a symbol: $ = normal user, # = root/administrator (be careful! — Chapter 12). The prompt waits for you to type a command and press Enter. That's the whole interface, and it's the same everywhere.

From the field — get comfortable being uncomfortable in the terminal Beginners cling to the GUI because the terminal feels intimidating — a blank prompt with no buttons to guide you. That discomfort is exactly the thing to push through, because the terminal is where Linux stops being "a different Windows" and becomes a genuinely more powerful way to work. The good news: the prompt is patient (it just waits), forgiving if you work in a VM (Chapter 3), and built around a small, consistent vocabulary you'll learn in Part II. Here's the mindset shift that helps: the GUI shows you a few things someone decided you'd want; the terminal lets you ask the machine anything. Spend the next chapters living at the prompt — force yourself to use it even for things you could click — and within weeks it'll feel faster than the mouse. Every Linux expert made exactly that crossing. This book is here to walk you across it.

Part II — The Command Line

The Shell & First Commands — Chapter 5

The shell is the program that reads what you type and makes it happen. Learn its grammar — command, options, arguments — and the handful of first commands, and you've crossed the threshold from "staring at a prompt" to "using Linux."

What the shell is

The shell is a program that interprets your typed commands. The default on most Linux systems is Bash (some use Zsh, which is similar). When you type a line and press Enter, the shell figures out what program to run, runs it, and shows you the output. That's the loop. The shell is also a full programming language (Chapter 18) — but it starts as just "type a command, get a result."

The anatomy of a command

Almost every command follows the same three-part grammar:

command  -options  arguments
   |          |          |
 what to    how to    what to
   run     do it       act on

ls       -l         /home        # list (-l = long format) the /home directory
  • Command — the program (ls, cd, cat).
  • Options/flags — modify behavior. Short form -l (single letter), long form --all (word). Combinable: ls -la = -l -a.
  • Arguments — what to act on (a file, a directory, text).

This grammar is consistent across nearly every command, which is why Linux gets easier fast: once you know the pattern, every new tool is "what's the command, what are its options."

Your first commands

CommandDoes
pwdPrint working directory — "where am I?"
lsList files in the current directory (ls -la = detailed + hidden)
cdChange directory (cd /etc, cd ~ = home, cd .. = up one)
catShow a file's contents
echoPrint text (echo hello)
whoamiShow your username
dateShow the date/time
clearClear the screen (or Ctrl+L)

The shortcuts that make you fast

These small habits separate the painfully slow from the fluent — learn them now:

  • Tab completion — start typing a command or filename and press Tab; the shell completes it (or shows options). Use this constantly — it's faster and prevents typos. This is the single most important habit.
  • Command history — press ↑/↓ to recall past commands; Ctrl+R to search history.
  • Editing — Ctrl+A (start of line), Ctrl+E (end), Ctrl+C (cancel the current command), Ctrl+U (clear line).
Try it — your first session Open a terminal (Chapter 3) and run these, watching what each does: 
whoami        # your username
pwd           # where you are (probably /home/you)
ls            # what's here
ls -la        # everything, in detail, including hidden files
cd /etc       # go to the system config directory
pwd           # confirm you moved
ls            # look around
cd ~          # go home
echo "hello, Linux"
Now do it again using Tab to complete names and ↑ to recall commands. That muscle memory is the foundation of everything.
From the field — Tab and history are 80% of being "fast" Watch an experienced Linux user and it looks like wizardry — they fly through the terminal. The secret is mostly two things, not memorized commands: Tab completion (they almost never type a full path; they type a few letters and Tab) and history (Ctrl+R and ↑ to reuse and edit past commands instead of retyping). Beginners type everything out fully, make typos, and get discouraged; pros lean on the shell's help. Build these two habits from your very first session and you'll feel fast within days. The commands themselves you'll learn naturally through use — and when you forget one, Chapter 9 shows you how to look it up. Fluency isn't memorization; it's good habits plus knowing how to find the rest.

The Filesystem & Navigation — Chapter 6

Linux organizes everything into one big tree starting at the root, `/` — no drive letters, no separate disks dangling in space. Learn the shape of the tree and how to move around it, and the filesystem stops being a maze and becomes a map you can read.

One tree, rooted at /

Unlike Windows (with C:, D:…), Linux has a single directory tree starting at / (the "root"). Other disks, USB drives, and partitions are mounted into this tree at some directory (Chapter 22) rather than getting their own letter. So a USB stick might appear at /media/you/USB — still part of the one tree. This unified model is simpler once it clicks: there's one place everything lives.

The Filesystem Hierarchy Standard (FHS)

The tree's layout is standardized, so these directories mean the same thing on every distro (full reference in Appendix B):

DirectoryWhat lives there
/The root of everything
/home/youYour personal files (the one place you fully own); shortcut ~
/rootThe root user's home (not the same as /)
/etcSystem-wide configuration — text files (the "control panel")
/bin, /usr/binPrograms (commands you run)
/varVariable data: /var/log (logs! — Ch 17), caches, spools
/tmpTemporary files, wiped on reboot
/devDevices as files — /dev/sda (a disk), /dev/null (the void)
/proc, /sysLive kernel/process info as virtual files (not real disk files)
/mnt, /mediaWhere external/other filesystems get mounted
/optOptional/third-party software

Absolute vs relative paths

  • An absolute path starts at root: /home/you/notes.txt — unambiguous from anywhere.
  • A relative path starts from where you are: notes.txt or ../photos/cat.jpg.
  • Special shortcuts: . = here, .. = parent directory, ~ = your home, - = the previous directory you were in.

Navigating

pwd              # where am I?
ls -la           # list here, detailed + hidden
cd /var/log      # go somewhere (absolute)
cd ..            # up one level
cd ~             # home (or just: cd)
cd -             # back to previous directory
tree             # show the tree visually (may need installing)

Hidden files start with a dot (.bashrc, .ssh/) and don't show in plain ls — use ls -a. These "dotfiles" hold your configuration (Chapter 19).

Try it — explore the tree 
cd /            # go to the root
ls              # see the top-level directories from the table above
cd /etc; ls     # config files live here
cat /etc/os-release   # which distro/version is this?
cd /var/log; ls # the system's logs
cd ~; ls -la    # home, with hidden dotfiles revealed
ls /dev | head  # devices-as-files (disks, terminals, etc.)
Wander around with cd and ls until the layout feels familiar — that familiarity is half of Linux competence.
From the field — knowing the tree is knowing the system The FHS isn't arbitrary trivia — it's a map that tells you where to look for anything. Something's misconfigured? It's in /etc. Need to read logs to diagnose a problem? /var/log (Chapter 17). Want to know what disks exist? /dev. Wondering what's running? /proc. Because the layout is standardized, this knowledge transfers to every Linux machine you'll ever touch — your laptop, a cloud server, an embedded router. Beginners feel lost because the tree is unfamiliar; spend an hour with the "Try it" box wandering through /etc, /var, and /home, and the maze becomes a neighborhood you know your way around. Everything else in this book happens somewhere in this tree.

Working with Files — Chapter 7

Creating, copying, moving, renaming, and deleting files and directories is the daily bread of the command line. The commands are short and the patterns consistent — and one of them, `rm`, deserves real respect because there's no undo.

The core file commands

CommandDoesExample
touchCreate an empty file (or update its timestamp)touch notes.txt
mkdirMake a directory (-p makes parents)mkdir -p proj/src
cpCopy (-r for directories)cp a.txt b.txt / cp -r dir1 dir2
mvMove or rename (same command!)mv old.txt new.txt / mv f.txt ~/docs/
rmRemove — permanent (-r dirs, -i ask first)rm old.txt / rm -r olddir
rmdirRemove an empty directoryrmdir emptydir
ln -sMake a symbolic link (a shortcut/pointer)ln -s /path/target linkname

Note the elegant overlap: mv both moves and renames (renaming is just moving to a new name in the same place). And copying or removing directories needs -r (recursive — act on the folder and everything inside).

Wildcards (globbing) — acting on many files

The shell expands wildcard patterns before running the command, so you can act on groups of files:

PatternMatches
*Any characters — *.txt = all .txt files; * = everything
?Any single character — file?.txt
[abc]Any one listed character — file[12].txt
{a,b}Brace expansion — cp report.{txt,bak}

So cp *.jpg ~/photos/ copies every JPEG, and rm *.tmp removes every temp file. Powerful — and, with rm, dangerous (below).

rm has no undo — and no recycle bin rm deletes permanently and immediately — there is no trash, no recovery (recovery is a forensic ordeal — Field Tech Guide). The genuinely dangerous combinations: rm -rf (recursive + force, no questions) on the wrong target, and wildcards gone wrong (a stray space in rm -rf / home/you deletes the whole system instead of your folder). Habits that save you: use rm -i (asks before each delete) while learning; run ls with the same pattern first (ls *.tmp) to see exactly what would be hit before deleting; double-check the path before pressing Enter; and never run rm -rf as root unless you've read it twice. "rm -rf /" is the legendary system-killer for a reason. Respect this one command and you'll be fine.
Try it — a safe file workout (in a throwaway dir) 
cd ~; mkdir -p sandbox; cd sandbox   # a safe play area
touch a.txt b.txt c.log              # make some files
mkdir backup
cp *.txt backup/                     # wildcard copy the .txt files
ls backup
mv a.txt renamed.txt                 # rename
ls
ls *.log                             # PREVIEW what a pattern matches...
rm *.log                             # ...then delete it (you saw it first)
cd ~; rm -r sandbox                  # clean up the whole sandbox
Notice the safe habit: ls the pattern before rm the pattern.
From the field — "ls before you rm" is the habit that saves careers Every long-time Linux user has a horror story (their own or a colleague's) about an rm that hit the wrong thing — a deleted home directory, a wiped server, a fat-fingered wildcard. The fix isn't fear, it's a reflex: preview destructive operations. Before rm *.log, run ls *.log and confirm the list is what you expect. Before rm -rf something, read the whole command twice and check your current directory with pwd. Keep alias rm='rm -i' in your dotfiles (Chapter 19) while you're learning. The command line trusts you completely and does exactly what you say — that's its power and its danger. A two-second preview is the cheapest insurance in computing.

Viewing & Editing Text — Chapter 8

Linux is built on text — config files, logs, scripts, data — so reading and editing text is constant. There's a tool for every situation: dump a small file, page through a big one, peek at the start or end, and edit when you need to.

Viewing files

CommandUse when
cat fileSmall file — dump it all to the screen
less fileBig file — scroll/search a page at a time (the workhorse)
head fileFirst 10 lines (head -n 20 for 20)
tail fileLast 10 lines — tail -f follows a growing file live (logs!)
wc fileCount lines/words/bytes (wc -l = line count)
nl fileShow with line numbers

less is the one to master for big files: Space/b page down/up, / search, n/N next/previous match, G end, g start, q quit. (It's also the pager man uses — Chapter 9.) And tail -f is how you watch logs scroll in real time (Chapter 17) — indispensable for "run something and watch what it does."

Editing files — the editors

EditorCharacter
nanoBeginner-friendly — on-screen shortcuts at the bottom (Ctrl+O save, Ctrl+X exit). Start here.
vimPowerful, modal, ubiquitous — steep but worth it; on every server (Chapter 20)
emacsAnother power editor; a whole ecosystem
GUI editorsgedit, VS Code, Kate — when you have a desktop

Use nano to start — it's obvious: nano file.txt, type normally, Ctrl+O to save (write Out), Ctrl+X to exit. The caret shortcuts (^X) shown at the bottom mean "Ctrl". You'll meet vim eventually because it's everywhere (every server has it), so Chapter 20 gives it a proper introduction — including the famous "how do I quit vim?" answer.

Creating text without an editor

You can write files straight from the shell using redirection (Chapter 10):

echo "hello" > greeting.txt        # write (overwrites)
echo "another line" >> greeting.txt # append
cat > quick.txt                     # type lines, then Ctrl-D to finish
Try it — view and edit 
cat /etc/os-release            # small file: cat is fine
less /etc/services             # big file: scroll (Space/b), search (/tcp), quit (q)
head -n 5 /etc/passwd          # first 5 user accounts
tail -n 5 /etc/passwd          # last 5
wc -l /etc/passwd              # how many accounts (lines)?
nano ~/mynotes.txt             # type something; Ctrl-O to save, Ctrl-X to exit
cat ~/mynotes.txt              # confirm it saved
(In less, if you get stuck, just press q.)
From the field — master less and tail -f, then learn one editor Two viewing tools earn their keep daily: less (for reading anything long — configs, logs, command output piped into it) and tail -f (for watching a log update live while you reproduce a problem — the classic "open the log in one window, trigger the issue in another"). Learn their handful of keys and you'll use them forever. For editing, start with nano — don't let anyone shame you; it's a real editor and it gets the job done while you're learning. But do plan to pick up basic vim eventually (Chapter 20), because it's installed on literally every Linux system including minimal servers and rescue environments, so the day you're on a box with only vim, you'll be glad you know how to open, edit, save, and quit. One editor you know cold beats five you sort-of know.

Getting Help — Chapter 9

Nobody memorizes every command and option — not even experts. The real skill is knowing how to look things up fast, and Linux is exceptionally good at documenting itself. Learn these and you're never truly stuck.

Pipes, Redirection & the Unix Way — Chapter 10

This is the chapter where Linux clicks. The Unix philosophy — small tools, combined — comes alive through pipes and redirection. Once you can chain simple commands into a pipeline, you can answer questions and solve problems that no single tool, and no GUI, can.

The three standard streams

Every command has three text streams, and understanding them unlocks everything:

  • stdin (standard input) — where it reads input from (default: your keyboard).
  • stdout (standard output) — where it writes results (default: the screen).
  • stderr (standard error) — where it writes error messages (default: the screen, separately).

The power comes from redirecting these — sending output to a file, or feeding one command's output into another's input.

From the field — thinking in pipelines is the Linux superpower The moment Linux goes from "a clunky text Windows" to "genuinely more powerful" is when you start thinking in pipelines. A question arrives — "how many unique IPs hit this server today?", "which files are eating my disk?", "what processes is this user running?" — and instead of hunting for an app, you compose the answer from small tools: filter with grep, transform with sed/awk/cut, sort, count with uniq -c and wc. Each tool does one thing; the pipe makes them a machine built for your exact question. Part III — System Fundamentals

Users, Groups & Permissions — Chapter 12

Linux is multi-user to its core, and its permission model — who can read, write, or execute what — is one of the first things that confuses newcomers and one of the most important to get right. Master the rwx model and sudo, and "Permission denied" stops being a mystery.

Users, groups, and root

Every file is owned by a user and a group, and every process runs as some user. The all-powerful administrator is root (user ID 0) — it can do anything, which is exactly why you don't run as root day-to-day. Instead you're a normal user and use sudo to run a single command with root powers when needed. Key files: /etc/passwd (accounts), /etc/group (groups), /etc/shadow (password hashes — Field Tech Guide). Groups let you grant a set of users shared access (e.g. the sudo/wheel group can use sudo; the docker group can run containers).

Reading permissions (the rwx model)

Run ls -l and each line begins with something like -rwxr-xr--. Decode it left to right:

  • First char: - file, d directory, l symlink.
  • Three trios: permissions for the owner, the group, and others (everyone else).
  • r w x: read, write, execute. (On a directory: r = list it, w = create/delete files in it, x = enter it.)

The numeric (octal) shorthand

Permissions are also written as three digits, summing r=4, w=2, x=1 per trio:

OctalMeansCommon for
755rwxr-xr-x — owner full, others read+runPrograms, directories
644rw-r--r-- — owner read/write, others readNormal files
600rw------- — owner onlyPrivate files (SSH keys! — Ch 21)
700rwx------ — owner only, executablePrivate scripts/dirs

Changing ownership and permissions

chmod 755 script.sh        # set permissions (numeric)
chmod +x script.sh         # add execute (symbolic) -- makes a script runnable
chmod u+rw,go-w file       # owner read/write, remove write from group/others
chown alice file          # change owner (needs sudo)
chown alice:devs file     # change owner and group
sudo command              # run one command as root
sudo -i                   # become root interactively (use sparingly)

The most common practical use: chmod +x to make a script executable (Chapter 18) — a file isn't runnable just because of its name; it needs the execute bit.

sudo and "Permission denied" — the daily realities Two things you'll hit constantly. "Permission denied" on a system file or directory almost always means you need sudo — you're a normal user trying to touch something root owns. Re-run with sudo and it usually works. But respect sudo: it's root power, and sudo rm -rf on the wrong thing (Chapter 7) wrecks the system with no undo. Rule of thumb: run as your normal user, reach for sudo only for the specific command that needs it, and read any sudo command twice before Enter. Avoid living in a root shell (sudo -i) — it removes the safety net of needing to opt in to danger.
From the field — permissions are 90% of "why won't this work?" An enormous share of Linux head-scratchers come down to permissions: a script that "won't run" (forgot chmod +x), a service that won't start (can't read its config or write its files), an SSH key that's "ignored" (it's 644 when SSH demands 600 — Chapter 21), a file you "can't edit" (owned by root, needs sudo). Train yourself to check permissions early with ls -l when something behaves oddly — read who owns it and what the rwx bits allow, and the problem usually names itself. The rwx model looks fiddly at first but it's small and logical: three actions (rwx) × three audiences (owner/group/others), plus root and sudo as the override. Get comfortable reading ls -l output fluently and you've eliminated a whole category of confusion.

Processes & Jobs — Chapter 13

Everything running on a Linux system is a process. Learning to see what's running, control it, and manage jobs in your terminal is core competence — the difference between "my system is doing something and I don't know what" and being in command of the machine.

What a process is

A process is a running program. Each has a PID (process ID), an owner (which user it runs as — Chapter 12), a parent (the process that started it), and a state. Processes form a tree: everything descends from PID 1 (systemd — Chapter 15). This is the same process model the Field Tech Guide covers for forensics — here it's about day-to-day control.

Package Management — Chapter 14

Installing software on Linux isn't "download an .exe and run it" — it's cleaner and safer than that. Package managers install from trusted repositories, handle dependencies automatically, and let you update your entire system with one command. This is one of Linux's genuinely superior ideas.

How it works (and why it's better)

A package manager installs software from repositories — curated, signed collections of software maintained by your distro. You ask for a program by name; the manager downloads it and everything it depends on, verifies signatures, and installs it in the right places. Benefits over the download-an-installer model: software is vetted and signed (less malware risk), dependencies are automatic (no "missing DLL" hunts), and you can update everything at once — OS and all apps — with a single command (Server Guide). It's a package store and an update system in one.

Boot & systemd — Chapter 15

What actually happens between pressing power and getting a login prompt? Understanding the boot sequence — and systemd, the program that brings the whole system up — turns "it won't boot" and "this service won't start" from mysteries into checklists.

The boot sequence, briefly

The chain (covered in depth in the Field Tech Guide):

  1. Firmware (UEFI/BIOS) powers on, runs hardware checks, finds the boot device.
  2. Bootloader (GRUB) loads — it shows the boot menu and loads the kernel. Its config is /boot/grub/grub.cfg.
  3. Kernel loads into memory, initializes hardware, mounts the root filesystem (with help from the initramfs, a tiny temporary filesystem with the needed drivers).
  4. systemd (PID 1) starts as the first process and brings up everything else — the rest of this chapter.

systemd: the init system

Once the kernel is up, it starts exactly one program — PID 1 — which on modern Linux is systemd. systemd is the init system: it starts, stops, and supervises everything else, and manages the system's services, mounts, devices, and timers. Everything running descends from it (Chapter 13). It's controlled by two main commands: systemctl (manage things) and journalctl (read logs — Chapter 17).

Units and targets

systemd manages everything as units — each a small config describing something to run or mount:

Unit typeIs
.serviceA program/daemon to run (sshd, nginx) — the main kind (Ch 16)
.targetA grouping / boot goal (like the old "runlevels")
.timerA scheduled trigger (the modern cron — Ch 16)
.mountA filesystem to mount (Ch 22)
.socketA socket that starts a service on demand

Targets are the boot goals that replaced runlevels: multi-user.target (full system, text/server), graphical.target (desktop on top of that), rescue.target (single-user, minimal — the "safe mode" for recovery, Field Tech Guide). The system boots toward its default target, activating all the units that target requires.

Inspecting the boot

systemctl get-default              # what target does it boot to?
systemctl list-units --type=service# what services are loaded
systemctl --failed                  # anything that FAILED to start (start here when broken!)
systemd-analyze                    # how long did boot take?
systemd-analyze blame              # which units were slowest to start?
journalctl -b                      # this boot's log (Ch 17)
Try it — examine your system's startup

systemctl --failed                     # hopefully empty
systemd-analyze                        # total boot time
systemd-analyze blame | head           # the slowest 10 units
systemctl status                       # overall system state + the unit tree
(On a VM or WSL this varies — WSL doesn't boot the same way, so use a VM for the full picture.)
From the field — systemctl --failed and journalctl -b are your first moves When a Linux system misbehaves at or after boot — a service didn't come up, something's broken — two commands start almost every diagnosis: systemctl --failed (which units failed?) and journalctl -b -1 (the previous boot's log — Chapter 17). Together they usually point straight at the problem: "the database service failed because its config has a typo," "the network mount timed out because the server's gone." You don't need to memorize systemd's full machinery to be effective — you need to know it's the thing that runs services (Chapter 16) and that these two commands surface what went wrong. The deep boot-repair side (GRUB, initramfs, rescue mode, chroot) lives in the Field Tech Guide; for daily Linux life, "check failed units, read the boot log" is the reflex that matters.

Services & Scheduling — Chapter 16

A service is a program that runs in the background, started and supervised by systemd — your web server, SSH daemon, database. Scheduling runs tasks automatically at set times. Together they're how Linux does work without you sitting there, and managing them is everyday admin.

Managing services with systemctl

A service (a .service unit — Chapter 15) is a background program, usually a daemon (its name often ends in d: sshd, httpd). You manage all of them with one verb-driven command, systemctl:

CommandDoes
systemctl status sshdIs it running? Why did it fail? + recent log lines — the diagnostic command
sudo systemctl start sshdStart it now
sudo systemctl stop sshdStop it now
sudo systemctl restart sshdRestart (after a config change)
sudo systemctl reload sshdReload config without a full restart (if supported)
sudo systemctl enable sshdStart automatically at boot
sudo systemctl disable sshdDon't start at boot
systemctl is-enabled sshdWill it start at boot?

The crucial distinction beginners miss: start ≠ enable. Start runs it now; enable makes it run at every boot. You usually want both (enable --now does both at once). A service you "started" but forgot to "enable" mysteriously vanishes after a reboot.

Scheduling: cron and systemd timers

To run things automatically on a schedule, there are two systems:

cron — the classic. Each line in a crontab is a schedule + a command. Edit yours with crontab -e. The five time fields are: minute, hour, day-of-month, month, day-of-week.

# min hour dom mon dow   command
0 2 * * *        /home/me/backup.sh        # every day at 2:00 AM
*/15 * * * *     /usr/local/bin/check.sh   # every 15 minutes
0 9 * * 1        /home/me/weekly.sh        # 9 AM every Monday (1 = Mon)
@reboot          /home/me/startup.sh       # once at every boot

(The cryptic * * * * * syntax is much easier with a helper like crontab.guru — remember the field order: min, hour, day, month, weekday.)

systemd timers — the modern alternative (.timer units, Chapter 15): more flexible, logged in the journal, and they can catch up missed runs. List active timers with systemctl list-timers. Both work; cron is simpler for quick jobs, timers integrate better with systemd.

Anatomy of a service status

systemctl status nginx packs a lot in: whether it's active (running) or failed, whether it's enabled (boots automatically), the main PID, and the last several log lines — often showing exactly why it failed. Reading this output is the core skill of service troubleshooting.

Try it — manage a service (SSH as the example) 
systemctl status ssh                 # (or sshd) is it running/enabled?
sudo apt install openssh-server      # if not present (Debian/Ubuntu)
sudo systemctl enable --now ssh      # start now AND at every boot
systemctl is-enabled ssh             # confirm it'll boot-start
systemctl list-timers                # scheduled systemd timers
crontab -l                           # your personal cron jobs (probably empty)
crontab -e                           # add one (try the @reboot example), save, then crontab -l
From the field — "enable AND start", and "status first" Two habits prevent most service headaches. Remember enable vs start: the #1 "it worked until I rebooted and now it's gone" bug is a service that was started but never enabled. Get in the habit of systemctl enable --now when you want something to stick. And always lead with systemctl status when a service misbehaves — it tells you running/failed/enabled state and shows the last log lines that usually contain the actual error, so you fix the cause instead of guessing. After a config change, restart (or reload) and re-check status to confirm it came back healthy — "change, restart, verify" is the safe loop. For scheduled jobs, cron is fine to start with; just double-check the five-field syntax (a misplaced field can run something every minute instead of once a day). These are the bread-and-butter moves of keeping a Linux system doing its job.

Logs & journald — Chapter 17

When something goes wrong on Linux, the answer is almost always written in a log — you just need to know where to look and how to read it. Reading logs is the single highest-value troubleshooting skill: it turns "it's broken and I don't know why" into "here's the exact error."

Two logging worlds

Modern Linux logs in two overlapping places:

  • journald — systemd's central logging system, queried with journalctl. It captures kernel messages, service output, and boot logs in one structured place. This is the primary one on modern distros.
  • Plain-text logs in /var/log — the traditional files, still used by many programs: /var/log/syslog or /var/log/messages (general), /var/log/auth.log or /var/log/secure (logins, sudo — security-critical), plus app-specific logs (e.g. /var/log/nginx/).

journalctl — the queries that matter

CommandShows
journalctlEverything (oldest first; it's in less — Ch 8)
journalctl -eJump to the end (newest)
journalctl -fFollow live — watch new logs as they arrive (like tail -f)
journalctl -bThis boot only — -b -1 = the previous boot (the one that failed)
journalctl -u sshdJust one service's logs — the everyday workhorse
journalctl -p errOnly error-priority and worse
journalctl --since "1 hour ago"By time window (also --until)
journalctl -kKernel messages (like dmesg)

These combine: journalctl -u nginx -p err --since today = today's nginx errors. That precision is why journald is powerful — you slice straight to the relevant lines instead of scrolling a giant file.

The plain-text side

For files in /var/log, use the text tools you already know (Chapter 8, 11):

sudo tail -f /var/log/syslog          # watch the general log live
sudo less /var/log/auth.log            # scroll the auth/login log
sudo grep "Failed password" /var/log/auth.log  # brute-force attempts (Server Guide)
dmesg -T                              # kernel ring buffer (hardware/driver), human timestamps

The troubleshooting workflow

The pattern that solves most problems: (1) something's wrong → (2) find the relevant log (a service? journalctl -u that-service; a boot issue? journalctl -b -1; a login/security issue? auth.log; hardware? dmesg) → (3) read the lines around the time it broke — the cause is almost always right before the symptom → (4) the error text usually names the fix. This is the exact same skill the Field Tech Guide and Server Guide teach — logs are how the machine tells you what happened.

Try it — read your system's logs

journalctl -u ssh --no-pager | tail   # recent SSH service activity
journalctl -f                   # follow live; in another terminal do something, watch it appear; Ctrl-C to stop

From the field — read the log before you guess (or reinstall) The number-one mistake beginners make when something breaks is to start randomly changing things, or to reinstall and hope. The number-one habit of people who are good at Linux is to read the log first. The system almost always tells you exactly what's wrong — "permission denied on /etc/foo," "address already in use," "no such file," "failed to parse config line 12" — if you just look. The instinct to build: when X fails, immediately run journalctl -u X (or check the relevant /var/log file) and read the last error before reaching for anything else. journalctl -f in one window while you reproduce the problem in another is especially powerful — you watch the failure happen in real time. Logs turn troubleshooting from frustrating guesswork into reading comprehension. It's the most valuable skill in this whole book.

Part IV — Power User

Shell Scripting — Chapter 18

A shell script is just a file of commands you'd type anyway — saved, so you can run them again, on a schedule, or share them. This is where Linux pays you back: anything you do twice, you can automate once. You already know most of the syntax; scripting just adds variables, conditions, and loops.

Your first script

A script is a text file of shell commands. Three steps make it runnable:

#!/bin/bash                  -- the "shebang": run this with bash
echo "Hello, $USER"
echo "Today is $(date)"
echo "You are in $(pwd)"
nano hello.sh               # write the above
chmod +x hello.sh           # make it executable (Ch 12)
./hello.sh                 # run it (./ = "in this directory")

The shebang (#!/bin/bash) on line 1 tells the system which interpreter to use. chmod +x is the step everyone forgets — without the execute bit, you get "Permission denied" (Chapter 12). ./ runs a script in the current directory.

The building blocks

FeatureSyntax
Variablesname="Sam" — no spaces around =; use as $name or ${name}
Command substitutiontoday=$(date +%F) — capture a command's output
Arguments$1 $2 (args passed in), $@ (all), $# (count)
Conditionalsif [ "$x" = "yes" ]; then ... fi
Tests-f file (exists?), -d dir, -z str (empty?), -eq -lt -gt (numbers)
Loopsfor f in *.txt; do ... done · while [ cond ]; do ... done
Exit status$? = last command's result (0 = success)

A realistic example

#!/bin/bash
# back up a directory, dated
SRC="$HOME/documents"
DEST="$HOME/backups"
mkdir -p "$DEST"
STAMP=$(date +%Y-%m-%d)
if [ -d "$SRC" ]; then
    tar -czf "$DEST/docs-$STAMP.tar.gz" "$SRC"
    echo "Backed up to $DEST/docs-$STAMP.tar.gz"
else
    echo "Error: $SRC not found" >&2
    exit 1
fi

That's real automation: it makes the destination if needed, dates the archive, checks the source exists, and reports success or failure. Schedule it with cron (Chapter 16) and you have automatic daily backups.

The scripting gotchas that bite everyone Bash is powerful but finicky. The classics: quote your variables ("$file" not $file) — an unquoted variable with spaces or wildcards breaks in surprising, sometimes destructive ways; no spaces around = in assignments (x=1, not x = 1); spaces are required inside [ ] tests ([ "$x" = "y" ]). And the big one for safety: test destructive scripts on throwaway data first — a script that rms based on a variable that's empty or wrong can do real damage (Chapter 7). Add set -euo pipefail near the top of serious scripts to make them stop on errors instead of charging ahead. Run in a VM (Chapter 3) while learning.
From the field — automate the thing you've done three times The scripting mindset is simple: if you've typed the same sequence of commands three times, turn it into a script. Backups, log cleanup, batch-renaming files, setting up a new machine, deploying an update — all the tedious repeatable work becomes a file you run once and forget (or schedule, Chapter 16). You already know the hard part — the commands — from Parts II–III; scripting just wraps them with a little logic. Start tiny: save a two-line script for something you do daily, then add a variable, then a condition, growing as you go. Bash is enough for most sysadmin glue; when scripts get complex (lots of logic, data structures, error handling), that's the signal to reach for Python instead. But the habit — "I'll never type that by hand again" — is what turns you from someone who uses Linux into someone who commands it.

Environment & Dotfiles — Chapter 19

Your shell's behavior — its prompt, its shortcuts, where it looks for commands — is configured by environment variables and "dotfiles." Learning to customize them turns the terminal from a generic tool into *your* tool, tuned to how you work.

Environment variables

Environment variables are named values the shell and programs read to know how to behave. See them all with env or printenv; the important ones:

Set one for the session with export NAME=value. To make it permanent, put the export line in a dotfile (below).

PATH — why "command not found" happens

PATH deserves special attention because it explains a common frustration. When you type ls, the shell searches each directory in PATH (in order) for a program named ls. If a command "isn't found" even though you installed it, its location probably isn't in PATH. Check with echo $PATH; add a directory with export PATH="$HOME/bin:$PATH" (this also explains why you run local scripts with ./script — the current directory isn't in PATH by default, for security). This is also why which command (Chapter 11) tells you which copy runs.

Dotfiles — your configuration

Configuration lives in hidden "dotfiles" in your home directory (Chapter 6). The key shell ones:

~/.gitconfigGit settings (covered in the Git & GitHub Guide)

Aliases and functions — the everyday wins

The most satisfying customization: aliases (shortcuts for commands) and small functions, added to ~/.bashrc:

# in ~/.bashrc

From the field — your dotfiles are worth keeping (and versioning) Over time you'll accumulate a set of aliases, functions, and settings that make your shell feel like home — and the day you get a new machine or log into a fresh server, you'll miss them badly. So two pieces of advice. First, build up your ~/.bashrc deliberately: every time you find yourself typing a long command repeatedly, add an alias; every time a default annoys you, change it. Small quality-of-life wins compound. Second, version your dotfiles with Git (a "dotfiles repo" is a rite of passage — the Git & GitHub Guide shows you how) so you can clone your entire personalized environment onto any new machine in seconds. And keep alias rm='rm -i' in there while you're learning — it's cheap insurance (Chapter 7). Customizing your environment is the moment Linux stops being someone else's OS and becomes yours.

Vim & Text Editors — Chapter 20

Vim is the editor you'll eventually have to know — it's on every Linux system, including minimal servers and rescue shells where nothing else is. It's intimidating because it's *modal* and works unlike any other editor, but the core is small. This chapter gets you productive (and, yes, teaches you how to quit).

Why bother with vim?

You can do most editing in nano (Chapter 8), so why learn vim? Because it's everywhere: every Unix-like system has vi/vim preinstalled, including stripped-down servers, containers, and rescue environments (Field Tech Guide) where nano may not exist. The day you SSH into a minimal server to fix a config and the only editor is vim, basic vim skills save you. It's also genuinely fast once learned — your hands never leave the home row. You don't need mastery; you need to confidently open, edit, save, and quit.

The big idea: modes

Vim is modal — this is what confuses everyone. Unlike normal editors where typing inserts text, vim has separate modes:

ModeWhat it's forEnter it by
NormalNavigating & commands (the default!)Esc (always returns here)
InsertActually typing texti (insert), a (append), o (new line)
VisualSelecting textv
Command-lineSave, quit, search/replace: (colon)

The mental model: you spend most time in Normal mode (navigating and issuing commands), dip into Insert to type, and hit Esc to come back. New users get stuck because they start typing in Normal mode and chaos ensues — press i first to type, Esc when done.

The survival kit

OPEN:    vim file.txt
i            # enter Insert mode -- now type normally
Esc          # back to Normal mode
:w           # write (save)
:q           # quit
:wq   or  ZZ # save and quit
:q!          # quit WITHOUT saving (discard changes) -- the escape hatch
How to quit vim (the famous question) The internet's favorite joke is people trapped in vim. The answer: press Esc (to ensure you're in Normal mode), then type :q! and Enter to quit without saving, or :wq to save and quit. That's it — Esc then :q! gets you out of any vim situation. Commit that one to memory and vim stops being scary.

From the field — learn enough vim to not be trapped, then grow as you like There's a spectrum here, and you only need the low end to be safe. Minimum: open, insert (i), escape (Esc), save (:w), quit (:q/:q!) — that's enough to edit a config on any server you'll ever touch, which is the real reason to learn it. Comfortable: add navigation, delete/yank/paste, search, and search-replace, and vim becomes genuinely fast. Power user: people build whole IDEs in vim — that's optional and a fun rabbit hole, not a requirement. Run vimtutor once to get past the modal weirdness, keep using nano for casual edits if you prefer, but make sure the survival kit is reflex. The worst outcome isn't "not mastering vim" — it's being on a minimal box, in vim, with no idea how to escape. Now you know: Esc, then :q!.

SSH & Remote Work — Chapter 21

Most Linux machines you'll ever use are somewhere else — a server in a datacenter, a cloud instance, a Raspberry Pi in a closet — and you reach them with SSH. Secure Shell is the universal remote-access tool, and getting comfortable with it (especially key-based login) is essential to real Linux work.

What SSH is

SSH (Secure Shell) gives you an encrypted command-line session on a remote machine — you type locally, it runs there. It's how the entire server and cloud world is administered (those machines usually have no screen or GUI — Chapter 4, Server Guide). The basics:

ssh user@hostname            # connect (asks for password the first time)
ssh user@192.168.1.50         # by IP
ssh -p 2222 user@host         # non-default port
exit                          # or Ctrl-D to disconnect

First connection shows a "host key fingerprint" prompt — that's SSH asking you to trust the server's identity; type yes (ideally after verifying it). After that, you're at the remote machine's prompt as if you were sitting there.

SSH keys — better than passwords

Password logins are weak and tedious. Key-based authentication is the standard: you generate a key pair — a private key (stays secret on your machine) and a public key (you put on servers). The server challenges you, your private key answers, and you're in — no password typed, and far more secure:

ssh-keygen -t ed25519                 # generate a modern key pair (press Enter for defaults)
ssh-copy-id user@host                  # install your public key on the server
ssh user@host                          # now logs in with no password

Your keys live in ~/.ssh/: id_ed25519 (private — never share) and id_ed25519.pub (public — safe to share). The same key pair is what GitHub uses for authentication (covered in the Git & GitHub Guide). Crucial: SSH refuses keys with loose permissions — your private key must be 600 and ~/.ssh must be 700 (Chapter 12); "key ignored" is almost always wrong permissions.

The SSH config file — shortcuts

Typing full connection strings gets old. ~/.ssh/config lets you define shortcuts (Chapter 19):

# ~/.ssh/config
Host myserver
    HostName 192.168.1.50
    User desmond
    Port 2222
# now just: ssh myserver

Moving files & staying connected

ToolDoes
scp file user@host:/pathCopy a file over SSH
rsync -av dir/ user@host:/path/Efficient sync (only changes) — the better choice for directories/backups
sftp user@hostInteractive file transfer over SSH
tmux / screenPersistent sessions — survive a dropped connection; reattach later

tmux is the unsung hero of remote work: run tmux on the server, start a long job, and even if your SSH connection drops (or you close your laptop), the job keeps running — reconnect and tmux attach to find it exactly as you left it (Chapter 13). It also splits your terminal into panes.

Try it — practice locally first 
ssh-keygen -t ed25519           # make a key pair (Enter through the prompts)
ls -l ~/.ssh                    # see id_ed25519 (private, 600) and .pub (public)
# if you have a second machine/VM/Pi:
ssh-copy-id user@other-machine  # install your key there
ssh user@other-machine          # log in with no password
# persistent session:
tmux                            # start; run something; press Ctrl-b then d to detach
tmux attach                     # reattach -- it's still there
From the field — keys not passwords, and live in tmux Two habits define comfortable remote work. Set up SSH keys early and stop using passwords — it's more secure (no password to guess or phish — Server Guide), more convenient (no typing), and it's the same key system GitHub and most cloud platforms use, so it pays off everywhere. The one gotcha to remember: if a key "doesn't work," check permissions first (chmod 600 the private key, 700 the ~/.ssh dir) — SSH silently ignores keys that are too readable. And use tmux for anything long-running over SSH — the number of people who've watched a 6-hour data transfer or compile die because their laptop went to sleep is endless, and tmux makes that impossible (the session lives on the server, not your connection). These two habits separate "SSH is scary" from "I live on remote machines all day." Remote-first is normal Linux life; get fluent at it.

Part V — Administration

Storage, Filesystems & Mounting — Chapter 22

Disks, partitions, filesystems, and mounting — how storage actually attaches to that single directory tree from Chapter 6. This is everyday admin: plugging in a drive, seeing what's there, mounting it, and making it stick across reboots.

The layers: disk → partition → filesystem → mount point

Storage stacks up in layers (the physical side is in the Field Tech Guide):

  • A disk is the device (/dev/sda, /dev/nvme0n1).
  • It's divided into partitions (/dev/sda1, /dev/sda2).
  • Each partition holds a filesystem (ext4, etc.) that organizes files.
  • To use it, you mount it onto a directory (a "mount point") in the tree (Chapter 6).

Seeing your storage

lsblk                  # tree of disks/partitions + mount points -- the go-to overview
lsblk -f               # + filesystem types and labels
df -h                  # mounted filesystems + how full (human-readable)
du -sh *               # size of each item here (find what's eating space)
sudo blkid             # UUIDs of partitions (used in fstab)
free -h                # RAM/swap usage (not disk, but related)

lsblk is your map; df -h answers "is a disk full?"; du -sh * (often du -sh * | sort -h) hunts down what filled it.

Common filesystems

FilesystemUse
ext4The reliable Linux default
Btrfs / ZFSAdvanced: snapshots, checksums, pooling
XFSHigh-performance, common on enterprise/RHEL
FAT32 / exFATUSB sticks, cross-platform sharing
NTFSWindows disks (readable via ntfs3)
swapDisk used as overflow when RAM fills

Mounting

sudo mount /dev/sdb1 /mnt          # attach a partition to /mnt
ls /mnt                            # now you can read it
sudo umount /mnt                   # detach cleanly BEFORE unplugging
sudo mount -t ntfs3 /dev/sdb1 /mnt # mount a Windows NTFS disk

Desktops auto-mount USB drives (under /media/you/...), but on servers and for fixed drives you mount manually or via fstab. Always umount before unplugging a drive — pulling it mid-write corrupts data.

Making mounts permanent: /etc/fstab

To mount a drive automatically at every boot, add a line to /etc/fstab — the filesystem table:

# UUID                                  mountpoint  fstype  options       dump pass
UUID=1234-abcd                          /data       ext4    defaults      0    2

Use the UUID (from blkid), not /dev/sdb1 — device letters can change between boots, but UUIDs are stable. Test with sudo mount -a (mounts everything in fstab) before rebooting, because a bad fstab line can prevent boot (Field Tech Guide).

The fstab trap — and the full-disk emergency Two storage dangers. A broken /etc/fstab can stop the system booting — a typo or a UUID for a disk that isn't there drops you into emergency mode (Field Tech Guide). Always run sudo mount -a after editing fstab to catch errors while you can still fix them, and keep a backup of the file. A full disk breaks everything — when / hits 100% (often /var/log filling up, or runaway files), services fail in confusing ways. df -h reveals it instantly, and du -sh /var/* | sort -h finds the culprit. Watching disk usage is basic system hygiene; a full root filesystem is one of the most common "everything is suddenly broken" causes.
From the field — lsblk to see, df to check full, du to find the hog Three commands handle nearly all everyday storage questions, and they're worth instant recall. lsblk — "what disks and partitions exist and where are they mounted?" (your storage map). df -h — "is anything full?" (the health check). du -sh * | sort -h — "what's taking the space?" (the investigation, run from inside the full directory). When a server mysteriously misbehaves, "is the disk full?" should be one of your first checks — it's a shockingly common root cause and df -h answers it in one second. For mounting, prefer UUIDs in fstab, always test with mount -a, and never yank a drive without umount. The deeper storage topics — LVM, RAID, the physical hardware — live in the Server Guide and Field Tech Guide; this is the daily core.

Networking from the CLI — Chapter 23

Sooner or later you need to answer "what's my IP?", "why can't I reach this server?", or "what's listening on this port?" — all from the command line, often on a machine with no GUI. These are the everyday Linux networking commands; the deep theory lives in the Networking Field Guide.

Seeing your network configuration

ip a                    # your interfaces and IP addresses (the modern command)
ip route                # the routing table -- where traffic goes (default gateway)
hostname -I             # just your IP address(es), quickly
cat /etc/resolv.conf     # which DNS servers you're using

(ip replaces the old ifconfig; you'll still see ifconfig on older systems.) The essentials these reveal: your IP address (who you are on the network), your default gateway (the router traffic exits through), and your DNS servers (what turns names into IPs) — all explained in the Networking Field Guide.

Testing connectivity — the layered approach

When "the network is down," walk up the layers (the same diagnostic ladder as the Networking Field Guide):

CommandTests
ping 8.8.8.8Can I reach the internet by IP? (routing works)
ping google.comCan I reach it by name? (if IP works but name doesn't → DNS problem)
ip aDo I even have an IP? (a 169.254.x = DHCP failed)
traceroute hostWhere along the path does it break?
dig google.com / nslookupDNS resolution specifically
curl -I https://siteCan I actually fetch from a web server?

The classic deduction: ping 8.8.8.8 works but ping google.com fails → your connection is fine but DNS is broken — the single most common "internet is down" cause (Networking Field Guide).

What's listening / connected

ss -tulpn               # listening TCP/UDP ports + which process (the modern netstat)
ss -tn                  # active TCP connections
curl ifconfig.me        # your PUBLIC IP (as seen from the internet)

ss -tulpn answers "what's listening on this machine, and what program owns each port?" — essential for "is my web server actually up on port 80?" and for spotting unexpected open ports (a security check — Server Guide).

Transferring & fetching

  • curl — fetch URLs, hit APIs, download files (curl -O url). The Swiss-army knife of HTTP from the CLI.
  • wget — download files/sites (wget url); great for grabbing things to a server.
  • scp / rsync — copy files to/from remote machines over SSH (Chapter 21).
Try it — explore your network 
ip a                      # your IPs and interfaces
ip route                  # your default gateway
ping -c 4 8.8.8.8         # reach the internet by IP (4 pings)
ping -c 4 google.com      # by name -- tests DNS too
dig +short google.com     # what IP does the name resolve to?
ss -tulpn                 # what's listening on this machine
curl -I https://example.com   # fetch just the headers from a web server
From the field — the four commands that diagnose most network issues On any Linux box, "the network isn't working" usually yields to four commands in sequence: ip a (do I have a valid IP, or a failed-DHCP 169.254 address?), ping 8.8.8.8 (can I route to the internet at all?), ping google.com (if the IP ping works but this doesn't, it's DNS — the most common culprit), and ss -tulpn (what's actually listening, when a service "isn't reachable"). Each step isolates one layer, and the step where it breaks names the problem — the triage mindset applied to networking. You don't need deep networking theory to fix most day-to-day issues; you need these commands and the habit of walking up the layers instead of guessing. When you do want the why — how IP, DNS, routing, and ports actually work — the Networking Field Guide is the companion to this chapter.

Hardening, Backups & Health — Chapter 24

A system you rely on needs to be kept secure, backed up, and healthy. This chapter is the maintenance mindset: the handful of high-impact habits that keep a Linux machine safe and running — without turning you into a full-time administrator.

Basic hardening (the high-impact basics)

You don't need to be a security expert to cover the essentials (the deep version is the Server Guide):

HabitWhy
Keep it updatedapt/dnf upgrade regularly — patching closes known holes (Ch 14). The single biggest win.
SSH keys, not passwordsDisable password SSH login; use keys (Ch 21). Kills brute-force.
Least privilegeRun as a normal user; use sudo only when needed (Ch 12). Don't live as root.
Firewall onAllow only the ports you actually use (below).
Remove what you don't needFewer running services = smaller attack surface. Disable unused ones (Ch 16).
Strong, unique passwordsFor any account that has one (Field Tech Guide).

The firewall

Linux's firewall is the kernel's netfilter, controlled by friendly front-ends:

# ufw (Ubuntu/Debian -- the easy one):
sudo ufw allow ssh        # permit SSH
sudo ufw enable          # turn the firewall on
sudo ufw status          # see the rules
# firewalld (Fedora/RHEL): firewall-cmd --add-service=ssh --permanent
Don't lock yourself out The classic self-inflicted disaster: enabling a firewall (or changing SSH config) on a remote machine and cutting off your own SSH access — now you can't get back in to fix it. Always allow SSH before enabling the firewall (ufw allow ssh then ufw enable), and when changing SSH/firewall settings remotely, keep your current session open and test a new connection before closing it. On a remote box with no console access, a lockout can mean rebuilding the server. This is the #1 way people break their own remote systems — respect it.

Backups — the rule that saves you

The hard truth: it's not if you'll lose data, it's when — disk failure, fat-fingered rm (Chapter 7), ransomware, mistake. Backups are the only real protection. The standard is 3-2-1: 3 copies, on 2 different media, with 1 off-site (Server Guide). Practical tools:

tar -czf backup-$(date +%F).tar.gz ~/important   # simple dated archive
rsync -av --delete ~/data/ /mnt/backup/data/    # efficient mirror (only changes)
rsync -av ~/data/ user@host:/backups/            # to a remote machine (Ch 21)

Automate them with cron or a timer (Chapter 16). And the rule everyone forgets: a backup you've never restored is not a backup — test that you can actually recover, periodically.

Health & monitoring

From the field — the five habits that keep a system happy You don't need to be a sysadmin to keep a Linux machine healthy and secure — just a few high-leverage habits, done consistently. (1) Update regularly — the biggest security win, one command (Chapter 14). (2) Back up, and test the restore — the only thing that saves you from the inevitable data-loss day; automate it (Chapter 16) and actually verify it works. (3) SSH keys + firewall, set up carefully so you don't lock yourself out. (4) Run as a normal user, sudo only when needed. (5) Glance at health — df -h and systemctl --failed occasionally catch problems before they become outages. That's it — the 20% that delivers 80% of safety and stability. When you need the full depth (CIS hardening, real monitoring, disaster recovery), the Server Guide is the next step. For your own machines, these five habits are plenty.

  2. Kill it by PID and by job number.
  3. Open top (or htop), find the biggest CPU/memory user, quit.
  4. Goal: see, find, and stop any process.

Lab 6 — Install & manage a service (Ch 14, 16)

  1. Install a package (htop or nginx) with your package manager.
  2. For a service (e.g. ssh/nginx): systemctl status, then enable --now, confirm with is-enabled.
  3. Read its logs: journalctl -u <service>.
  4. Goal: the install → enable → verify → read-logs loop.

Lab 7 — Write a script (Ch 18)

  1. Write a script that takes a directory as $1, checks it exists, and counts the files in it.
  2. chmod +x it; run it with an argument; run it with a bad argument and see your error handling.
  3. Bonus: make it tar the directory with a dated filename (the backup example).
  4. Goal: you can automate a real task.

Lab 8 — Customize your shell (Ch 19)

  1. Add three aliases and an export EDITOR= to ~/.bashrc; source it; use them.
  2. Inspect $PATH; understand why ./script needs the ./.
  3. Goal: the shell is now yours.

Lab 9 — Logs & troubleshooting (Ch 17)

  1. Run journalctl -f in one terminal; in another, restart a service — watch the log react.
  2. Find this boot's errors: journalctl -b -p err.
  3. Search auth.log (if present) for login events.
  4. Goal: when something breaks, you read the log first.

Lab 10 — Remote & persistent (Ch 21) (needs a 2nd machine/VM, optional)

  1. Generate an SSH key, copy it to another machine, log in without a password.
  2. Start tmux, run a long command, detach (Ctrl-b d), reattach.
  3. rsync a directory to the other machine.
  4. Goal: comfortable working on remote systems.
From the field — the only way to learn Linux is the keyboard You can read this entire book and remember almost none of it — or do these ten labs and own it. That's not a knock on reading; it's how skills work. The commands only stick when your fingers have typed them, made the mistakes, and figured out the fixes. So treat the labs as the actual curriculum and the chapters as the reference. Do them in a VM where breaking things is free (Chapter 3), redo any that felt shaky a week later from memory, and — the master move — find a small real project (host a website, automate a backup, set up a home server, build a dotfiles repo) and do it on Linux. Nothing teaches like a real goal you care about. Reading got you the map; the keyboard gets you the territory.

Two config-editing safety notes Edit /etc/sudoers only with sudo visudo — it checks your syntax before saving; a broken sudoers file can lock you out of sudo entirely. And back up a config before editing it (sudo cp file file.bak) — especially fstab, sshd_config, and anything in /etc that affects boot or remote access, so you can always revert (Ch 22, 24).
From the field — "where's the config for X?" almost always answers itself Because the layout is standardized, you can usually guess where something lives: system config → /etc (often /etc/<program>/ or /etc/<program>.conf); your personal config → a dotfile in ~ or ~/.config/; logs → /var/log or journald (Ch 17); the program itself → which <cmd> (Ch 11). When the guess fails, find /etc -name "*program*" or the program's man page (which lists its config files) gets you there. This map is one of Linux's quiet gifts: learn it once and it's true on every machine you'll ever touch — your laptop, a server, a container, a router.
