The VS Code Field Guide

The VS Code Field Guide

The Editor, Learned Properly
Most people use maybe five percent of VS Code: they open files, they type, they save. That works, and it also means doing by hand a dozen things the editor would do instantly — jumping to a definition, renaming a symbol everywhere at once, stepping through a running program instead of guessing with print statements, editing code on a robot across the room as if it were local. This book covers the parts that actually change how fast you work, in roughly the order you should learn them, and skips the parts you can safely ignore.
A companion in the Field Guide series · pairs with the Python, Git & Linux guides · offline, self-contained
This book is interactive Press Ctrl+K to search every heading; tick the sidebar checkboxes to track progress (or press R); use ←/→ to move chapter to chapter; toggle light/dark and text size top-right; hover any command block to copy it. Look for ⌨️ Try it boxes — do them in VS Code, because editor skills are pure muscle memory and reading about a shortcut does nothing. Everything works offline.

How to Read This Book — Front Matter

An editor is a tool you'll spend thousands of hours inside, so a few hours learning it properly pays back at an absurd rate. But you don't need all of it at once — this book is deliberately ordered so you can stop after Part II and already be far ahead of where most people ever get.

The journey, part by part Part I (Getting Oriented) is installation and the layout — what every panel is for, and the command palette, which is the single most important thing in the entire application. Part II (Daily Driving) is the everyday skill set: extensions and picking the right Python interpreter, the built-in terminal, the editing tricks that save real time, and how to move around a codebase you didn't write. Part III (Real Work) is what separates casual use from professional use — the debugger, Git integration, and remote development, which is how you'll actually work on a robot or lab machine. Part IV is troubleshooting, labs, and reference.
How to actually use it Have VS Code open on a second window or monitor and do things as you read. Shortcuts are shown for Windows/Linux with the macOS equivalent in brackets — as a rule, Ctrl becomes ⌘ and Alt becomes ⌥. If you only have twenty minutes, read Chapter 4 on the command palette and Chapter 9 on debugging; those two chapters contain most of the value in this book. If you're setting up for a robotics class, Chapter 5 and Chapter 11 are the ones you'll need first.

Part I — Getting Oriented

What VS Code Is — Chapter 1

Knowing what kind of tool this is explains most of its design decisions — including the ones that seem strange at first, like an editor that doesn't understand your language until you tell it to.

An editor with an extension habit

VS Code is a source-code editor, not an IDE in the traditional sense. Out of the box it edits text, understands JSON and JavaScript, and does very little else. Everything language-specific — Python autocomplete, C++ navigation, ROS 2 message support — arrives through extensions you install. That's the central design bet: a fast, small core, plus a marketplace that covers everything else.

The practical consequence for a newcomer is the one thing worth knowing today: if VS Code seems not to understand your code, you're probably missing an extension (Chapter 5). It isn't broken and it isn't a bad editor for your language; it just hasn't been told about it yet.

Where it sits

VS CodeFull IDE (PyCharm, Visual Studio)Terminal editor (vim, nano)
StartupFastSlowInstant
Language supportVia extensionsDeep, built inMinimal
Works over SSHYes, seamlessly (Ch 11)Paid tiers onlyNatively — it's already there
Multi-language projectExcellentUsually one primary languageFine, but no tooling
Best atAlmost everything, adequatelyOne language, superblyQuick edits on a server

None of these replaces the others. It's genuinely worth knowing enough vim to fix a config file on a machine where you can't install anything — the Linux Field Guide covers that. But for daily project work, VS Code's combination of speed, breadth, and remote support is hard to beat.

A note on the name

"Visual Studio Code" and "Visual Studio" are unrelated products that unhelpfully share a brand. Visual Studio is a large Windows-only IDE for .NET and C++. VS Code is the cross-platform editor this book is about. There's also VSCodium, a build of the same open-source code without Microsoft's telemetry and branding — identical to use, though a few Microsoft-licensed extensions (including the Remote-SSH pack in Chapter 11) aren't available on it.

Installing & First Launch — Chapter 2

Ten minutes, most of it optional. The one setting genuinely worth changing on day one is the code command, because it's how the editor and the terminal stop being separate worlds.

Install

PlatformHow
Ubuntu / Debiansudo snap install code --classic, or the .deb from code.visualstudio.com
FedoraAdd Microsoft's repo, then sudo dnf install code
macOSbrew install --cask visual-studio-code, or drag the download to Applications
Windowswinget install Microsoft.VisualStudioCode, or the installer

Verify with code --version. On Windows, tick "Add to PATH" and both "Open with Code" context-menu options during install — they're genuinely convenient.

The code command

On Linux and Windows this is set up for you. On macOS you have to ask: open the command palette (Chapter 4) and run Shell Command: Install 'code' command in PATH. Now the terminal and the editor connect:

code .                    # open the current folder — the one you'll use constantly
code myfile.py            # open one file
code file1.py file2.py    # open several
code -d old.py new.py     # open a diff view of two files
code -r .                 # reuse the existing window instead of a new one
code --list-extensions    # what's installed
code --install-extension ms-python.python

code . is the habit to build. Navigate to a project in your shell, type it, and you're working — no file dialogs.

Folders, not files

This is the one conceptual thing to get right immediately. VS Code is designed around opening a folder, not individual files. The open folder becomes your workspace, and nearly everything good depends on it: project-wide search, Git integration, the debugger, per-project settings, and the extensions' ability to understand how your code fits together. Open a lone file and you get a text editor. Open the folder and you get the tool this book describes.

Open the right folder Open your project root — the folder containing .git, your requirements.txt, and your source. Not your home directory (VS Code will try to index everything you own and crawl), and not a subfolder three levels down (Git integration and project-wide search will both quietly miss things). If you're already in the wrong one, File → Open Folder is a two-second fix. When people report that VS Code is "slow" or that search "doesn't find things", the opened folder is the cause more often than anything else.

The status bar is a dashboard

It's easy to ignore and it's constantly telling you useful things. Left to right you'll typically find the remote indicator (green, far left — tells you if you're editing over SSH, Chapter 11), the Git branch and sync state, the error and warning counts, and on the right the language mode, line ending, encoding, and — critically for Python work — the selected interpreter. Every one of those is clickable and most open the relevant picker directly. Glancing at it before asking "why isn't this working" resolves a surprising share of problems.

Splitting is worth the habit for the common case of a test file beside the code it tests, or a config file beside the script that reads it.

The Command Palette — Chapter 4

If you read one chapter, read this one. Every command in VS Code — every extension's commands too — is reachable from a single search box, which means you never have to know where anything is in a menu.

The shortcut

Ctrl+Shift+P     Command palette            [Cmd+Shift+P]
Ctrl+P           Quick Open — go to file    [Cmd+P]

Ctrl+Shift+P opens a fuzzy search over every available action. You don't need exact names — type "interp" and you'll find Python: Select Interpreter. This is why VS Code's menus don't matter much: describing what you want is faster than remembering where it lives.

Quick Open and its prefixes

Ctrl+P opens a file by fuzzy name — typing mtst will find my_test_script.py. It also takes prefix characters that switch what you're searching, and these are the real power feature:

TypeSearches
filenameFiles by name
>commandCommands (same as the palette)
@symbolSymbols in the current file — functions, classes
@:Symbols in the current file, grouped by kind
#symbolSymbols across the whole project
:42Jump to line 42
?Lists every prefix, if you forget

@ is the sleeper hit here: in a 900-line file you didn't write, Ctrl+P then @ gives you an instant, searchable table of contents of every function in it.

Try it — commit to the palette for one session 
Ctrl+Shift+P  ->  "settings json"     open settings as a file
Ctrl+Shift+P  ->  "toggle word wrap"  wrap long lines
Ctrl+Shift+P  ->  "change language"   set syntax for the current file
Ctrl+Shift+P  ->  "keyboard short"    the full shortcut list
Ctrl+P        ->  "@"                 outline the current file
Ctrl+P        ->  ":50"               jump to line 50
Deliberately don't touch the menu bar for one working session. It feels slow for about ten minutes and then the menus start feeling slow instead.
From the field — the palette is the documentation Here's the habit that makes VS Code click, and it inverts how people usually learn software. When you wonder whether the editor can do something, don't search the web — open the palette and type the thing you want. "sort lines", "convert indentation", "rename symbol", "compare with saved", "record keyboard shortcut". About eighty percent of the time it's already there, often from an extension you forgot you installed. This is also how you discover features you'd never have gone looking for, because the fuzzy search surfaces neighbours of what you typed. People who have used VS Code for years and still navigate by menu are doing perhaps a third of the work they could be, and the difference isn't talent or memorized shortcuts — it's one reflex, applied constantly.

Part II — Daily Driving

Extensions & the Interpreter — Chapter 5

Extensions are how VS Code learns your language. This chapter installs the few that matter and then solves the single most common Python-in-VS-Code problem: the editor using a different interpreter than your terminal.

Installing extensions

Ctrl+Shift+X opens the Extensions view. Search, click Install. Or from the terminal:

code --install-extension ms-python.python
code --list-extensions
code --uninstall-extension some.extension

Resist installing dozens. Each one costs startup time and some conflict — two formatters fighting over the same file is a genuinely confusing afternoon. Appendix B lists the ones worth having.

The Python extension

ms-python.python brings IntelliSense, linting, debugging, test discovery, and notebook support. Install it and reload. It in turn installs Pylance, the language server that does the actual code intelligence.

Selecting the interpreter — the important part

The Python Environment Field Guide makes the case at length: a Python "environment" is an interpreter plus its packages, and problems come from using the wrong one. VS Code has its own interpreter selection, separate from whatever your terminal has activated. If they disagree, you get the classic symptom — a squiggly red underline under import numpy in the editor while the same script runs fine in the terminal.

Ctrl+Shift+P  ->  Python: Select Interpreter

Pick the one inside your project's .venv. VS Code auto-detects a .venv folder in the project root, which is exactly why that naming convention is worth following. Your choice is remembered per project, and the current interpreter is always visible in the status bar — click it to change.

The editor and the terminal are two different selections Selecting an interpreter tells VS Code which Python to use for IntelliSense, linting, running, and debugging. It does not retroactively change terminals you already had open. VS Code auto-activates the selected environment in new integrated terminals, so the reliable move after switching interpreters is to kill the terminal and open a fresh one. When the editor and terminal disagree about whether a package exists, this is nearly always why. The diagnostic from the Python guide settles it in one line — run python -m pip --version in the terminal and compare its path against the status bar.

Linting and formatting

Modern setups use Ruff for both, replacing the older flake8/black/isort combination and running fast enough to be invisible. Install the Ruff extension, then set it as the formatter and turn on format-on-save:

{
  "[python]": {
    "editor.defaultFormatter": "charliermarsh.ruff",
    "editor.formatOnSave": true,
    "editor.codeActionsOnSave": { "source.organizeImports": "explicit" }
  }
}

Format-on-save is worth turning on immediately. It ends every argument about style, produces smaller and more readable Git diffs (Git guide), and removes a whole category of thing you'd otherwise think about while writing code.

The Integrated Terminal — Chapter 6

A real terminal, docked in the editor, already in your project directory and with your virtual environment activated. It removes the constant window-switching that otherwise eats a working day.

Opening and managing

Ctrl+`            Toggle the terminal          [Ctrl+`]
Ctrl+Shift+`      New terminal instance
Ctrl+Shift+5      Split the terminal
Ctrl+PageDown     Next terminal
Ctrl+Shift+C      Copy   (Ctrl+C sends SIGINT, as it should)
Ctrl+Shift+V      Paste

Note the copy/paste shortcuts. In a terminal, Ctrl+C must keep meaning "interrupt the running process" — so copy moves to Ctrl+Shift+C. This trips up everyone once.

What it gives you for free

  • It starts in your project folder, so no cd to get going.
  • It auto-activates your selected venv (Chapter 5) in new terminals.
  • File paths in output are clickable — Ctrl+click a traceback line to jump straight to that line of that file. This alone is worth using it for.
  • Split terminals let you run a server in one and commands in another, both visible.
  • Over SSH, terminals open on the remote machine (Chapter 11).

Choosing your shell

Run Terminal: Select Default Profile from the palette. On Windows the choice matters more than elsewhere: PowerShell is the sane default, but if you're following Linux-flavoured instructions — which most robotics documentation is — use WSL or Git Bash so that ls, source, and forward-slash paths behave as written.

Editing Superpowers — Chapter 7

A dozen shortcuts that replace a lot of tedious manual editing. These are the ones that genuinely pay for themselves; there are hundreds more you can safely never learn.

Multi-cursor

The headline feature. Multiple cursors, all typing at once:

Alt+Click              Add a cursor wherever you click
Ctrl+Alt+Up / Down     Add a cursor above / below      [Cmd+Opt+Up/Down]
Ctrl+D                 Select next occurrence of the selection  [Cmd+D]
Ctrl+Shift+L           Select ALL occurrences at once   [Cmd+Shift+L]
Shift+Alt+drag         Column (box) selection
Escape                 Back to one cursor

Ctrl+D repeatedly is the everyday one: select a variable name, press it four times to grab the next four occurrences, and type the new name once. For renaming a variable properly across a whole project, though, use rename symbol instead — it understands scope, whereas multi-cursor is just clever text matching.

Moving and duplicating lines

Alt+Up / Alt+Down            Move the line up / down          [Opt+Up/Down]
Shift+Alt+Up / Down          Duplicate the line up / down
Ctrl+Shift+K                 Delete the whole line
Ctrl+Enter                   New line below, from anywhere in the line
Ctrl+/                       Toggle comment
Shift+Alt+A                  Toggle block comment

Alt+Up/Down becomes reflexive fast — reordering statements without cut-and-paste, and without ever losing a line to a mistimed paste.

Selection and search

Ctrl+L              Select the current line
Ctrl+Shift+\        Jump to the matching bracket
Ctrl+F / Ctrl+H     Find / Replace in this file
Ctrl+Shift+F        Find across the whole project
Ctrl+Shift+H        Replace across the whole project
Alt+Enter           (in Find) select every match at once

Project-wide search supports regular expressions (the .* icon) and glob filters for included and excluded files. Ctrl+Shift+H shows a full diff preview before you commit to anything, which makes bulk replacement far less nerve-wracking than it sounds.

Snippets and Emmet

Type a prefix and press Tab. Extensions ship language snippets, and you can define your own via Snippets: Configure Snippets in the palette. For a robotics course, a snippet for your DDS subscriber boilerplate or a ROS 2 node skeleton saves genuine time across a semester.

Navigating a Codebase — Chapter 8

Most real work is reading code you didn't write — vendor SDKs, a teammate's module, an open-source library. These are the tools that turn "where on earth is this defined" into one keystroke.

Jumping around

F12                  Go to definition
Alt+F12              Peek definition — inline, without leaving the file
Shift+F12            Find all references
Ctrl+Click           Same as F12, with the mouse
Alt+Left / Right     Navigate back / forward through your jumps
Ctrl+Shift+O         Go to symbol in this file
Ctrl+T               Go to symbol across the project
F2                   Rename symbol — everywhere, correctly

F12 and Alt+← are a pair worth internalizing together: dive into a definition, read it, come straight back. That loop is how you read an unfamiliar SDK without losing your place, and it's the difference between "reading the code" and "grepping and hoping".

F2 is not find-and-replace

F2 (rename symbol) uses the language server's actual understanding of your code. It renames the variable in every place that refers to this variable — and correctly leaves alone a different variable of the same name in another scope, and the same word inside an unrelated string. Find-and-replace can't distinguish those and will happily corrupt your code. Use F2 for anything that has a definition.

Problems and the outline

The Problems panel (Ctrl+Shift+M) aggregates every error and warning across the project from all extensions — the fastest way to see whether a change broke something elsewhere. The Outline view, at the bottom of the Explorer, is a live tree of the current file's classes and functions; in a long vendor file it's the fastest way to see the shape of what you're looking at.

From the field — reading beats searching The instinct most beginners bring to an unfamiliar codebase is to search for a string and scroll. It works, slowly, and it teaches you almost nothing about how the code is organized. The professional pattern is to follow the structure: start at the entry point, F12 into the first call you don't understand, read it, Alt+← back, continue. Ten minutes of that gives you a mental map of the call graph, which is knowledge that keeps paying off; ten minutes of scrolling gives you one answer. This matters most exactly where robotics students hit it hardest — a vendor SDK with fifty thousand lines and documentation that assumes you already know the architecture. You are not expected to read it all. You're expected to be able to find the one function you need and understand what it touches, and F12 plus Shift+F12 is how that's actually done.

Part III — Real Work

Debugging — Chapter 9

The single biggest skill upgrade in this book. Print-statement debugging works, but it's slow, it requires you to guess in advance what to print, and it means editing and re-running for every question you think of. A debugger lets you stop the program and look.

The core idea

Set a breakpoint — click in the gutter to the left of a line number, and a red dot appears. Run under the debugger and execution pauses at that line, before it runs. Now every variable in scope is visible and inspectable, you can evaluate arbitrary expressions against the live state, and you can step forward one line at a time watching things change.

Starting and stepping

F5                Start debugging (or continue to the next breakpoint)
Ctrl+F5           Run without debugging
F9                Toggle a breakpoint on the current line
F10               Step over  — run this line, don't descend into calls
F11               Step into  — descend into the function being called
Shift+F11         Step out   — finish this function, return to the caller
Shift+F5          Stop

Step over vs step into is the distinction to get right: F10 when you trust the function being called, F11 when you suspect it. Most debugging is F10 until something looks wrong, then F11 into the suspect.

What you get while paused

  • Variables — everything in scope, expandable, live.
  • Watch — pin an expression (len(joints), msg.header.stamp) and see it re-evaluate at every step.
  • Call Stack — how execution got here. Click any frame to inspect that function's variables.
  • Debug Console — a REPL inside the paused program. Run any expression against the real live state. This is the feature that makes debuggers feel like a superpower.

Conditional breakpoints

Right-click a breakpoint → Edit Breakpoint to attach a condition. This is the killer feature for loops: instead of pressing continue three hundred times, break only when joint_id == 14, or only when abs(torque) > 50. A logpoint is the same idea in reverse — it prints a message and keeps going, giving you print-debugging without editing your source at all.

launch.json

For anything beyond "run this file", VS Code stores debug configurations in .vscode/launch.json. Create one from the Run and Debug view:

{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Python: Current File",
      "type": "debugpy",
      "request": "launch",
      "program": "${file}",
      "console": "integratedTerminal",
      "justMyCode": true
    },
    {
      "name": "Robot: teleop with args",
      "type": "debugpy",
      "request": "launch",
      "program": "${workspaceFolder}/scripts/teleop.py",
      "args": ["--iface", "eth0", "--rate", "50"],
      "env": { "ROBOT_IP": "192.168.123.161" }
    }
  ]
}

Set "justMyCode": false when you need to step into library code — which is exactly what you want when debugging a vendor SDK and you suspect the problem is on their side of the boundary.

Try it — one real debugging session 
# Save this as buggy.py, then debug it rather than reading it:
def average(numbers):
    total = 0
    for n in numbers:
        total += n
    return total / len(numbers)

data = [4, 8, 15, 16, 23, 42]
print(average(data))
print(average([]))          # this one explodes
Put a breakpoint on return total / len(numbers), press F5, and inspect total and numbers on each call. Then add the condition len(numbers) == 0 to the breakpoint and run again — it stops only on the failing call. Finally, in the Debug Console while paused, type numbers and len(numbers). That's the whole workflow, and it's about ninety seconds of learning.
From the field — the hour that changes how you work Learning the debugger is the highest-leverage hour in this book, and almost nobody spends it. The reason is that print statements work — they're familiar, they need nothing set up, and each individual one feels faster than configuring a launch config. But the costs compound invisibly: every question you think of requires an edit and a re-run, you can only see what you thought to print, and you routinely ship a debug print you forgot to remove. The debugger inverts all of that — pause once and ask unlimited questions of the real state, including ones you hadn't thought of when you started. In robotics this matters more than in most fields, because re-running isn't free: it may mean re-homing a robot, re-establishing a network session, or re-creating the exact physical situation that triggered the bug. Being able to stop at the moment it goes wrong and look around is worth an enormous amount when each attempt costs you five minutes of setup.

Git & Source Control — Chapter 10

VS Code's Git integration is genuinely good, and it's especially useful for the two things that are awkward on the command line: reviewing exactly what you changed, and resolving merge conflicts.

The Source Control view

Ctrl+Shift+G. Changed files are listed; clicking one opens a side-by-side diff against the last commit. The + next to a file stages it, the message box plus Ctrl+Enter commits. The Git & GitHub Field Guide covers what these operations actually mean; this chapter is only about the interface.

Staging individual lines

This is the feature that's meaningfully better than the CLI. Select some lines inside a diff view, then run Stage Selected Ranges from the palette. You can commit a bug fix while leaving unrelated debug edits in the same file unstaged — producing clean, single-purpose commits without stashing or manual surgery. The command-line equivalent is git add -p, which is capable but far less pleasant.

Inline history with GitLens

The GitLens extension annotates each line with who last changed it and when, and lets you open the commit that introduced any line. On a shared codebase this answers "why on earth is this here" faster than anything else — you get the commit message and, if the team writes good ones, the reasoning.

Merge conflicts

When a merge conflicts, VS Code shows the conflicted region with clickable Accept Current / Accept Incoming / Accept Both / Compare actions, and the three-way merge editor puts both versions and the result side by side. This is a large improvement over editing conflict markers by hand, particularly the first several times you hit one. Conflict resolution itself — the judgement about which change should win — is covered in the Git guide.

Remote Development — Chapter 11

This is the chapter that matters most for robotics and lab work. You can open a folder on a remote machine — a robot, a lab server, a Raspberry Pi — and work on it exactly as if it were local: full IntelliSense, debugging, terminal, extensions, all running on the remote side.

How it works

The Remote-SSH extension connects over SSH and installs a small VS Code server on the remote machine. Your local window becomes a thin client: the UI is on your laptop, but the files, the terminal, the Python interpreter, the extensions, and the debugger are all on the remote host. Nothing is synced or copied — you are editing the real files in place.

Compared with the alternatives this is transformative. Editing over vim in an SSH session gives you no IntelliSense and no debugger. Editing locally and scp-ing files up gives you a sync problem and a class of bug where the thing you're testing isn't the thing you edited. Remote-SSH removes both.

Connecting

Ctrl+Shift+P  ->  Remote-SSH: Connect to Host...

It reads your ~/.ssh/config, so define hosts there once and they appear in the list:

# ~/.ssh/config
Host robot
    HostName 192.168.123.161
    User unitree
    IdentityFile ~/.ssh/id_ed25519

Host labpc
    HostName lab-workstation.csusb.edu
    User yourname
    ForwardAgent yes

Then Connect to Host → robot, and Open Folder to whatever you're working on. Set up key-based authentication first — VS Code reconnects frequently and typing a password each time gets old immediately. The Robotics Installation Guide covers keys and SSH config for reaching a robot, and the Networking Field Guide covers the addressing and routing underneath it.

Things to know

  • Extensions install per-host. The Python extension on your laptop doesn't help the robot — install it again on the remote side. VS Code prompts you, and it's a one-time cost per machine.
  • The green indicator at the far-left of the status bar always tells you where you are. Check it before running anything destructive; running a script on the wrong machine is an easy and memorable mistake.
  • Port forwarding is automatic for many cases and manual via the Ports panel — useful for viewing a web dashboard or visualiser running on the robot in your local browser.
  • The remote needs resources. The VS Code server is not free; on a very small board it competes with your control loop. Prefer connecting to the lab machine that talks to the robot rather than to a tiny embedded controller directly.
  • Also available: WSL (Windows Subsystem for Linux) and Dev Containers, which use the same mechanism to target a Linux subsystem or a Docker container.
Know which machine you're on Remote development is convenient enough that it becomes easy to forget the folder you're looking at is on a robot. Two consequences worth internalizing. Your local .venv is not the remote's — interpreter selection, installed packages, and requirements.txt all have to be right on the remote side, and the Python guide's robotics chapter covers how that interacts with a system ROS install. And a script you run from a remote terminal runs on the robot, with real actuators attached. Before pressing F5, glance at that green status-bar indicator. It takes half a second and it is the difference between a test and an incident.

Settings & Profiles — Chapter 12

Settings live at several levels, and knowing which level you're editing prevents the frustration of a change that seems not to take effect — or one that unexpectedly follows you into every project.

The layers

LevelApplies toWhere it lives
UserYou, everywhere~/.config/Code/User/settings.json
WorkspaceThis project only — overrides User.vscode/settings.json in the project
RemoteThis remote hostOn the remote machine
LanguageOne language, e.g. "[python]"Either file, nested

Open either with Preferences: Open Settings (JSON) or Open Workspace Settings (JSON) from the palette. Editing the JSON directly is usually faster than hunting through the GUI, and it's the form every piece of documentation quotes.

Workspace settings are a team tool

Committing .vscode/settings.json to your repository means everyone on the project gets the same formatter, the same line length, the same excluded folders. For a class, it means students get a working configuration by cloning. Pair it with .vscode/extensions.json, which recommends extensions to anyone who opens the folder:

// .vscode/extensions.json
{ "recommendations": ["ms-python.python", "charliermarsh.ruff", "ms-vscode-remote.remote-ssh"] }

Do not commit .vscode/ settings that encode your personal machine — absolute interpreter paths, your username in a path. Those break for everyone else. Commit the shared, project-level decisions; keep the personal ones in User settings.

Profiles and Settings Sync

Profiles bundle settings, extensions, and shortcuts into named sets you can switch between — a lightweight "Robotics" profile with ROS and Python tooling, a separate one for web work, so neither is slowed by the other's extensions. Settings Sync pushes your configuration to a GitHub or Microsoft account and pulls it down on any machine you sign into — genuinely useful when you work across a laptop and a lab workstation.

Troubleshooting — Chapter 13

The problems that actually come up, and what causes them. Most are configuration rather than bugs.

Editor is sluggishHuge folder open (home dir), or too many extensionsOpen a narrower folder; Developer: Startup Performance

F12 does nothingLanguage server still indexing, or file not in the workspaceWait for the status bar; check the folder is open
Remote-SSH won't connectSSH itself is failingTest ssh host in a plain terminal first

The two general fixes

Ctrl+Shift+P  ->  Developer: Reload Window        # fixes a surprising amount
Ctrl+Shift+P  ->  Extensions: Disable All Installed Extensions
                                                   # then re-enable to bisect

Reload Window restarts the editor's internals without losing your session and resolves most extension weirdness. If something is genuinely broken, disabling all extensions and re-enabling them in halves finds the culprit in a few rounds — the same bisection idea as git bisect in the Git guide.

Lab Exercises — Chapter 14

Do these in VS Code, not in your head. Editor skill is muscle memory, and the only way to build it is repetition with intent.

Lab 1 — Palette only

  1. Work for thirty minutes without touching the menu bar. Use Ctrl+Shift+P for everything.
  2. Find these purely by palette search: toggle word wrap, change the color theme, open keyboard shortcuts, split the editor, open settings as JSON.
  3. In a file over 100 lines, use Ctrl+P @ to jump to three different functions.

Lab 2 — Interpreter mismatch, on purpose

  1. Create a project with a .venv and install one package into it (Python guide, Ch 5).
  2. Deliberately select the system interpreter in VS Code. Observe the red squiggle on your import.
  3. Run the file in the integrated terminal with the venv activated — it works. Explain the contradiction.
  4. Switch to the venv interpreter. Confirm the squiggle disappears and the status bar updates.

Lab 3 — Debug instead of print

  1. Take the buggy.py from Chapter 9. Find the bug using only the debugger — no print statements.
  2. Set a conditional breakpoint that fires only on the empty-list call.
  3. While paused, use the Debug Console to evaluate three expressions against live state.
  4. Add a logpoint that prints len(numbers) on every call without modifying the file.

Lab 4 — Multi-cursor and rename

  1. Write a file with a variable used eight times, plus the same word inside a string and in a comment.
  2. Rename it with Ctrl+Shift+L (select all occurrences). Note what it wrongly changed.
  3. Undo. Now rename with F2. Note the difference and explain why it knows better.

Lab 5 — Remote

  1. Add a host to ~/.ssh/config and confirm plain ssh thehost works first.
  2. Connect with Remote-SSH and open a folder there. Find the green indicator in the status bar.
  3. Open a terminal — confirm with hostname that it's the remote machine.
  4. Install the Python extension on the remote and select an interpreter there. Note that it's a separate selection from your local one.

From the field — the short version If you take four things from this book, take these. Open the folder, not the file — almost every feature depends on it. Use the command palette instead of remembering where things are; it's faster than menus and it's how you discover what the editor can do. Learn the debugger, properly, once — it is a genuinely different way of understanding a running program than print statements, and the hour it costs comes back within a week. And check the status bar before you go looking for a mystery: which interpreter, which branch, which machine. Those four habits are most of the distance between using VS Code as a text editor and using it as the tool it is, and none of them requires memorizing a single additional shortcut.
A closing word An editor is infrastructure. You'll spend more hours in it than in any other program you use, and small frictions repeated ten thousand times add up to real cost — not just in time, but in the ideas you don't pursue because chasing them felt like too much work. The point of learning the palette, the jumps, and the debugger isn't speed for its own sake; it's that when the cost of investigating something drops far enough, you start investigating things you would otherwise have guessed at. That's the actual upgrade. So pick two shortcuts from Appendix A you don't currently use, force yourself to use them for a week until they're automatic, and then pick two more. That's the whole method, and it works.
