The Docker Desktop Field Guide

Containers, From Zero to Working
Every technical course eventually hands you a project that will not run on your machine. The versions are wrong, a library refuses to build, the instructions assume an operating system you do not have — and an afternoon disappears into it. Containers are the answer the industry settled on, and Docker Desktop is the box they come in: one installer that puts the whole toolchain, plus a graphical dashboard for it, on Windows, macOS or Linux. This book starts from the assumption that you have never run a container, explains what one is before asking you to type anything, walks the installation on all three platforms, then builds up through running containers, storing data, writing your own images, and orchestrating several at once. Everything in it is checked against Docker’s own documentation.

How to Read This Book — Front Matter

This book assumes you have never run a container and, quite possibly, are not sure what one is. That is the right place to start from, because almost every Docker tutorial on the internet begins two steps after that — and those two steps are where the confusion lives.

The journey, part by part Part I is concepts, and it contains no installation and almost no commands. It is short, and it is the part most people skip and then spend a semester regretting, because every later confusion — "why did my data disappear", "why can't I reach it in my browser", "why is my image four gigabytes" — is a Part I misunderstanding wearing a costume. Part II installs Docker Desktop on Windows, macOS and Linux; read only your own platform's chapter, plus Chapter 5 and Chapter 9, which apply to everyone. Part III is a tour of the application itself — the Dashboard, its views, and its settings. Part IV is the daily skill: running containers, exposing ports, keeping data. Part V is building your own images with a Dockerfile. Part VI is multi-container projects with Compose, containerizing an existing application, image security, and the Kubernetes cluster hiding inside Docker Desktop. Part VII is housekeeping, troubleshooting, labs and reference.
If you only have an hour Read Chapter 2 (containers versus virtual machines) and Chapter 3 (images versus containers), install from your platform's chapter, then do Chapter 16 and Chapter 18. That is enough to run software other people have containerized, which is what most coursework actually asks of you. Building your own images (Part V) can wait until you need it.

What you should already know

You need to be able to open a terminal and run a command in it. That is genuinely the whole prerequisite. Where a chapter leans on something deeper — file permissions, environment variables, the shell's PATH — it links to the Linux Field Guide, which covers those from the ground up. Part V assumes you can use Git well enough to clone a repository, and several examples containerize Python applications, where the Python Environment Field Guide explains the dependency problem that containers generalize.

Docker Desktop ships roughly weekly This book was checked against Docker Desktop 4.88.1. Menu labels and the exact position of settings move between releases more often than you would expect, so if a screen described here does not look quite like yours, trust the screen. Concepts and command-line flags are far more stable than the graphical interface, which is one good reason this book teaches both and leans on the CLI for anything you might want to reproduce later.

Part I — What a Container Is

The Problem Docker Solves — Chapter 1

Before the tool, the problem. Containers are an answer to a specific, ordinary, deeply annoying failure — and knowing exactly which failure they address tells you when to reach for them and when not to.

"It works on my machine"

You clone a classmate's project. It ran perfectly in the demo. On your laptop it fails on the first command with a stack trace mentioning a library you have never heard of. An hour later you discover the project needs Python 3.11 and you have 3.13; that a native extension needs a C compiler and a header package; that one dependency was installed system-wide on their machine and never made it into requirements.txt; and that the whole thing assumes a Linux path layout while you are on Windows.

None of this is anyone's fault, and none of it is a programming problem. It is an environment problem: the code is identical, but everything around the code differs. Four layers can each drift independently.

LayerHow it differs between machinesTypical symptom
Operating systemWindows vs macOS vs a dozen Linux distributionsPath separators, missing shell tools, case sensitivity
System librariesDifferent versions of glibc, OpenSSL, image and math librariesCompilation failures, "symbol not found" at import
Language runtimePython 3.11 vs 3.13, Node 18 vs 22, Java 17 vs 21Syntax errors in library code, removed standard-library functions
ConfigurationEnvironment variables, config files, service ports, credentialsConnects to nothing, or to the wrong thing

The escalating ladder of fixes

The industry tried each rung of this ladder in turn, and each one solves a bit more of the problem at a bit more cost.

ApproachIsolatesDoes not isolateCost
Install everything on the hostNothingEverythingFree, until two projects disagree
A virtual environment (venv, nvm)Language packagesThe runtime itself, system libraries, the OSNearly free; language-specific
A containerOS userland, system libraries, runtime, packages, configThe kernelSome disk, a little RAM, one new tool to learn
A virtual machineEverything, including the kernel—Gigabytes of disk, minutes to boot, dedicated RAM

A container sits at the sweet spot: it captures essentially everything that made the project work on the author's machine, without the weight of shipping an entire operating system. When you run someone's container, you are not running a program they wrote — you are running the environment they tested in, byte for byte.

From the field — what containers do not fix Containers make an environment reproducible. They do not make your code correct, they do not make it fast, and they do not remove the need to understand what you are running. Two things in particular trip up newcomers. First, a container is not a virtual machine and cannot run a different kernel — you cannot run Windows software in a Linux container, whatever your host is (Chapter 2). Second, hardware is not automatically portable: a container that expects a USB device, a serial port, a camera or a GPU needs that access granted explicitly, and "it works in the container on my machine" can still fail on yours for reasons that have nothing to do with software versions. Containers eliminate one enormous class of problem. They do not eliminate all of them, and the people who get the most out of Docker are the ones who know which class it is.

Containers vs Virtual Machines — Chapter 2

This is the single most important idea in the book, and it explains almost every surprising thing Docker does — including why Docker Desktop quietly runs a virtual machine on your Mac or Windows laptop.

Docker's own definition

Docker's documentation is admirably blunt about it: containers are "isolated processes" for each of your app's components — not small computers, not lightweight VMs, but processes running on your machine's existing kernel with a restricted view of the world. Each is self-contained: it has "everything it needs to function with no reliance on any pre-installed dependencies."

The contrast Docker draws with virtual machines is the part worth memorizing. A virtual machine runs "an entire operating system with its own kernel, hardware drivers, programs, and applications"; a container is "simply an isolated process with all of the files it needs to run." Because containers "share the same kernel," you can "run more applications on less infrastructure."

Why Docker Desktop runs a VM anyway

Here is the consequence that confuses everybody. Container images are, overwhelmingly, Linux images: they contain Linux binaries and expect a Linux kernel. If you are on Linux, that kernel is already there and containers really are just processes on your machine. If you are on macOS or Windows, there is no Linux kernel to share — so Docker Desktop provides one, by running a small, purpose-built Linux virtual machine in the background and putting your containers inside it.

This is not a hack or a compromise you should feel bad about; it is the design, and Docker Desktop manages it so completely that you can go months without thinking about it. But it explains several things that otherwise look arbitrary, and which come up repeatedly later in this book:

  • Docker Desktop has a memory and CPU allocation (Chapter 14) — that is the VM's allocation.
  • Files shared from your host into a container cross a boundary, and on macOS and Windows that crossing has a real performance cost. This is why Docker warns that "sharing too many files can lead to high CPU load and slow filesystem performance".
  • "localhost" is ambiguous. Inside a container, localhost means the container. On your host it means your machine. Bridging the two is what port publishing is for.
  • Docker Desktop's disk image grows and does not shrink on its own (Chapter 29).
  • On Windows, the VM is a WSL 2 distribution by default, which is why WSL appears throughout Chapter 6.
Isolation is real, but it is not a sandbox for hostile code Docker states that containers are isolated so they "have minimal influence on the host and other containers, increasing the security of your applications." That is true and useful: a container's mess stays in the container, and "deleting one container won't affect any others." But the boundary is enforced by the shared kernel, so a kernel vulnerability — or, far more commonly, a container you deliberately gave extra privileges, a mounted host directory, or the Docker socket — crosses it. Treat containers as excellent isolation between things you trust, and do not treat "I ran it in a container" as sufficient reason to execute code you would not otherwise run. The Linux guide's hardening chapter and Chapter 27 here go further.

Images, Containers & Registries — Chapter 3

Three nouns. Almost every early Docker mistake is really a confusion between the first two, and almost every later one is a misunderstanding of the third.

An image is a package; a container is a running copy of it

Docker defines a container image as "a standardized package that includes all of the files, binaries, libraries, and configurations to run a container." It sits on disk, inert. A container is what you get when you run one.

The relationship is exactly the relationship between a class and an object, or between a program on disk and a process in memory. One image can produce a hundred containers, each with its own filesystem changes, its own process, its own lifetime. Deleting a container does not delete the image; deleting the image does not affect containers already running from it.

Images are immutable, and made of layers

Two properties do most of the explanatory work. First, immutability: "Once an image is created, it can't be modified." You do not edit an image; you build a new one. Second, layers: "Container images are composed of layers. Each layer represents a set of file system changes that add, remove, or modify files."

Layers are why Docker feels so much lighter than its file sizes suggest. If ten images on your machine all start FROM python:3.13, that base is stored once and shared. When you rebuild after editing one source file, only the layers at or after that change are rebuilt — everything below is reused from cache. And when you push an image to a registry, only layers the registry does not already have travel over the network. Chapter 23 turns this into a practical skill; for now, just know that the order of instructions in a Dockerfile has real consequences.

Reading an image name

Image names look casual and are actually strictly structured. The full form is:

[HOST[:PORT_NUMBER]/]PATH[:TAG]

where PATH on Docker Hub is  [NAMESPACE/]REPOSITORY

Every part except the repository has a default, which is why short names work and why they can surprise you:

What you typeWhat Docker actually resolvesNotes
nginxdocker.io/library/nginx:latestThe library namespace holds Docker Official Images
python:3.13docker.io/library/python:3.13Tag pinned to a version — better
docker/welcome-to-dockerdocker.io/docker/welcome-to-docker:latestPublished by the docker organisation
ghcr.io/acme/tool:v2—A different registry entirely (GitHub's)
myname/myapp:v1docker.io/myname/myapp:v1Your own Docker Hub account (Ch 22)
"latest" does not mean latest latest is not a magic pointer to the newest release. It is just the tag Docker assumes when you do not give one, and it points at whatever the publisher last pushed under that name — which may be months old, and which will silently change under you. The result is the exact problem containers were supposed to solve: two people run the "same" image on different days and get different software. Pin a real version tag in anything you or a classmate will run more than once, and pin a digest (python:3.13@sha256:…) in anything that has to be reproducible in six months, as Docker's own best-practices guide recommends.

Registries, and Docker Hub in particular

A registry is a server that stores images. Docker's documentation is explicit that "Docker Hub is a public registry that anyone can use, and Docker looks for images on Docker Hub by default." Other registries exist and are common in industry — GitHub Container Registry, Amazon ECR, Google Artifact Registry, and self-hosted ones — and you address them by putting the hostname at the front of the image name.

On Docker Hub, three labels are worth recognising. Docker Official Images live in the library namespace and appear as bare names like nginx or postgres; they are maintained in the open and are the sensible default for base images. Verified Publisher images come from a company Docker has confirmed is who it says it is. Everything else is an ordinary user account — which is fine, and is also where you should apply the same judgement you would apply to any package on the internet.

The commands that go with this chapter

docker pull python:3.13        # download an image without running it
docker image ls                # what is on this machine, with tag, ID, age, size
docker image history nginx     # the layers, newest first, with sizes
docker search postgres         # query Docker Hub from the terminal
docker image inspect nginx     # full metadata as JSON

You will use docker image ls constantly, mostly to answer "did that build actually produce anything" and "why is my disk full". Note that docker pull is rarely necessary on its own: docker run pulls automatically if the image is not present.

What Docker Desktop Is — Chapter 4

Docker Desktop is not "Docker with a GUI bolted on". It is a bundle — an engine, a command-line client, several separate products, a virtual machine to run them in, and a dashboard over the top. Knowing which piece is which makes the documentation, and the error messages, far easier to read.

The client and the daemon

Docker is a client–server system. Docker's overview puts it plainly: "The Docker client talks to the Docker daemon, which does the heavy lifting of building, running, and distributing your Docker containers." The daemon, dockerd, "listens for Docker API requests and manages Docker objects such as images, containers, networks, and volumes." The client, docker, is the command you type; it "sends these commands to dockerd, which carries them out."

Crucially, the two need not be on the same machine: "The Docker client and daemon communicate using a REST API, over UNIX sockets or a network interface." That is why docker commands can target a remote machine, and it is the mechanism behind contexts, which matter in Chapter 8.

What is in the box

Docker describes Desktop as "a one-click-install application for your Mac, Linux, or Windows environment that lets you build, share, and run containerized applications and microservices." The installer includes a genuinely long list of separate products:

Docker Desktop versus Docker Engine

On Linux you have a genuine choice, and it is worth understanding before Chapter 8. Docker Engine is the daemon alone, installed as a system service, running containers directly on your kernel — free, open source, no GUI, and what essentially every Linux server in the world runs. Docker Desktop for Linux adds the Dashboard, the bundled extras above, and a virtual machine.

That last point catches people out. Docker's documentation states that "Docker Desktop on Linux runs a Virtual Machine (VM) which creates and uses a custom docker context, desktop-linux, on startup." The practical consequence: images and containers you created with a native Docker Engine install will not appear in Docker Desktop, and vice versa. They are two separate daemons with two separate stores of everything, and docker context use is the switch between them.

From the field — which one should a student install? On Windows and macOS the question does not arise: Docker Desktop is how you get Docker at all. On Linux, install Docker Desktop if you want the same environment your Windows and Mac classmates have, the graphical views, and one-click Kubernetes — that consistency is worth a lot in a class where the instructions have to work for everyone. Install Docker Engine instead if you are on a server, a headless lab machine, or a Raspberry Pi; if you are short on RAM; or if you want containers to have direct access to host hardware, since a container inside Desktop's VM is one boundary further away from your USB ports and GPUs than one under a native Engine. Do not run both at once casually — Docker warns they can conflict over network ports, and recommends stopping Engine while using Desktop. The most common form of "Docker is broken" on a Linux machine is really "two daemons, and you are talking to the wrong one".

Part II — Installing It

Before You Install — Chapter 5

Ten minutes of reading that prevents the two most common bad outcomes: an installation that cannot work because virtualization is off in firmware, and a licensing surprise if you later take the same setup to a job.

Is Docker Desktop free?

For a student, yes — unambiguously. Docker's subscription agreement makes Docker Desktop free for:

  • Personal use
  • Education
  • Non-commercial open source projects
  • Small businesses — defined as "fewer than 250 employees AND less than $10 million in annual revenue"

A paid subscription (Pro, Team or Business) is required for professional use in organisations above that threshold, and for government agencies. Note the AND in the small-business test: both conditions must hold for the free tier to apply.

The licence covers Docker Desktop, not Docker itself This is a point people get wrong in both directions. Docker Engine and the underlying Moby project are open source under licences including the GNU GPL, and are unaffected by any of the above — a company with 50,000 employees can run Docker Engine on servers for free. What the subscription covers is the Docker Desktop application. If you go on to work somewhere large, expect the answer to be "Docker Engine on the servers, and a paid Desktop licence or an alternative on the laptops". Knowing that distinction in an interview is a small but real signal.

Realistically, 8 GB is a floor rather than a target on any platform. Docker Desktop's VM takes a share of your RAM, and a database container plus a web application plus your editor plus a browser will make a 8 GB machine unhappy. If you have 16 GB you will not think about it.

Turn on virtualization first

The most common "Docker won't install" on Windows and Linux is hardware virtualization disabled in firmware. It is called Intel VT-x, AMD-V or SVM Mode depending on your machine, and it lives in the BIOS/UEFI setup screen you reach with F2, Del or F10 during boot. Check before you download anything — it is a two-minute reboot now versus a confusing failure later.

Get a Docker Hub account

You can use Docker Desktop without signing in, but you should not, for one concrete reason: pull rate limits. Docker Hub limits image downloads over a rolling six-hour window.

Unauthenticated limits are shared across everyone on your network Read the middle column again. When you are not signed in, the 100-pull budget is counted per IP address — so an entire computer lab, or a lecture hall of students on one campus network doing the same tutorial at the same time, shares a single allowance. This is the actual explanation behind the mysterious 429 Too Many Requests that hits a whole class ten minutes into a lab session while working fine at home the night before. Sign in on every machine you use. It is free, it moves you to a personal 200-pull budget, and it makes the failure go away.

Why WSL 2

WSL 2 is "a full Linux kernel built by Microsoft that lets Linux distributions run without managing virtual machines." Docker describes the backend's advantages as "improvements to file system sharing, faster cold-start times, and dynamic resource allocation" — that last one matters most day to day, because Docker only consumes the memory it is actually using rather than reserving a fixed block. Multi-stage builds in particular are noticeably faster.

Install WSL 2 first if you do not have it. From an administrator PowerShell:

wsl --install
wsl --version                 <# confirm 2.1.5 or later #>
wsl -l -v                     <# list distributions and their WSL version #>

Installing

  1. Download the installer from Docker's site, choosing your architecture — x86_64 for almost everyone, or the Arm build (Early Access) on Arm hardware. A Microsoft Store build also exists.
  2. Double-click Docker Desktop Installer.exe.
  3. Choose an installation mode. Per-user is recommended and installs to %LOCALAPPDATA%\Programs\DockerDesktop without needing administrator rights — genuinely useful on a managed university machine. All users installs to C:\Program Files\Docker\Docker and requires elevation.
  4. On the Configuration page, tick "Use WSL 2 instead of Hyper-V". (You can change backend later in Settings → General, including switching to Docker VMM.)
  5. Finish the wizard, select Close, then launch Docker Desktop from the Start menu.
  6. Accept the Docker Subscription Service Agreement when it appears.

After installing

If you chose an all-users install and your administrator account differs from your daily account, add yourself to the docker-users group or you will get permission errors:

Then log out and back in. Verify the whole stack with wsl --version and the checks in Chapter 9.

WSL integration — using Docker from inside Ubuntu

By default the docker command works from any Windows terminal (PowerShell, Command Prompt, Windows Terminal). If you also work inside a WSL Linux distribution — and if you are taking a Linux-based course, you should — enable integration so docker works there too:

  1. Confirm the distribution is running in WSL 2 mode: wsl.exe -l -v.
  2. Docker Desktop → Settings → Resources → WSL Integration, enable your distribution, Apply & restart.

The default Ubuntu distribution has this on already. Docker Desktop itself runs inside its own isolated docker-desktop WSL distribution; integration with your other distributions happens only when you explicitly enable it.

Uninstall Docker Engine from inside WSL first If you previously ran sudo apt install docker.io inside your WSL Ubuntu, remove it before enabling integration. Otherwise you have two daemons and a docker command whose behaviour depends on which one won the race — the same "wrong daemon" confusion described in Chapter 4, and it is genuinely hard to diagnose from the symptoms.
Where the data lives, and how to move it Docker Desktop stores WSL 2 engine data in C:\Users\<USERNAME>\AppData\Local\Docker\wsl by default. Images are large and this grows; if your C: drive is small, move it in Settings → Resources → Advanced. Docker also recommends enabling WSL's autoMemoryReclaim setting so the Linux kernel returns RAM to Windows after a heavy build instead of holding onto it.

Installing on Linux — Chapter 8

More steps than the other platforms, and one genuine trap: if you already have Docker Engine installed, Docker Desktop will not show you any of your existing containers, and it will look like it lost them.

Supported distributions and requirements

Docker publishes Docker Desktop packages for Ubuntu, Debian, Red Hat Enterprise Linux, Fedora, and Arch-based distributions (experimental). Support covers current and previous LTS releases plus the most recent version. Your machine needs:

  • A 64-bit kernel with CPU virtualization support, and KVM virtualization enabled
  • QEMU 5.2 or later
  • systemd as the init system
  • A GNOME, KDE or MATE desktop environment
  • At least 4 GB of RAM

Nested virtualization is not supported — Docker Desktop will not run inside a VirtualBox or VMware guest.

Check and enable KVM

modprobe kvm
modprobe kvm_intel      # Intel processors
modprobe kvm_amd        # AMD processors

lsmod | grep kvm        # confirm the modules are loaded

sudo usermod -aG kvm $USER

Sign out and back in after the usermod, since group membership is established at login — the Linux guide's chapter on users and groups explains why. If lsmod | grep kvm returns nothing after modprobe, virtualization is disabled in firmware; see Chapter 5.

Prerequisites: an x86-64 system running Ubuntu 26.04 LTS or 24.04 LTS. On GNOME you need the AppIndicator and KStatusNotifierItem extensions for the tray icon; on other desktops, install gnome-terminal.

sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF

The installer sets binary capabilities so containers can bind privileged ports, adds a Kubernetes DNS entry to /etc/hosts, and links the CLI into place (a symlink from /usr/local/bin/com.docker.cli to /usr/bin/docker).

Starting it

Launch Docker Desktop from your applications menu and accept the subscription terms, or use systemd's user instance:

systemctl --user start docker-desktop     # start it now
systemctl --user enable docker-desktop    # and on every login
systemctl --user status docker-desktop    # is it actually running?

Note --user: Docker Desktop is a per-user service, unlike Docker Engine which is a system service. That difference is the source of a lot of confusion when someone copies a sudo systemctl start docker instruction from a server tutorial and it does nothing.

Two daemons, two separate worlds If Docker Engine is already installed, read this twice. Docker Desktop for Linux runs its containers inside a VM and creates its own context, desktop-linux. Your existing images and containers from Docker Engine will not appear in Docker Desktop — they have not been deleted, they belong to the other daemon. Docker recommends stopping Docker Engine while using Desktop, since the two can consume resources and conflict over network ports. Switch between them explicitly: 
docker context ls                    # which contexts exist, and which is current (*)
docker context use desktop-linux     # talk to Docker Desktop
docker context use default           # talk to the system Docker Engine

sudo systemctl stop docker           # stop the Engine service entirely
sudo systemctl disable docker        # and stop it starting at boot
When a Linux user says "Docker deleted all my images", this is the explanation roughly every time.

Running Docker without sudo, on Engine

This does not apply to Docker Desktop, whose per-user architecture handles it, but it is the single most-copied Linux Docker instruction and worth knowing why it exists. Under Docker Engine the daemon's socket is owned by root, so every command needs sudo unless you join the docker group:

sudo usermod -aG docker $USER      # then log out and back in
The docker group is root, spelled differently Membership of the docker group grants the ability to run containers with arbitrary access to the host filesystem. It is functionally equivalent to passwordless sudo, and it is not a "convenience" setting in a security sense — it is a privilege grant. Fine on your own laptop. Think carefully on a shared lab machine.

First Launch & Verification — Chapter 9

Four commands prove the whole stack works, and they are worth running deliberately rather than skipping to the interesting part — because when something breaks later, knowing which of these four still passes localizes the problem instantly.

Sign in

On first launch, accept the subscription agreement, then sign in with a Docker account (or create one — it is free). Recall from Chapter 5 that signing in quadruples your effective pull budget in a shared-network lab and moves it off the campus IP address. Signing in is also what enables Docker Scout's remote features (Chapter 27) and pushing your own images (Chapter 22).

Docker Desktop then offers the Learning Center, a short built-in walkthrough. It is genuinely decent and takes about five minutes.

The four checks

docker --version        # 1. is the CLI installed and on PATH?
docker version          # 2. can the CLI reach the daemon? (note: no dashes)
docker info             # 3. what is the daemon's state — storage, resources, containers?
docker run hello-world  # 4. can it pull an image and run a container end to end?
If this fails……the problem is
docker --versionThe CLI is not installed, or not on your PATH. Nothing else can work.
docker version (Client prints, Server errors)Docker Desktop is not running, or you are pointed at the wrong context (Ch 8). Start Docker Desktop and wait for the whale to stop animating.
docker infoThe daemon is up but unhealthy — usually out of disk (Ch 29) or a broken storage driver.
docker run hello-worldNetworking or registry access: a proxy, DNS, a firewall, or a rate limit (Ch 5).

Note the difference between docker --version and docker version. The first is a string printed by the CLI alone and proves almost nothing. The second contacts the daemon and prints both Client and Server blocks — if you only see Client, the daemon is not reachable, and that is the single most useful diagnostic in Docker.

Try it — run something real, in one line 
docker run -d -p 8080:80 docker/welcome-to-docker
Open http://localhost:8080 in your browser. A web server you never installed is now serving a page. Then look at the Containers view in Docker Desktop — it is there, with a name Docker invented for it. Now unpick what happened: -d ran it in the background, -p 8080:80 forwarded your port 8080 to its port 80, and the image was downloaded from Docker Hub because you did not have it. Every one of those is a chapter later in this book. Stop it with docker ps to find the ID and docker stop <id> — Docker notes you only need enough characters of the ID "to make it unique".
From the field — the whale in the tray is a status light Docker Desktop's tray icon animates while the engine is starting and settles when it is ready, and the Dashboard shows the engine status at the bottom left. On a cold boot this can take thirty seconds or more, which is long enough that people type docker ps, get "cannot connect to the Docker daemon", and conclude the installation failed. It did not. Before doing anything drastic, wait for the whale. The number of perfectly good installations that get reset to factory defaults during those thirty seconds is not small.

The second shape deserves a moment of appreciation: it is a clean, disposable Ubuntu machine that starts in under a second, in which you can test anything — a suspicious install script, an unfamiliar package, a different distro's behaviour — and which vanishes completely when you type exit. touch /I_WAS_HERE          # write a file at the filesystem root
exit

docker run -it --rm ubuntu bash

exit
The file vanished because exit ended the first container and --rm deleted it; the second command built a fresh container from the unchanged image. You have just demonstrated the two most important facts in this book: images are immutable (Ch 3), and container filesystems are disposable (Ch 19).

The Container Lifecycle — Chapter 17

Containers are created, run, stop, and — this is the part people miss — hang around afterwards. Half of Docker housekeeping is understanding the "stopped" state.

The commands

docker ps                  # running only
docker ps -a               # ALL — including the stopped ones you forgot
docker stop web            # polite: SIGTERM, then SIGKILL after a grace period
docker start web           # restart a stopped container — same container, same files
docker restart web         # stop + start
docker pause web           # freeze without stopping
docker unpause web
docker rm web              # remove a stopped container
docker rm -f web           # force-remove a running one
docker logs web            # stdout/stderr, even for stopped containers
docker cp web:/etc/nginx/nginx.conf .   # copy files out (or in)

Stopped is not gone

When a container's process exits — you stopped it, it crashed, it finished — the container stops but is not deleted. Its filesystem, its logs and its configuration are all retained, invisible to plain docker ps but right there under docker ps -a. This is genuinely useful: docker logs on a crashed container is how you find out why it crashed, and docker start resumes it, changes and all.

It also means containers accumulate. Every docker run without --rm leaves a body behind when it exits. Run a tutorial five times and you have five stopped containers — five is fine, but months of this is how a machine ends up with hundreds, and why Chapter 29 exists.

The name-collision error, decoded docker run --name web … a second time fails with "Conflict. The container name /web is already in use" — because the first web still exists, stopped. This is the most common beginner error message in Docker, and now you can read it: either remove the old one (docker rm web) or restart it (docker start web) instead of creating a duplicate. Which one you want depends on whether you care about the old container's state — and after Chapter 19, the answer will usually be "I keep data in volumes, so no".

Ports & Networking — Chapter 18

Two separate skills that use one mental model: letting your browser reach a container, and letting containers reach each other.

Reaching a container from your host

Each container runs in what Docker calls its own "sandbox environment, completely isolated from everything else on your host machine" — including its network. A web server listening on port 80 inside a container is invisible from your browser until you publish the port, which Docker describes as creating "a forwarding rule" through the isolation:

docker run -d -p 8080:80 nginx
#              │    └ container port: where the server actually listens
#              └ host port: what you type into your browser

Now http://localhost:8080 on your machine forwards to port 80 in the container. The two numbers are independent: the container's port is fixed by whatever the software inside listens on; the host side is your choice, and choosing different host ports is how you run three containers that all internally use port 80.

docker run -d -p 127.0.0.1:8080:80 nginx   # only reachable from this machine
docker run -d -p 80 nginx                  # Docker picks a free host port — see docker ps
docker run -d -P nginx                     # publish every EXPOSEd port to random ports

By default a published port listens on all of your machine's network interfaces — other devices on your network can reach it. Prefixing 127.0.0.1: restricts it to your own machine, a sensible default for anything you would not deliberately serve to the whole lab's Wi-Fi.

Containers reaching each other

The second skill arrives the moment you have two containers — an app and its database. The wrong instinct is to publish the database's port and connect via localhost; the right tool is a user-defined network. Docker's documentation is explicit about the difference: on the default bridge network, containers "cannot refer to each other by name", while on a user-defined network they "communicate with each other using container IP addresses or container names." Docker's embedded DNS server (at 127.0.0.11 inside each container) resolves container names automatically. Docker's own assessment is unambiguous: "User-defined bridge networks are superior to the default bridge network," which "is considered a legacy detail of Docker and is not recommended for production use."

docker network create mynet
docker run -d --network mynet --name db postgres:18
docker run -d --network mynet --name app -p 8000:8000 myapp
# inside "app", the database is reachable as host "db", port 5432 —
# no published port, no IP address, just the container's name
docker network ls
docker network connect mynet existing-container   # attach a running container too

Note what did not happen: the database's port was never published. It is reachable from app, because they share a network, and unreachable from your host and everyone on the Wi-Fi — which for a database is precisely what you want. Publish ports for things people use; connect networks for things containers use.

DriverWhat it does
bridgeThe default: private network on the Docker host, egress allowed, ingress via published ports
hostDocker: "Remove network isolation between the container and the Docker host" — the container shares your host's network directly

"localhost" inside a container is the container The error this chapter prevents: your app container fails with connection refused to localhost:5432, though Postgres is definitely running. Inside the container, localhost means that container — and Postgres is not running in it, it is running in a different one. Fix: put both on a user-defined network and connect to the container's name (db:5432). You will see this bug in your own work, in classmates' work, and eventually in production incident write-ups; it is the same "which machine am I on?" confusion the VS Code guide warns about for remote development, wearing a networking costume.

Persisting Data — Chapter 19

The chapter that saves you from the classic Docker heartbreak: a semester project's database, gone with a deleted container. Two mechanisms exist; you need both, for different jobs.

Why data disappears

A container gets a writable layer on top of its image, and everything the running software writes lands there. Docker's documentation states the consequence flatly: "When the container is deleted, these file changes are also deleted." This is by design — it is what makes containers disposable and identical — and it means anything you care about must live somewhere with a longer lifespan than the container. There are two such places.

Volumes — Docker-managed storage

A volume is "a storage mechanism that provide the ability to persist data beyond the lifecycle of an individual container." Docker manages where it physically lives; you refer to it by name. Docker's own analogy: it is "like providing a shortcut or symlink from inside the container to outside the container."

docker volume create mydata
docker run -d -v mydata:/var/lib/postgresql --name db postgres:18
#              │      └ the path INSIDE the container the software writes to
#              └ the volume name — everything written to that path lands here

docker volume ls
docker rm -f db                       # kill the container entirely...
docker run -d -v mydata:/var/lib/postgresql --name db2 postgres:18
# ...and the new container has all the old data. That is the whole trick.

The container's half of the mapping is not your choice — it is wherever the containerized software keeps its data, documented on the image's Docker Hub page (/var/lib/postgresql for Postgres, /data for Redis, and so on).

Bind mounts — a host folder, visible inside

A bind mount skips Docker's management entirely: "a file or directory on the host machine is mounted from the host into a container." Your actual folder, your actual files, appearing at a path inside the container — edits on either side are instantly visible to the other.

# -v syntax: host path (absolute!) : container path
docker run -v "$(pwd)":/app mytool

# --mount syntax — Docker's recommendation: "more explicit and supports all the available options"
docker run --mount type=bind,src="$(pwd)",dst=/app mytool

# read-only, for config you want visible but untouchable
docker run -v "$(pwd)/config":/etc/app:ro mytool
docker run --mount type=bind,src="$(pwd)/config",dst=/etc/app,readonly mytool

One behavioural difference is worth knowing because it bites: if the host path does not exist, -v silently creates it as an empty directory (a typo becomes an empty mount and a mysterious "where are my files"), while --mount "produces an error" — which is exactly why Docker recommends it.

Which one, when

The development pattern that uses both at once, and that you will meet again in Compose: bind-mount your source code so edits appear live in the container, and volume-mount the database so it survives everything.

A bind-mounted folder is really shared — deletions included Docker warns that by default, bind mounts "have write access to files on the host": software in the container can "create, modify, or delete important system files or directories" in anything you mounted. rm -rf gone wrong inside the container deletes your real files. Mount the narrowest directory that works — the project folder, not $HOME — and add :ro whenever the container only needs to read. On Mac and Windows, the File sharing allowlist (Ch 14) is the outer fence around what can be bind-mounted at all.

Configuration & Environment — Chapter 20

The same image, doing different things on different machines, without being rebuilt — that is what environment variables are for, and it is how every configurable image on Docker Hub expects to be driven.

Passing configuration in

docker run -d -e POSTGRES_PASSWORD=devpass -e POSTGRES_DB=classdb postgres:18

# or many at once, from a file of KEY=value lines:
docker run -d --env-file .env postgres:18

The -e flag is Docker's "Set environment variables"; --env-file is "Read in a file of environment variables." Which variables an image understands is documented on its Docker Hub page — reading that page is a skill in itself, and the official postgres image's page is a good first example: it documents POSTGRES_PASSWORD, POSTGRES_USER, POSTGRES_DB and where the data lives, which is everything you need to run it properly.

Environment variables and their inheritance are a shell concept before they are a Docker one — if KEY=value feels underexplained here, the Linux guide's environment chapter is the ground truth.

Secrets and .env files An .env file with real passwords in it is one git add . away from being public. Put .env in your .gitignore before writing a secret into it, commit a .env.example with dummy values so classmates know what keys exist, and treat any secret that has ever been committed as burned — the Git guide's security chapter explains why history makes deletion nearly impossible. Environment variables are also visible to anyone who can docker inspect the container, which is fine on your laptop and a real consideration on shared machines.

Restart policies

on-failureRestart only after a non-zero exit
alwaysRestart whenever it stops, including after reboots — even if you had stopped it manually before the reboot
unless-stoppedLike always, but a manual stop stays stopped — usually what you actually want

unless-stopped on your course database is the difference between it simply being there every morning and re-running a setup command every time you reboot.

Part V — Building Images

The Dockerfile — Chapter 21

Everything so far ran other people's images. A Dockerfile is how you make your own: a short text file that turns "here's how I set up my machine" into a build anyone can reproduce.

What it is

Docker's definition: "a text-based document that's used to create a container image." It lives in your project's root directory, is named Dockerfile (no extension), and is read top to bottom by the builder. Conceptually it is your project's setup instructions — the ones that currently live in a README as "install Python 3.13, then pip install…" — made executable and therefore made honest: a README can drift from reality, but a Dockerfile that drifts stops building.

The instruction set

Definitions from Docker's documentation:

InstructionOfficial description
FROM"specifies the base image that the build will extend"
WORKDIR"specifies the 'working directory' or the path in the image where files will be copied and commands will be executed"
COPY"tells the builder to copy files from the host and put them into the container image"
RUN"tells the builder to run the specified command"
ENV"sets an environment variable that a running container will use"
EXPOSE"sets configuration on the image that indicates a port the image would like to expose"
USER"sets the default user for all subsequent instructions"
CMD"sets the default command a container using this image will run"

Two distinctions repay early attention. RUN versus CMD: RUN happens once, at build time, and its results are baked into the image; CMD is what happens at run time, every time a container starts. Installing dependencies is RUN; starting your server is CMD. EXPOSE versus -p: EXPOSE publishes nothing — it is documentation baked into the image saying "the software in here listens on this port". Actual publishing still happens at run time with -p (Chapter 18).

A real one, line by line

This is the example from Docker's own documentation, for a Python web application:

FROM python:3.13
WORKDIR /usr/local/app

# Install the application dependencies
COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt

# Copy in the source code
COPY src ./src
EXPOSE 8080

# Setup an app user so the container doesn't run as the root user
RUN useradd app
USER app

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8080"]
  • FROM python:3.13 — start from the official Python image: a Linux userland with Python already installed. Note the pinned version, not latest (Chapter 3).
  • COPY requirements.txt before COPY src — deliberate, and the single most important trick in Dockerfile writing. Chapter 23 explains why this order makes rebuilds fast.
  • RUN useradd app / USER app — Docker's best practices: "If a service can run without privileges, use USER to change to a non-root user." Without this, the application runs as root inside the container.
  • CMD ["…"] — the JSON-array form, which avoids wrapping the command in a shell. Prefer it.
The mental bridge from venv If you have read the Python Environment guide, a Dockerfile is requirements.txt taken to its logical conclusion. requirements.txt pins your Python packages but silently assumes a Python version, an OS, and system libraries. The Dockerfile pins all of those too — FROM python:3.13 is the assumption, written down. That is the entire idea of Part V in one sentence.

Build, Tag & Push — Chapter 22

A Dockerfile does nothing until you build it. Build turns it into an image; tag names the image; push publishes it — the same publish-to-a-shared-place motion as git push, aimed at a registry instead.

Building

docker build .
docker build -t myapp .
docker build -t myapp:v2 .
#             │         └ the build CONTEXT — the directory sent to the builder
#             └ -t names (tags) the result; without it you get only an ID

The trailing dot is not decoration. It is the build context — the directory whose files COPY instructions are allowed to reach, sent to the builder in its entirety. That "in its entirety" has consequences: a context containing a virtual environment, a node_modules, or your dataset transfers all of it on every build. Chapter 23 introduces .dockerignore to fix exactly this.

Watch a build's output once, deliberately: each Dockerfile instruction becomes a numbered step, each step produces a layer, and steps whose inputs have not changed since last time are marked CACHED and take no time at all. The Builds view (Chapter 13) shows the same thing graphically, with timing.

Naming for a destination

Recall the full image-name grammar from Chapter 3: [HOST[:PORT]/]PATH[:TAG]. A push destination is encoded in the name — there is no "push to…" argument. To push to your Docker Hub account, the image must be named your-username/something:

docker build -t myusername/myapp:v1 .        # name it correctly from the start
docker image tag myapp myusername/myapp:v1   # or re-tag an existing image

Note that docker image tag does not copy anything — both names point at the same image, like two Git branches on one commit.

Pushing

docker login
docker push myusername/myapp:v1

Docker notes that "all of the layers for your image will be pushed to the registry" — but layers the registry already has (your base image, most obviously) are skipped, which is why a small code change pushes in seconds. Once pushed, anyone can docker pull myusername/myapp:v1 — a classmate, a lab machine, a grader. That closes the loop this book opened with: the "works on my machine" project from Chapter 1 is now a single name that runs identically anywhere.

Public means public Free Docker Hub accounts get unlimited public repositories and one private one. A pushed public image is downloadable by anyone on the internet — and images contain every file you COPY-ed in. An .env full of credentials baked into an image is compromised the moment it is pushed, and like a committed Git secret (Git guide), un-pushing does not un-leak it. Keep secrets out of images entirely — pass them at run time (Chapter 20) — and let .dockerignore (next chapter) enforce that mechanically.
Try it — your first built image, end to end 
mkdir hello-build && cd hello-build
printf 'print("built by %s")\n' "$USER" > app.py
printf 'FROM python:3.13-slim\nWORKDIR /app\nCOPY app.py .\nCMD ["python", "app.py"]\n' > Dockerfile

docker build -t hello-build .
docker run --rm hello-build
docker image history hello-build     # your layers, on top of the base's
Then change the string in app.py and rebuild. Steps 1–2 report CACHED; only the COPY and later layers rebuild. You have now seen the cache work, which makes the next chapter concrete.

Layers, Cache & .dockerignore — Chapter 23

The difference between a two-second rebuild and a five-minute one is almost never hardware. It is whether the Dockerfile was written with the cache in mind.

The one rule of the cache

Each instruction produces a layer, and the builder reuses a cached layer only if the instruction and everything it depends on is unchanged — for a COPY, that means the copied files themselves. The crucial consequence: the first changed layer invalidates every layer after it, whether or not they changed.

Now re-read the Chapter 21 Dockerfile with that rule in mind:

COPY requirements.txt ./
RUN pip install --no-cache-dir -r requirements.txt   # slow — minutes
COPY src ./src                                       # the thing that changes constantly

Dependencies are copied and installed before the source code, because they change rarely while source changes constantly. Edit a source file and rebuild: the two expensive steps are CACHED, and only the cheap final COPY re-runs. Reverse the order — COPY . . first, then install — and every source edit re-installs every dependency from scratch. Same image, same correctness, minutes versus seconds. Order instructions from least-changing to most-changing; that is most of Dockerfile performance in one sentence.

Keep apt update and apt install together

A caching subtlety with an explicit rule in Docker's best-practices guide: "Always combine RUN apt-get update with apt-get install in the same RUN statement." The shape of their example, condensed:

RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    nginx \
    && rm -rf /var/lib/apt/lists/*

Splitting apt-get update into its own RUN means it can be served stale from cache while a later, edited install line re-runs against an outdated package index — failing on package versions that no longer exist. One RUN, always together; the trailing clean-up keeps the index out of the layer. (The list is sorted alphabetically for maintainability, per the same guide; the trailing \ continues the shell line.)

.dockerignore

The companion file to every Dockerfile, working "similar to .gitignore": patterns listed in .dockerignore are excluded from the build context before it is sent to the builder.

# .dockerignore
.git
.venv
__pycache__
node_modules
*.log
.env

Three distinct wins. Builds get faster — gigabytes of .git history and virtual environments stop being transferred. The cache gets stabler — COPY . . stops being invalidated by files that do not affect the build. And secrets stay out — .env in .dockerignore makes the Chapter 22 leak scenario mechanically impossible rather than a matter of remembering.

Choosing a base image

Docker's best practices distilled into three rules: prefer Docker Official Images or Verified Publisher images as bases; prefer small ones — Alpine is "tightly controlled and small in size (under 6 MB)", and -slim variants of language images are a gentler middle ground; and pin versions, up to and including the digest form FROM alpine:3.21@sha256:… for builds that must be byte-for-byte reproducible. Smaller bases are not just about disk: fewer packages means fewer vulnerabilities for Chapter 27's scanner to find, and less to download on every pull.

Multi-Stage Builds — Chapter 24

The tools that build software and the files that run it are different things, and only the second belongs in the image you ship. Multi-stage builds are how you keep them apart without maintaining two Dockerfiles.

The problem

A single-stage build accumulates everything: compilers, dev headers, package caches, test dependencies — all of it in layers, all of it shipped, none of it needed at run time. The result is the classic four-gigabyte image that contains a twelve-megabyte application. It is slower to push, slower to pull, and carries a larger attack surface for no benefit.

The mechanism

Docker's best practices: "Split your Dockerfile instructions into distinct stages to make sure that the resulting output only contains the files that are needed to run the application." Multiple FROM instructions, each starting a stage; later stages copy artifacts out of earlier ones with COPY --from; only the final stage becomes the image.

# Stage 1 — "builder": has the whole toolchain
FROM node:22 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # produces /app/dist

# Stage 2 — what actually ships: a web server and the built files
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html

Node, npm, node_modules, the source — all of it exists only in the builder stage and is discarded. The shipped image is nginx plus static files: tens of megabytes instead of over a gigabyte. The same shape works for any compiled or bundled stack — Go and Rust builders copying a single binary into a minimal base are the extreme version of the same idea.

From the field — when to bother Honestly: not always. A Python class project built on python:3.13-slim with three pip packages gains little from a second stage, because Python needs its interpreter and packages at run time anyway — there is no big toolchain to leave behind. Multi-stage builds earn their keep wherever build-time and run-time requirements genuinely diverge: anything compiled (C++, Go, Rust), anything bundled (JavaScript front-ends), anything whose pip install needs a compiler for native extensions. Learn the pattern now so you recognise it, apply it when the image size or the CVE count says so — and note that it is a standard idiom you will meet in nearly every production Dockerfile you read, including the ones docker init generates in Chapter 26.

Part VI — Real Projects

Docker Compose — Chapter 25

Real applications are several containers: an app, a database, maybe a cache. Compose replaces the growing pile of docker run commands with one file and one command — and the file doubles as documentation of how the whole thing fits together.

The idea

Docker's description: "Compose simplifies the control of your entire application stack, making it easy to manage services, networks, and volumes in a single YAML configuration file." The file is compose.yaml, at the project root, next to the Dockerfile. Everything Part IV taught — ports, volumes, environment, networks — reappears here as YAML keys instead of flags; Compose adds no new concepts, only a place to write the existing ones down.

A file worth reading closely

This is (lightly condensed) the configuration Docker's own getting-started tutorial builds — a Python web app with a Redis data store:

services:
  web:
    build: .                        # build this service from ./Dockerfile
    ports:
      - "8000:5000"                 # -p 8000:5000, as YAML
    environment:
      - REDIS_HOST=redis            # the other service's NAME — see below
    depends_on:
      redis:
        condition: service_healthy  # wait for redis's healthcheck to pass
    develop:
      watch:                        # for docker compose up --watch
        - action: sync+restart
          path: .
          target: /code
        - action: rebuild
          path: requirements.txt

  redis:
    image: redis:alpine             # pulled, not built
    volumes:
      - redis-data:/data            # named volume — data survives everything
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

volumes:
  redis-data:                       # declare the named volume

Every line is a chapter of this book in YAML form. ports is Chapter 18; volumes is Chapter 19; environment is Chapter 20; build is Chapter 22. The part Compose adds silently: it creates a network for the project and attaches every service to it, so web reaches Redis at the hostname redis — the service's name — with no network commands typed at all. That is Chapter 18's user-defined network, done for you.

Two refinements from the same tutorial worth knowing exist: ${APP_PORT}-style variables read from an .env file, and include: for splitting a large file into parts.

The commands

docker compose up             # create and start everything, attached
docker compose up -d          # ... in the background
docker compose up --watch     # ... syncing code changes live into the containers
docker compose ps             # status of this project's services
docker compose logs -f web    # follow one service's logs
docker compose down           # stop and remove containers and the network
docker compose down -v        # ... and the named volumes: the real "start over"

Note what down preserves: named volumes. Your database contents survive a down/up cycle by default, which is almost always what you want; -v is the deliberate, data-destroying reset.

Compose is the answer to "how do I run this?" A repository containing a compose.yaml is telling you its entire run story in one file: what gets built, what gets pulled, what talks to what, which ports to open, where data lives. docker compose up and read it while it starts. This is also the polite way to hand in coursework — a project with a working Compose file is one command away from running on the grader's machine, which is a much better place to be than a README of manual steps. In Docker Desktop, Compose projects appear grouped in the Containers view (Chapter 11) with the whole stack collapsible under the project name.

Containerizing an App — Chapter 26

The synthesis chapter: take an existing project of your own and make it run in a container. There is even a tool that writes the first draft for you.

docker init

Point it at a project and Docker's scaffolding tool "creates Docker-related starter files for your project" — specifically all four of: Dockerfile, .dockerignore, compose.yaml, and a README.Docker.md explaining what it generated. It has templates for ASP.NET Core, Go, Java, Node, PHP, Python, Rust, and a generic "Other", and asks a few questions — language version, port, start command — before writing anything. It prompts before overwriting existing files (and warns that overwritten files cannot be recovered).

cd your-project
docker init
# answer the prompts, then:
docker compose up --build

Read what it generated before running it — not because it is untrustworthy, but because it is a free, project-specific worked example of Part V: the generated Dockerfile pins a version, orders instructions for the cache, drops root, and often uses a multi-stage build you can compare against Chapter 24.

Doing it by hand — the checklist

For projects docker init does not fit, or to understand what it did:

  1. Find the run story. What command starts the app? What runtime version? What must be installed first? (This is the README, made precise.)
  2. Choose a base image matching the runtime — python:3.13-slim, node:22-alpine — pinned, per Chapter 23.
  3. Write the Dockerfile in the Chapter 21 shape: dependencies first, source second, non-root user, CMD last.
  4. Write .dockerignore before the first build, not after the first slow one.
  5. Build, run, iterate. The first attempt rarely works; the error messages are the missing lines of your Dockerfile. A missing system library → a RUN apt-get…; a file-not-found → a COPY or WORKDIR issue.
  6. Externalize what varies. Hard-coded ports, paths and passwords become environment variables (Chapter 20).
  7. Add services in Compose. The moment a database enters the picture, stop typing docker run and write the compose.yaml (Chapter 25).
From the field — the app must listen on 0.0.0.0 The single most common "it builds but I can't reach it" failure: the app inside the container binds to 127.0.0.1, which inside the container means the container itself — so the port forward from your host arrives at an interface the app is not listening on. Symptoms: the container runs, logs look happy, browser gets connection reset. Fix: make the server listen on 0.0.0.0 (all interfaces). Flask's app.run(host="0.0.0.0"), uvicorn's --host 0.0.0.0 — notice that argument sitting in Chapter 21's CMD, and in essentially every containerized server you will ever read. It is there because of exactly this.

Security & Docker Scout — Chapter 27

Every image you build inherits the vulnerabilities of everything inside it. Docker Desktop ships a tool that makes them visible — and a student who can read its output has a genuinely marketable skill.

What Scout is

Docker Scout is Docker's "solution for proactively enhancing your software supply chain security." Mechanically it does three things: analyzes images at the layer and package level; "compiles an inventory of components, also known as a Software Bill of Materials (SBOM)"; and matches that inventory "against a continuously updated vulnerability database to pinpoint security weaknesses" — known vulnerabilities, indexed as CVEs. You have already seen its output without asking: the vulnerability numbers in the Images view (Chapter 12) are Scout analyses.

Using it

docker scout quickview myimage      # summary: base image, CVE counts by severity
docker scout cves myimage           # the full vulnerability list
docker scout cves --only-package express myimage    # narrow to one package

In the GUI: select an image in the Images view and open its vulnerabilities. Either route answers the same questions — what is in this image, which components have known CVEs, at what severity, and (frequently the useful part) whether a newer base image fixes them. Organisation-wide features — policy evaluation, repository watching via docker scout enroll — exist beyond this, but local analysis is the everyday tool.

Reading the results like an adult

The first scan of any real image is alarming — dozens or hundreds of findings — and the correct response is triage, not panic. Severity matters: critical and high findings in packages your application actually exercises deserve attention; a low-severity finding in a library a base-image utility links against usually translates to "rebuild on a newer base when convenient". The practical playbook, in order of effectiveness:

  • Rebuild on a newer base. Most CVEs arrive via the base image, and FROM python:3.13-slim rebuilt this week is quietly newer than the same line built in January. This single habit clears most findings.
  • Shrink the image. Chapter 23's smaller bases and Chapter 24's multi-stage builds are security measures wearing a performance costume — software that is not in the image cannot be vulnerable in it.
  • Update your own dependencies — the requirements.txt and package.json layer is yours to fix.
The rest of the security posture, briefly Scout covers known vulnerabilities in what you ship. The other habits from this book complete the picture, and are worth restating as security items: run as a non-root USER (Ch 21); pass secrets at run time, never bake them in (Ch 22); mount narrowly and read-only where possible (Ch 19); publish only the ports people need, on 127.0.0.1 where they don't (Ch 18); and prefer Official and Verified Publisher images (Ch 3). None of these is advanced. Together they are the difference between a container setup a reviewer nods at and one they write a ticket about.

Kubernetes in Desktop — Chapter 28

Docker Desktop contains a real, single-machine Kubernetes cluster behind a checkbox. This chapter is deliberately short: it tells you what it is, how to switch it on, and when you actually need it — which as a student is later than you think.

What Kubernetes is, in one paragraph

Compose runs your containers on one machine and stops there. Kubernetes is the industry's tool for running containers across many machines — scheduling them, restarting failures, scaling replicas up and down, rolling out updates. It is a large system with its own vocabulary (pods, deployments, services) and its own command-line tool, kubectl. Docker Desktop's cluster exists so you can learn and test against a real Kubernetes API without renting cloud machines.

Switching it on

Dashboard → Kubernetes view → Create cluster (the flow since Docker Desktop 4.51), choosing a provisioning method:

Kubernetes versionFixedSelectable

Kind is the better default for learning: faster, versioned, and multi-node lets you see scheduling actually happen. The cluster registers a kubectl context named docker-desktop; if your kubectl is pointed elsewhere, switch:

Notes from Docker's documentation worth knowing: on Linux, kubectl must be installed separately; the cluster does not upgrade itself when Docker Desktop updates — you reset and recreate it; and the Kubernetes settings tab (Chapter 14) has the reset button.

Do you need this yet? If a course, an internship posting, or curiosity says "Kubernetes", this checkbox is the cheapest possible entry point — a real cluster, on hardware you already own, deletable in one click. If not: everything else in this book stands entirely without it, and Compose (Ch 25) is the right tool for every multi-container project a student is likely to build. Leave the cluster off when unused; it consumes real memory doing nothing.

Part VII — Practice & Reference

Housekeeping & Disk Space — Chapter 29

Docker accumulates. Stopped containers, superseded images, orphaned volumes, build cache — none of it cleans itself up, and one day your disk is full. Five minutes a month prevents it.

See where the space went

docker system df        # images, containers, volumes, build cache — with "reclaimable"
docker ps -a            # how many stopped containers have you collected?
docker image ls         # any images you'll never run again?
docker volume ls        # volumes whose containers are long gone

The prune family

docker system prune removes, per Docker's reference: all stopped containers, networks not used by at least one container, dangling images (untagged layers left behind by rebuilds), and unused build cache. Two escalations exist:

docker system prune            # the safe-ish default above
docker system prune -a         # ALSO removes all images with no container using them
docker system prune --volumes  # ALSO removes anonymous volumes no container uses

Read the confirmation prompt as a contract. -a means every image without a current container gets deleted — including ones you will want next week and will have to re-pull (a real cost on metered connections, and a rate-limit consideration from Chapter 5). Critically, volumes are excluded by default precisely to protect data; --volumes removes anonymous ones, and named volumes are only ever deleted explicitly (docker volume rm) or via docker volume prune. Your database is safe from a plain prune — keep it that way by keeping data in named volumes (Chapter 19).

The Desktop-specific part

On Mac and Windows, containers live inside the VM's disk image (Chapter 2), which grows to your configured limit and does not shrink just because you deleted things inside it. The size cap lives in Settings → Resources; the Troubleshoot menu's Clean up data (Chapter 30) is the bigger hammer that resets Docker data while keeping your settings. On Windows, the WSL data root can be relocated to another drive (Chapter 6).

The habit version Use --rm on every experiment and one-off (Chapter 16) so most junk never exists; run docker system df when you think of it; run a plain docker system prune at the end of each project or month. That is the entire discipline. People who do this never meet the "no space left on device" build failure; people who don't, meet it the night an assignment is due.

Docker problems sort into layers: the app, the container, the daemon, the machine. Diagnose top-down with the tools you already know, and use the built-in escalation ladder when it really is Docker Desktop itself.

The escalation ladder

When the problem is Docker Desktop itself rather than your containers, the Troubleshoot menu (the bug icon in the Dashboard header, or the whale menu) is an ordered ladder — take the smallest step that fixes it:

  1. Restart Docker Desktop — or docker desktop restart. Genuinely fixes most transient weirdness.
  2. Reset Kubernetes cluster — removes all Kubernetes resources; touch only if you use Chapter 28.
  3. Clean up data — resets Docker data (images, containers, volumes) while keeping your settings. Everything from Chapter 29, at once. Export volumes you care about first (Ch 13).
  4. Reset to factory defaults — everything back to the initial-install state, settings included.
  5. Uninstall (Mac/Linux from this menu) and reinstall — the last resort, and rarely needed.

Diagnostics, for when you ask for help

This gathers Docker Desktop's logs into an archive and can upload them, giving you a diagnostic ID to attach to a support request or GitHub issue — the difference between "it doesn't work" and a report someone can act on. The underlying com.docker.diagnose tool lives at a platform-specific path (C:\Program Files\Docker\Docker\resources\ on Windows, inside Docker.app on Mac, /opt/docker-desktop/bin/ on Linux) if the CLI plugin is unavailable. And when asking a human for help — instructor, forum, classmate — include the output of docker version, the exact command you ran, and the exact error. Those three lines answer the first four questions anyone competent will ask.

Lab Exercises — Chapter 31

Containers become intuitive through breakage, not reading. Each lab targets one load-bearing concept and includes a step where the naive expectation fails — that step is the lesson.

Lab 1 — Lifecycle, witnessed

  1. Run docker run -d -p 8080:80 --name web1 nginx and confirm localhost:8080 responds in your browser.
  2. Watch it in the Dashboard: logs tab open, then refresh the browser page and watch requests appear live.
  3. docker stop web1. Confirm it vanishes from docker ps but not docker ps -a.
  4. docker start web1 — same container returns, port mapping intact.
  5. Try docker run -d --name web1 nginx while it exists. Read the error; explain it using Chapter 17; fix it two different ways.

  1. Run docker run -it --name scratch ubuntu bash; create /notes.txt with some content; exit.

  3. Create a volume, run docker run -it -v mynotes:/notes ubuntu bash, write a file under /notes, exit, remove the container, mount the same volume in a brand-new container: the file persists.
  4. In the Dashboard's Volumes view, find mynotes, browse its files, and export it to a local file.

Lab 3 — Two containers, one network

  1. Run docker run -d --name db -e POSTGRES_PASSWORD=devpass postgres:18 — note: no published port.
  2. Run docker run -it --rm postgres:18 psql -h db -U postgres and watch it fail to resolve db.
  3. Create a network, docker network connect it to db, and rerun the client with --network. It connects by name.
  4. Explain why the database was never reachable from your browser at any point — and why that is the correct configuration.

Lab 4 — Build an image and beat the cache

  3. Add a .dockerignore, put a large junk file in the project directory, and confirm build context size in the build output stays small.
  4. Run docker scout quickview on your image. Rebuild FROM python:3.13-slim instead of python:3.13 and compare the CVE counts and sizes.

Lab 5 — Compose a stack

  1. Write a compose.yaml for the Chapter 25 shape: one built service, one pulled database with a named volume and a healthcheck, depends_on with condition: service_healthy.
  2. docker compose up -d, then find the auto-created network with docker network ls and the grouped project in the Dashboard.
  3. Write data into the database. docker compose down, then up again: data intact. down -v, then up: gone. Say exactly which flag made the difference and why.
